# 东方夜雀食堂料理机制知识库

更新日期：2026-07-12

适用范围：本仓库的推荐算法、Tag 解析、评价预测和用户说明。本文档只记录当前代码仍在使用的机制与边界；特殊经营规则见 `docs/special-business-scenes-notes.md`。

## 评价名称

代码和技术文档使用游戏枚举语义：

| 代码名 | 用户可读名称 |
| --- | --- |
| `ExGood` | 完美 |
| `Good` | 满意 |
| `Normal` | 普通 |
| `Bad` | 不满 |
| `Exbad` / `ExBad` | 极差 |

不使用基于颜色的评价称呼作为逻辑名称。用户界面如需颜色区分，通过主题语义 token 实现，不在机制文档中写死色值。

## 稀客评价模型

稀客每笔标准点单包含一个料理 Tag 要求和一个酒水 Tag 要求。料理与酒水命中的喜好/厌恶 Tag 共同参与评价：

- 每命中一个喜好 Tag：`+1`。
- 每命中一个厌恶 Tag：`-1`。
- 料理点单和酒水点单是独立的满足条件。

当某个特殊经营规则需要预测标准五档评价时，使用以下模型：

1. `ExGood`：总分 `>= 4`，且料理与酒水点单均满足。
2. `Good`：总分 `>= 3`，且至少满足一项点单。
3. `Normal`：总分 `>= 2`，且至少满足一项点单。
4. `Bad`：总分 `>= 1`，但未达到上述条件。
5. `Exbad`：总分 `<= 0`。

怪诞料理大赛和幽幽子挑战存在独立改判或等级分档，不能把上述标准模型直接写成所有挑战的原生规则。

## 当前推荐搜索

当前推荐引擎不假设“酒水固定贡献 1 分”，也不在料理喜好命中达到 3 时提前停止搜索。实际流程为：

1. 从当前游戏运行时目录取已解锁料理、可用材料、可用酒水和稀客 Tag。
2. 对料理和酒水分别生成候选，再组合成完整计划。
3. 料理加料使用有界 beam search。候选材料只保留能满足点单 Tag、命中喜好 Tag、满足特殊目标 Tag，或能压制当前厌恶 Tag 的材料。
4. 加料数同时受用户设置和游戏五格材料上限约束。基础配方里重复出现的材料按实际份数占用格子，不得去重。
5. 硬条件先过滤解锁、库存、排除项、缺失厨具、预算阻止和配方禁忌。满足点单的计划优先；不满足点单但命中稀客喜好的候选可作为“偏好备选”显示，不会被冒充为完成点单。
6. 排序再结合任务/自定义/收藏置顶、喜好与厌恶风险、材料压力、预计利润、酒水库存、厨具和用户权重。

## Tag 生成与压制

料理的有效 Tag 输入包括：

- 配方自带的正面 Tag。
- 额外材料的 Tag。
- 动态 Tag：价格 `< 20` 时生成“实惠”，价格 `> 60` 时生成“昂贵”；带“不可加价”的配方不生成这两个价格 Tag。
- 基础配方材料份数与额外加料数合计 `>= 5` 时生成“大份”。
- 在基础、加料和动态 Tag 完成压制后，再根据当前流行喜爱/厌恶与明星店状态派生“流行喜爱”或“流行厌恶”。

Tag 压制优先使用游戏运行时 `TagRules`。运行时规则不可用时，当前项目已验证的基础顺序为：

- 肉 压制 素。
- 重油 压制 清淡。
- 饱腹 压制 下酒。
- 大份 压制 小巧。
- 灼热 压制 凉爽。

被压制 Tag 保留在 `suppressedTags` 中供界面解释，但不参与后续喜好、厌恶或流行判定。界面使用 `steward-tag-cancelled` 语义样式和删除线表示压制，不依赖某个固定色值。

配方负面 Tag 表示额外材料禁忌。加料搜索在组合前直接排除会命中配方负面 Tag 的材料。

## 运行时数据边界

- 料理、食材、酒水、普客、稀客、Tag 映射和 `TagRules` 来自当前游戏运行时目录，不从社区攻略或仓库内历史静态表推测。
- 已解锁料理、材料和酒水库存以单次 `RunTimeStorage.GenerateSaveData()` 生成的快照为权威来源。`recipes` 为空时等待下一轮，不发布“全内容可用”。
- 流行料理 Tag 从 `RunTimePlayerData.GetPopFoodTags(...)` 读取；明星店从 `RunTimeDayScene.GetTrackedSwitch("Aya_FamousIzakaya", false)` 读取。明星店开启且流行喜爱为“招牌”时，只启用明星店效果，不重复占用 `popularFoodTag`。
- 当前推荐类型没有流行酒水字段，也没有基于硬编码联动 key 的角色显隐表。稀客可用性以游戏运行时稀客目录、场景和有效 Tag 为准。
- `GuestFoodEasterEggData` 当前只写入运行时诊断。推荐类型、偏好设置和推荐引擎均没有“稀客彩蛋”执行路径；在完成游戏数据、原生改判路径和实机行为验证前，不对外宣称或执行这类规则。

## 开发约束

- 新增或修改评价、Tag、特殊顾客或挑战规则前，必须用游戏运行时数据、`Assembly-CSharp` 结构和 IDA 执行路径交叉验证。
- 数字 Tag 映射以游戏资源或运行时 `DataBaseLanguage` 为权威来源；重新提取步骤见 `docs/addressables-tag-mapping-playbook.md`。
- 推荐输出必须保留硬条件、喜好/厌恶命中、被压制 Tag、预算和特殊经营规则原因，便于用户与日志对照。
- 未进入当前类型和执行路径的历史功能，不得继续在 README、帮助页或机制文档中宣称为已支持。
