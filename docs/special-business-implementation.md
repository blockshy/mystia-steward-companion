# 特殊经营实现

更新日期：2026-09-02

本文只记录 Mod 对已确认特殊经营规则的推荐和自动化策略。游戏原生规则见[特殊经营游戏规则](special-business-scenes-notes.md)，通用订单与自动化安全边界见[订单捕获与生命周期](runtime-order-lifecycle.md)和[自动化运行时](automation-runtime.md)。

## 共同架构

- C# challenge 上下文、订单角色和运行时匹配位于 `mods/bepinex/src/Save/SpecialBusiness/`。
- 前端规则位于 `apps/companion/src/companion/domain/special-business/`，通过注册表按精确的 `challengeType` 接入。
- “原订单目标”用于定位和验证真实订单，“实际执行目标”用于推荐、开锅和送达；两者不能互换。
- `executionPlans[0]` 是页面首项、自动化初始锁和游戏 UI 目标的唯一主执行方案。场景模块不能再选第二次。
- 所有跨帧状态保留挑战类型、所属对象、订单角色、匹配/执行目标、标签（Tag）策略签名、经营轮次、具体订单类型、订单/控制器指针和订单实例序号。
- 挑战类型、角色、回调捕获对象、阶段、标签、修订号或对象标识不完整时停止相关功能，不把特殊订单转回普通规则继续执行。

## 怪诞料理大赛策略

- 第一阶段选择能稳定命中至少三个喜好标签的料理/酒水组合。
- 第二阶段和第三阶段分身保留原订单，只在原料理上选择安全加料，并谨慎要求预估 `ExGood` 和当前目标标签。第三阶段的 `ExGood` 是安全策略，不是游戏最低要求。
- 目标剩余时间不足时不开始新锅。`CookingJob` 记录开锅时的挑战类型、阶段和标签签名；出锅时签名变化或成品标签不符则回收成品，不送到旧目标。
- 古明地恋本体护盾期按揭示的正面、厌恶和酒水标签规划；破防后按剩余目标分、预算和提交次数共用同一投食评分入口。
- 本体与分身必须通过生成类型、阶段、订单形态和控制器标识区分，不能只看稀客 ID。

## 幽幽子策略

- 第二阶段按当前稀客标准点单评价寻找 `ExGood`：满足料理/酒水点单、避开该稀客厌恶，并在点单外至少命中两个喜好。无完整方案时保持阻断，不降级。
- `Story_Yuyuko` 第三阶段使用 `story-level-sum`：保留原料理/酒水，等级合计至少 `5` 才作为推进方案，`>= 8` 优先。
- `Challenge_Yuyuko` 的 `SpecialOrder` 使用 `retake-tag-order`：满足两项点单并至少增加一个额外喜好，两个额外喜好的方案优先。
- `Challenge_Yuyuko` 的精确 `NormalOrder` 使用 `retake-food-modifiers`：只保留原料理/酒水，仅以实际生效的厨具、价格、大份或相对原配方新增加料所产生的标签判断能否从 `Normal` 提升。
- 可能开锅前固定保存完整执行目标。评价前重新读取并核验加料、成品、订单实例、`PeekOrders()` 和回调绑定。
- 只有显式命名且完整依赖与订单标识检查全部通过的幽幽子 `SpecialOrder` 可以使用专用实时控制器路径；该例外不能抽象成一般管理器降级方案。
- 料理已送达后可以先释放厨具占用，评价确认继续有界等待；超出收尾预算时只进入待人工确认状态，不重复送达或猜测成功。

## Mizuchi 策略

- 只匹配 `Story_Mizuchi` 与 `Story_Mizuchi_1/_2/_3`，基础场景和三场试炼使用不同协议角色，不互认。
- 共用的标识读取器精确复核评价委托、两层回调捕获对象、所选稀客/分组控制器/订单/控制器中的稀客标识、控制类型和目标材料。
- `(-1,None)` 是普通订单保护期；合法活动目标按当前被控制的稀客把订单分为附身订单和普通订单；其他组合标记为未确认。
- 附身订单除原料理/酒水标签外，基础场景必须额外加入 `5002`，试炼必须加入 `5005`；普通订单禁止该场目标材料。
- 自定义料理只有明确包含目标额外材料时才能进入附身候选。目录、库存、禁忌或五格上限不允许时保持无方案。
- 回调、订单标识、材料或订单实例发生变化时停止后续游戏操作；不通过旧角色、名称、文本或宽松反射恢复。

## 血池地狱策略

- 只有挑战类型、具体订单类型以及订单/控制器中的稀客都精确确认为 BOSS `1003` 时，才标记 `yuuma-boss-order`。声明为 `OrderBase` 时必须通过共用的类型转换恰好解析为一种具体订单。
- 保留原订单条件，并先搜索同时满足两项动态料理标签的严格方案。`SpecialOrder` 严格无解时保持阻断；只有 BOSS `NormalOrder` 可在严格无解且原料理/酒水仍合法时进入明确的低收益推进方案。
- 双标签使用 `require + all`。Yuuma 严格搜索按 `matched/reachable/blocked` 保留可达分支，不能被通用束搜索提前裁掉。
- 低收益推进由 `/orders/normal/complete-first` 的 `allowYuumaControlledProgression` 显式授权，并携带完整预测
  标签；预测必须确实未全部命中。该许可须贯穿后端目标、`CookingJob` 和快照中的订单标识，严格任务与低收益推进任务
  不能复用；它不放宽原订单、实际料理、订单标识、厨具锅次或结算路由。
- 规范策略签名与当前目标修订号分离。修订号必须作为独立正数贯穿快照、Worker、请求、后端目标和 `CookingJob`，防止 `A -> B -> A` 时接受第一轮迟到动作。
- 已匹配成品在当前主设备配置、配置修订号和 `YuumaSettlement` 执行许可暂不可用时保留在原锅并可恢复；玩家取走或替换成品才转为手动交接。
- 最终结算持有一次执行许可，串行执行料理/酒水提交、重新取得订单、厨具复位、`AfterPlayerExtract`、fulfilled、评价和经营记账。任何不可逆阶段结果不确定时都进入待人工确认状态，不重复执行。
- 每次厨具操作都从当前物理目录按索引、游戏对象标识、网格位置和锅次重新取得控制器。事件锁定、移除、替换或坐标变化会停止旧任务；不主动解锁、恢复或扫描替代厨具。

## 禁止路径

- 不枚举 `AllOrders` / `AllOrdersData` 建立活动订单，不用 HUD 或 manager 扫描补建一般捕获。
- 不按名称、文本、模糊类型、托管 hash、桌位或料理相同合并订单。
- 不把特殊经营条件写入普通推荐状态后让普通规则猜测。
- 不保留旧挑战角色、旧签名、旧请求参数、通用直接评价、手动回调兼容或 UI 模拟路径。
- 不在文档或代码写死来自数据资产的伤害、阈值、倒计时或投食次数。

## 维护与验证

修改场景模块时同时检查游戏规则证据、首选推荐方案、自动化、游戏 UI 目标和日志中的对象标识。自动化测试与实机覆盖见[特殊经营验证](special-business-validation.md)。
