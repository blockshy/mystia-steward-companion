# Repo Memory

## 当前项目定位

仓库项目名统一为 `mystia-steward-companion`，定位为《东方夜雀食堂》BepInEx IL2CPP Mod 与 Tauri 伴随窗口。桌面端是 A 设备本机主入口，Android 端只作为 B 设备通过 LAN 连接的移动伴随窗口。

## 关键目录

- `mods/bepinex/`：插件源码、本地 API、运行时读取、构建脚本和 Mod 文档。
- `apps/companion/src/`：伴随窗口 React 工作台、推荐算法、tag 规则、类型和结构化数据。
- `apps/companion/src-tauri/`：Tauri 伴随窗口壳，桌面能力与 Android 移动端边界在这里隔离。

## 开发事实

- Mod 不编译引用额外的游戏业务 DLL，运行时通过反射读取游戏已加载的 IL2CPP interop 类型。
- 用户可见项目名、安装目录和发布产物使用 `mystia-steward-companion`。`v1.2.x` 仅暂时保留 Local API 启动阶段执行的 `favorites.source=manual` 转自定义料理一次性数据迁移，计划在 `v1.3.0` 删除。自 `v1.2.0` 起不再读取旧 GUID 配置；除该数据迁移外，旧名称只允许出现在上游来源说明中，不保留旧路径、旧类型或旧 API 别名。
- `References/` 只放本机编译 DLL，不提交仓库。
- 推荐数据来自游戏运行时 `RuntimeDataCatalog`；`build-release.ps1` 和发布包只包含 Mod DLL 与伴随窗口程序。
- 用户安装和测试优先使用已验证的 BepInEx Bleeding Edge #783 Windows x64 IL2CPP 包：`BepInEx-Unity.IL2CPP-win-x64-6.0.0-be.783+c58c42d.zip`。#784 及之后构建当前不建议用于本项目，后续如需支持新版 BepInEx，必须重新实测并检查运行时日志。
- 独立伴随窗口默认通过 `127.0.0.1:32145` 读取运行态；该回环 listener 必须始终保留。`LocalApi.AllowLanConnections=true` 只会额外开启 LAN listener，供可信局域网设备连接；LAN 配置和 Token 重置只能由 A 设备本机回环客户端调用。所有正式 Tauri runtime 统一通过 Rust TCP command 访问 API，只有浏览器开发模式直接 fetch；Rust 代理的连接超时最长 5 秒，响应读取超时按前端命令要求最多允许 60 秒。除 `/health` 外，本地 API 使用 `X-Mystia-Steward-Companion-Token` 授权，远程伴随窗口需要手动输入 A 设备 endpoint 和 token，代理只接受 loopback/private/link-local IPv4 endpoint。API 只接受规范路径，不提供 `/` 或 `/api/*` 别名；只读查询使用 `GET`，所有文件、运行时、配置、控制权、诊断和更新副作用使用 `POST`，现阶段写操作参数仍可使用 query。`/updates/status` 会归并 updater 结果并可能写入或删除状态文件，因此也使用 `POST`。
- 伴随窗口控制端口固定为 `127.0.0.1:32146`，支持 `show`、`toggle`、`exit` 消息。Tauri 在初始化窗口前原子占有端口并移交预绑定 listener，绑定失败的并发实例只通知端口所有者后退出；Mod 热键先通知已有窗口，控制端口不可达时进入 single-flight launch，所有权保持到端口可连接或明确超时。
- 桌面伴随窗口使用官方 `tauri-plugin-window-state`，在 Tauri app config 目录的 `.window-state.json` 中保存普通窗口位置、大小和最大化状态。插件在最大化或最小化期间保留最近一次普通窗口边界，恢复位置前检查窗口是否仍与可用显示器相交；可见性、最小化、装饰和全屏不进入持久化状态，关闭到托盘或临时最小化不会让下次启动保持隐藏。
- 桌面主窗口在 Tauri 配置中初始隐藏，窗口状态插件先恢复普通边界和最大化状态，Rust setup 再显示并聚焦，避免启动时先显示默认位置再跳到保存位置。桌面最小宽度固定为 640 逻辑像素；核心内容在 640px 及以上保持至少双列。640-719px 使用紧凑窄桌面布局：Header 品牌区可以与连接工具条分行，但连接工具条内部的 endpoint、Token、连接和刷新保持单行；设置专用 SegmentedControl 按内容收缩且标签单行，不得强制全宽等分或任意断词。三项状态摘要保持三列，一级导航使用五列两行完整显示；低于 640px 的移动窄屏才允许连接工具条内部换行、纵排状态摘要和横向滚动一级导航。全平台图标以 `apps/companion/src-tauri/icon-source.svg` 为唯一母版；母版根元素通过 `data-icon-background` 声明通用底色、通过 `data-android-background` 声明 Android adaptive 底色，并用 `icon-background` / `icon-foreground` 提供明确分层。`pnpm icons:generate` 从母版重建桌面 PNG、Windows tile、九层 256-first ICO、tray、固定 chunk 顺序的 ICNS、不透明 iOS 图标、Android legacy/adaptive 图标、APK 工程实际资源和 favicon；`pnpm icons:check` 对全部生成物做字节幂等、尺寸、alpha、安全区和容器结构校验。Android legacy 固定为 48/72/96/144/192，规避 Tauri CLI 2.11.2 的 hdpi 49px 生成错误；adaptive foreground 使用缩小后的前景层，除官方安全区外还需通过额外视觉留白校验，`icons/android` 与 `gen/android/app/src/main/res` 的图标必须同步。
- 伴随窗口 `设置` 页分为 `窗口 / 连接 / 推荐 / 自动化 / 更新`。`窗口` 负责背景透明度、文字透明度、90% 至 130% 字体大小、焦点切换行为、切换冷却时间、置顶、鼠标穿透锁定、主题、手柄导航和显示调试信息；`连接` 负责本机地址、LAN 状态、按默认网关和接口类型排序的结构化 LAN endpoint、LAN 监听地址、Token 和可信局域网访问，多地址必须逐项复制，不能静默使用字符串排序首项；`推荐` 负责经营中订单排序、稀客专注模式默认精简、缺失厨具硬过滤、任务料理置顶、收藏料理/收藏酒水置顶、推荐权重、预算处理、带库存显示和名称/库存排序的排除材料/酒水、同基础料理展示数量、实验性游戏界面置顶和目标厨具高亮；`自动化` 负责实验性自动化总开关和参数。字体大小按客户端 localStorage 独立保存，默认 100%，通过单一 CSS 比例同步 Tailwind、Mantine、自定义控件和继承文本，不改变固定间距、图标、窗口几何或响应式断点。背景透明度通过 Tauri transparent window + CSS 背景 alpha 实现，旧 `windowOpacity` 会迁移为背景透明度；文字透明度单独影响普通文字、图标和辅助徽章内容，主操作按钮保持不透明；稀客专注模式的料理/酒水显示数量在专注模式浮层内调整。鼠标穿透通过 Tauri 原生窗口忽略鼠标事件实现，`F10` 切换，`F8`/`RS Click`/托盘显示会自动关闭穿透。
- 伴随窗口固定包含 `概览`、`普客`、`稀客`、`自定义推荐料理`、`经营中`、`任务`、`修改`、`帮助`、`设置` 页签；`任务` 内含 `任务列表` 和 `稀客邀请`，`日志` 页签只在 `显示调试信息` 开启后显示。任务列表合并 available 与 active tracked 项，使用 `全部 / 可接取 / 可完成 / 进行中 / 待确认` 受控页签，同一时间只显示一个列表；同 label 重叠时 tracked 优先，`全部` 按状态、中文标题和 label 稳定排序，页签计数保留零值，窄屏页签栏允许横向滚动。帮助页内容来自 `apps/companion/src/data/help-content.json`，页面只做搜索、目录树和详情渲染；用户可见功能或排查流程变化时需要同步该 JSON。
- 稀客订单专注页顶部不重复显示模式标题和说明，只保留全宽右对齐的精简模式、料理/酒水数量和退出控制组。稀客页、经营中页和专注模式的生效自定义配方入口统一放在料理推荐标题的 action 区，紧凑可见文案保留完整 `aria-label` 和 tooltip；展开内容仍位于标题后、料理列表前。手柄确认展开时通过声明式确认焦点 key 进入详情滚动区，鼠标点击不抢焦点。
- 伴随窗口 UI 基础组件集中在 `apps/companion/src/components/ui/`，并通过 `apps/companion/src/components/ui-kit/` 对外提供统一导出。当前项目组件层以 Mantine 组件为交互基础，封装了按钮、输入、选择框、多选框、页签、开关、滑杆、树形目录、折叠面板，以及项目展示组件 `ListPanel`、`InfoLine`、`StatusCard`、`Metric`、`EmptyRow`、`EmptyState` 和选项组。视觉形态以企业控制台式扁平分组、直角窄边框、标题条和表格化行项目为准，保留项目既有配色；除开关、滚动条滑块等需要圆形几何的控件外，不再使用圆角。后续不要继续复制外部模板风格组件，也不要在业务页面手写第二套开关/滑杆/卡片样式。
- 伴随窗口根滚动区域固定预留纵向滚动条槽位，避免页面高度变化时滚动条挤占宽度造成内容横向跳动；窗口、下拉和日志滚动条使用主题色并跟随背景透明度。
- 焦点切换支持两种模式：隐藏伴随窗口再聚焦游戏，或保持伴随窗口悬浮并只聚焦游戏。保持悬浮依赖窗口置顶，独占全屏游戏可能覆盖置顶窗口，推荐窗口化或无边框窗口化。
- 伴随窗口退出跟随不只依赖本地 API `/health` 失联，还会监控启动参数中的 `--game-pid`。游戏窗口 X、游戏内退出按钮、或 Unity 退出阶段未及时发送 `exit` 控制消息时，都应由 PID 监控兜底关闭伴随窗口。
- `修改` 页通过 `/inventory/set` 和 `/inventory/bulk-set` 在 Unity 主线程写入当前运行时材料和酒水库存；材料和酒水列表可按名称或库存排序。页面只保留单项 `-10`、`+10`、`99` 和当前存档可编辑材料/酒水批量设为 `99` 快捷按钮，用户仍需在游戏内保存才能持久化。
- 库存写入只走 `RunTimeStorage` 四个 Range 原生入口并在写后精确读取数量；不得在原生异常时直写 `Ingredients` / `Beverages` 私有字典。库存、订单和稀客邀请的主线程命令按类型有界排队且每帧最多执行一个；排队超时会取消未开始命令，已开始命令等待确定结果，控制器销毁会唤醒所有等待者。Local API handler 同样有并发上限，停止服务时先拒绝新连接并关闭在途 socket。
- 伴随窗口 `日志` 页保留总日志 `BepInEx/config/MystiaStewardCompanion/aggregate-mod.log` 开关、总日志目录、文件上限、诊断包导出，以及仅限回环客户端使用的 BepInEx 控制台显示/隐藏按钮。总日志默认关闭，启用后捕获 BepInEx 全局日志源，并接收自动化、经营诊断和运行时固定数据诊断；每条记录标注时间、channel、来源和线程，单个文件 10 MB 后拆分为递增编号分片。默认保留 30 个文件，约 300 MB，超过上限时删除最旧分片；该上限不保护 BepInEx/Unity 共享 output log，后台 worker 不得无限异常重试刷共享日志，Mod 也不接管共享日志文件。订单相关自动化日志使用 `trace=R-0001` / `trace=N-0001` 标识单笔稀客/普客订单，经营中页显示同一“日志”标识；排查长时间或难复现问题时优先让用户开启总日志、复现后提供当前文件和相关分片。
- Mod 不修改全局 `BepInEx.cfg`，也不释放宿主控制台。默认启动自动显示关闭且不覆盖 BepInEx 全局选择；游戏电脑回环客户端可显式显示或隐藏当前进程窗口。隐藏只改变可见性，日志链保持活动；`SetConsoleUtf8` 只调整当前已创建控制台的编码。
- 自动更新检查、下载和安装由单操作门串行；`UpdateService` 在 Local API 生命周期内运行一个可取消调度器，成功按配置间隔续检，失败按 15m/30m/1h/2h/4h/6h 退避。关闭 Local API 会先阻止新操作，再通过统一生命周期令牌取消自动/手动检查和下载，等待 handler、活动操作和调度器退出；取消检查恢复原稳定状态并立即到期，不保留虚假 `checking`。服务启动时把强制退出留下的 `checking/downloading` 恢复为当前元数据对应的稳定状态并立即安排检查，同时只清理下载一级目录内符合 `.<semantic-version>.<guid>.tmp` 的残留目录。状态明确区分最近尝试、最近成功、下次检查和连续失败数，不再使用混合语义的 `checkedAtUtc`。工作台级 `useUpdateManager` 是唯一前端控制器，活动状态 2 秒、稳定状态 60 秒读取主机状态，状态端点连续失败按 2s/5s/15s/60s 退避；状态请求和用户动作分开管理，断连或连接身份变化会清理动作并隔离迟到响应。发现新版后显示非模态提示，可直达更新页或按 endpoint + tag 延后 24 小时。manifest 严格校验 schema 1、版本/tag/channel、包名、SHA256 和长度，包体流式写盘。安装只使用 staged 包内已校验的 updater，且 staged 版本必须高于当前插件版本，旧暂存包只显示为不可安装，不得触发降级。读取更新状态时会归并独立 updater 留下的结果并维护状态文件，因此对应本地 API 不是只读 GET。发布页通过 capability 限定的 Tauri opener 打开；该更新只服务游戏主机 Mod 主包，远程独立 Windows 窗口和 Android APK 不自更新。
- 游戏内 IMGUI 面板已移除；Mod 在游戏侧只保留后台控制器、本地 API、运行时读取、自动化和伴随窗口唤起。
- 仓库不使用 GitHub Actions 自动构建 Release；`.github/workflows/ci.yml` 只保留手动前端检查。版本发布采用 Windows 本机构建后由 GitHub CLI 上传。自动更新发布只支持稳定版 `X.Y.Z` 和预览版 `X.Y.Z-preview.N`；预览版必须是 GitHub Prerelease，用于 `dev` 上测试 `preview.1 -> preview.2 -> stable` 更新链路，稳定版再合并 `main` 发布普通 Release。Release 资产包含 `mystia-steward-companion-bepinex.zip`、`update-manifest.json` 和可直接运行的 `mystia-steward-companion-companion-windows-x64.exe`；如发布机已配置 Android 工具链和签名配置，可通过 `build-release.ps1 -BuildAndroidApk` 或 `publish-release.ps1 -BuildAndroidApk` 额外生成并上传 `mystia-steward-companion-android-arm64-v8a.apk` 和 `mystia-steward-companion-android-armeabi-v7a.apk`。更新清单只指向 Mod 主包，独立 Windows 伴随窗口 EXE 和 Android APK 只给 B 设备跨局域网连接使用。
- 仓库内构建缓存统一通过 `pnpm artifacts:report/prune/clean` 管理。默认 12 GiB 高水位、8 GiB 清理目标、Android 1.5 GiB、.NET 0.5 GiB 和 14 天过期优先级，按文件逻辑大小统计；清理只以完整 Cargo profile/target triple、Gradle build 或 .NET `bin/obj` 为单位，不裁剪 Cargo 单文件，也不得与 Cargo、Gradle、Vite 或 dotnet 构建并发。常用 Tauri/Android package 命令在构建前 prune，直接 Cargo/dotnet 命令需要显式检查。`dist`、References、temp、依赖、Playwright 浏览器和签名材料不自动删除。正常 package/build 使用 staging 完整重建本次 `dist`，不得把旧 APK、manifest、tar、zip 或旧目录带入新发布；`publish-release.ps1 -SkipBuild` 才显式复用现有资产。PowerShell 和 bash package 脚本都只生成 canonical ZIP，缺少 ZIP 工具时必须在触碰旧 `dist` 前失败。
- Android APK 不能从 Windows EXE 直接转换。Android 版按 Tauri mobile 独立目标处理，Android applicationId 固定为 `com.tyukki.mystia.steward.companion`，通过 `apps/companion/src-tauri/tauri.android.conf.json` 覆盖 Android identifier，桌面 Tauri identifier 不变；前端通过 `companion_platform` 识别移动端并隐藏桌面窗口能力；Rust 后端用平台 cfg 隔离托盘、单实例控制、鼠标穿透、窗口状态、全局快捷键和游戏 PID 监控，但本地 API TCP command 与桌面共用。仓库已包含 `apps/companion/src-tauri/gen/android/` 工程和 `src-tauri` library entrypoint；生成的 Gradle Rust 插件使用 Corepack 调用 pnpm，release build 允许连接可信 LAN HTTP endpoint。签名 APK 通过 `pnpm tauri:android:apk:signed` 构建，读取本地被忽略的 `gen/android/keystore.properties`，按 `aarch64` 和 `armv7` 生成拆分 APK，验签后复制到 `mods/bepinex/dist`；release 脚本的 `-BuildAndroidApk` 参数复用该流程。Android Gradle 关闭 Kotlin incremental compilation，避免 Windows 上 Cargo registry 和项目分属不同盘符导致 Kotlin daemon 报 `different roots`。APK 构建需要 Android Studio/SDK/NDK、JDK、Android Rust targets、签名配置和真机 LAN 连接测试；未连接真机时只能验证 APK 构建和包元数据，不能宣称 LAN 已验证。Android 竖屏顶部页签使用横向滚动，焦点或激活页签需要自动滚入可视区域；应用整体需要通过 safe-area inset 避开状态栏和导航栏。
- Android APK 体积优化由签名 APK 脚本注入 `CARGO_PROFILE_RELEASE_STRIP=symbols`、`CARGO_PROFILE_RELEASE_LTO=thin` 和 `CARGO_PROFILE_RELEASE_CODEGEN_UNITS=1`；全局 Cargo release profile 不启用 LTO，避免 Windows-only 发布构建在 Rust 链接优化尾段长时间停顿。
- Tauri mobile 的 Rust lib target 内部名为 `mystia_steward_companion_mobile`，用于避开 Windows MSVC 下桌面 bin `mystia-steward-companion` 规格化后的 PDB 名冲突；桌面产品名、EXE 名、Tauri identifier 和 Android applicationId 不因此改变。
- 默认热键 `F8` 和 `RS Click` 的主语义是游戏与伴随窗口焦点切换；Mod 侧 `RS Click` 只做释放锁存，默认 800ms 可配置冷却由 Tauri 唯一 gate 管理且只在实际 `applied` 后计时。伴随窗口聚焦时由 Tauri 前端处理热键并按设置切回游戏，必须先确认游戏聚焦成功再隐藏窗口。Windows 侧以 `SetForegroundWindow` 非零返回或当前前台窗口属于目标进程确认成功，不把激活转换期的精确 HWND 瞬时不一致误判为失败。

- 特殊经营规则按模块维护：C# 位于 `mods/bepinex/src/Save/SpecialBusiness/`，前端位于 `apps/companion/src/companion/domain/special-business/` 并通过 registry 接入；规则构造在 `rules/`，普客执行目标在 `normal-targets/`，怪诞料理运行时策略集中在 `WackyCookingCompetitionRuntimePolicy`。
- 怪诞料理大赛的游戏原生规则按阶段不同：第一阶段按喜好 Tag 命中数改判；第二阶段先要求 `ExGood` 再检查当前目标 Tag；第三阶段分身接受 `Normal` 以上并由目标 Tag 再改判。前端对第二阶段和第三阶段分身均保留原订单料理/酒水，并要求预估 `ExGood` 与当前目标 Tag；第三阶段的 `ExGood` 条件是 Mod 的保守策略，不得写成游戏原生最低门槛。
- 怪诞料理大赛分身只在原料理上选择安全加料。`AutomationCookingJob` 保存阶段、目标 Tag 签名、原订单 match 目标和实际 execution 目标；出锅前比较签名，再用 `Sellable.Tags` 校验成品。签名或 Tag 不符时只对本 generation 执行 commit-once `StoreFood`，前后端共同抑制已确认失败的组合。
- 古明地恋本体不能只凭 `guestId=2006` 判断；分身优先读取 `GuestControllerSpawnType=GhostInChallenge`，本体还需结合阶段、订单类型、手动控制器状态和真实 controller。护盾期按揭示 Tag 选择并走通用评价；破防后保留原订单、按剩余目标分/预算/剩余提交次数规划，并通过带 Boss 原生评价回调的 live controller 进入 `EvaluateOrder()` / `OverrideEvaluationCallback`。破防期推荐与自动化共享同一规划入口。
- 幽幽子第二阶段只在稀客标准评价达到 `ExGood` 并触发正面符卡后推进；候选满足当前稀客料理/酒水点单、避开该稀客自身的厌恶，并在排除点单 Tag 后命中至少 `2` 个额外喜好 Tag。该阶段不使用任何三阶段规则，没有可预测达到 `ExGood` 的完整组合时保持无计划并输出候选阶段诊断，不得降级执行。
- 幽幽子三阶段必须先按版本、再按订单形态拆分。剧情版 `Story_Yuyuko` 主幽幽子使用 `story-level-sum`，按已送达料理与酒水等级合计分档：`>= 2` 为 `Normal`、`>= 5` 为 `Good`、`>= 8` 为 `ExGood`。重修版 `Challenge_Yuyuko` 的稀客 `SpecialOrder` 使用 `retake-tag-order`，按最终料理与酒水的完整 Tag 走标准点单评价：满足两项请求 Tag 后基础为 `2`，排除点单 Tag 后的当前稀客额外喜好/厌恶继续影响结果；推荐以每个额外喜好至少 `+1`、每个厌恶 `-1` 计算保守下界，`Good>=3` 才推进，`ExGood>=4` 优先。不得把这类订单收窄为精确料理/酒水，也不得套用 modifier-only 契约。
- 重修版精确料理/酒水的 `NormalOrder` 才使用 `retake-food-modifiers`。精确匹配先建立 `Normal=2`，仅统计实际生效的厨具/价格/大份等动态料理 Tag，以及相对原配方新增且实际生效的额外材料 Tag；原料理基础 Tag 不得作为 modifier 二次计分。搜索前只保留原料理/原酒水，并单独生成和合并无加料候选；结果 `>= 3` 才推进，等于 `2` 时以无加料精确订单清理，结果 `< 2` 阻断。
- 重修三阶段 `NormalOrder` 的完整 `NormalOrderExecutionTarget` 在开锅确认后锁存，避免扣除库存后重算出不同 extras/mode；后续送达、评价和厨具容量估算统一消费该目标。局部关闭普客自动化或全部普客阶段时保留仍绑定目标/job 的状态，全局关闭仍走取消屏障。原生评价前要求实际 `Sellable.Modifier` 与请求 extras 精确全等，并要求 `Tags.Except(RawTags)` 映射出的 addedTags 与 `expectedFoodModifierTags` 精确全等；读取失败或不一致时暂停。该契约不得用于 `SpecialOrder`。
- 幽幽子订单未 fulfilled 时只等待；已送齐后 capture 优先严格复核、manager scan fallback。剧情版只复用同一原生 order/controller 捕获的 `onEvaluate` 调用 `EvaulateManualOrder`；重修版确认 `_50` / `_70` 进度回调后调用 `EvaluateOrder()`。`SpecialOrder` 门禁精确校验实际加料，并确认两个请求 Tag 存在于实送料理/酒水的完整 Tag 数组；完整喜恶集合与最终档位交给游戏原生评价，不比较前端预测集合。`NormalOrder` 则继续校验 exact extras/expected modifier contract。对应回调、送达目标或评价语义不可确认时暂停，普客执行目标、稀客 execution plan、推荐首项和自动化目标共享同一评分入口。
- 挑战/BOSS 订单可能表现为 `OrderBase/Normal` 或 `SpecialOrder`，必须由统一分类器标记归属。live `OrderBase` 客人字段不可读时不能只因 `guestId` 缺失拒绝，但 controller、评价回调、送达目标和原订单不变量仍必须严格确认。血池地狱挑战的 BOSS 订单阻止标准自动化；新增 BOSS 自动化前必须用实机总日志验证移动、送达、评价和结算副作用。
- 自动化步骤和总日志记录 `rule=`、原始/有效挑战类型、match/execution 对照、评价回调证据和阻断原因。任何跨帧任务都保留挑战类型、阶段、订单角色和目标签名，绝不能在空目标 Tag 时回退到当前轮换 Tag。
- 特殊经营激活时，可以在订单层按经营中当前排序跳过没有主执行计划的订单，选择第一笔存在 `executionPlans[0]` 的稀客订单；选中后页面料理/酒水首项、自动化初始锁、游戏界面置顶和目标厨具高亮只能消费同一个主计划。没有主计划时不发布目标，也不得从后续计划另选目标。
- 稀客订单专注模式支持精简模式和料理/酒水显示数量配置；精简模式隐藏推荐料理 Tag 并压缩推荐面板间距，显示数量包含收藏置顶项。默认精简状态在 `设置 -> 推荐` 配置，进入专注模式后仍可临时切换并记忆。
- 实验性自动化由设置页总开关启用，经营中页按稀客订单和普客订单分组配置。稀客使用 `autoPrep*` 阶段配置，普客使用 `autoNormal*` 阶段配置；普客送酒、开始料理、送料理、完成订单和出错暂停互不复用。设置页参数控制稀客/普客并发、最大重试和最大回退，默认值为 `2`、`3`、`3`、`2`；稀客和普客完成订单都按单笔订单 readiness 独立推进，并优先处理已满足料理和酒水的订单，但本地 API 调用仍串行执行。开启自动开始料理后固定尝试完成原生 QTE 奖励结算，不再提供跳过或完成 QTE 的配置开关；该流程不会打开游戏音游面板，失败时只显示诊断并继续料理流程。稀客和普客的酒水、目标料理都通过统一运行时送达 helper 直接送至订单，不再经过送餐盘、保温箱或游戏料理暂存容器作为自动化中转；只有非目标/黑暗料理出锅，或出锅后目标订单/可执行控制器连续不可达时，才作为恢复动作写入游戏保温箱。普客自动化需要开启“启用普客处理”且至少开启一个实际阶段；临时失败应继续等待并重试，非临时失败才按对应订单类型配置暂停。稀客与普客暂停状态不能共用，普客内部也要按订单 key 隔离暂停。

## 推荐排序口径

- 经营中/稀客推荐排序可由伴随窗口 `设置` 页的任务料理、收藏料理、收藏酒水置顶开关、自定义推荐料理单条置顶和推荐权重共同控制。固定顺序是硬过滤、任务料理置顶、自定义推荐料理置顶、收藏料理/酒水置顶，最后进入普通权重排序；默认均衡预设综合稀客偏好、厌恶风险、加料数量、资源压力、成本、利润、酒水库存和当前厨具可做等目标。
- 当前推荐权重项包含料理偏好命中、酒水偏好命中、减少厌恶标签、减少加料数量、少用低库存食材、降低食材成本、提高预计利润、优先酒水库存和当前厨具可做。资源压力优先惩罚低库存材料，并对额外加料加权；不要再使用“总成本越高越靠前”作为收益判断。收藏料理和收藏酒水不是权重项，只能通过对应置顶开关控制。
- 稀客和经营中主推荐使用统一料理/酒水候选池；满足当前点单料理 Tag / 酒水 Tag 的结果优先，不满足点单但命中稀客喜好的结果直接进入同一列表并标注为“偏好备选”。完整候选先构造并排序执行计划，`executionPlans[0]` 是唯一主执行计划，其料理与酒水必须投影为页面首项；经营中页和稀客订单专注模式再按用户设置截取其余展示行，不再维护独立喜好备选数组。料理推荐优先 3 分以上候选，但低于 3 分且满足点单的料理仍要作为兜底显示。
- `blockedDiagnostic` 只在最终 `executionPlans` 为空时生成，并复用正式候选、特殊经营过滤和计划构造入口。它按料理目录/点单 Tag/解锁/基础材料/厨具/特殊规则与厌恶安全、酒水库存/排除/Tag、预算、特殊评价和最终计划记录首个清零阶段，附带缺失材料、所需/已摆厨具、剩余预算与最低组合价。该诊断只解释结果，不参与过滤、排序、业务缓存身份或目标选择；自动化总日志用稳定状态签名在当前会话内维护最多 64 条有界去重集合，稀客和普客分开，切换自动化会话时清空，避免同一状态重复刷日志。
- `排除缺失厨具` 开启且已读取厨具快照时，统一推荐列表会隐藏当前场景未摆放对应厨具的料理；厨具类型 1-5 映射为煮锅、烧烤架、油锅、蒸锅、料理台。
- 夜间 live 厨具控制器的唯一来源是 `CookSystemManager.get_AllCookers` 的精确 `Dictionary<Vector3Int,CookController>`；开锅、快照和高亮都通过 `RuntimeConcreteCollectionReader.TryReadDictionary` 共用该来源。完整厨具能力只接受 `AllAvailableCookerType` 的精确泛型 enumerable 读取。已有厨具暂时忙碌、被自动化预约或被挑战机制禁用时属于可重试等待，不等于集合读取为空。
- 运行时稀客目录在前端分为普通地点可选的 `rareCustomers` 与不要求地点的 `rareCustomerProfiles`。后者只提供特殊经营评价需要的 canonical ID 与喜好/厌恶 Tag；映射 ID、名称和静态 Tag 不能作为回退。两份投影都进入推荐数据签名，特殊 NormalOrder 目标缓存也绑定该签名。
- 稀客收藏保存在 `BepInEx/config/MystiaStewardCompanion/favorites.json`，按 `customerId + foodTag` 收藏料理方案（含加料 ID），按 `customerId + beverageTag` 收藏酒水。自定义推荐料理保存在 `BepInEx/config/MystiaStewardCompanion/custom-recipes.json`，按 `customerId + foodTag/null + foodId + extraIngredientIds` 生效，其中 `foodTag=null` 表示该稀客全部点单料理 Tag；顶层 `enabled` 是整个功能的门禁，关闭不改写单条状态。管理页可按稀客或基础料理派生分组，页面/分组/单条 flags 更新使用同一原子端点，推荐优先级只在同一稀客内移动。旧 `favorites.source=manual` 仅在 `v1.2.x` 作为一次性迁移输入：Local API 启动阶段先原子写入自定义料理，再删除旧收藏条目，使后续读取和 CRUD 端点不承担迁移副作用；该迁移计划在 `v1.3.0` 删除，不是正常推荐路径。收藏料理置顶、收藏酒水置顶、自定义推荐置顶和自动化收藏限定都不绕过解锁、库存、预算、排除项和缺失厨具过滤。
- 经营中稀客推荐会根据当前稀客资金构造预算上下文。预算策略支持阻止超预算、仅提示和忽略预算；订单级 `isFreeOrder=true` 时不应用付款预算阻止，非免费订单继续按当前预算策略判断。排除材料会同时过滤基础配方和加料，排除酒水只过滤酒水候选。排除项下拉的库存显示来自 `RuntimeSets`，排序方式只影响设置页选项展示，不进入推荐缓存签名。预算、免费订单状态、排除项、缺失厨具和同基础料理展示数量都必须进入推荐缓存签名，避免设置变化后继续显示旧结果。
- `同基础料理显示` 默认值为 1。同一基础料理存在多个加料变体时，稀客页和经营中页只展示主计划之外当前排序最靠前的指定数量；主计划料理始终保留在首项。收藏匹配仍按基础料理和加料精确匹配；自动化收藏限定只有在总开关、对应阶段和订单自动化权限均开启时参与主计划归一化，并且必须在执行计划上限截断前处理。自动化开始时只锁定主计划，不得依赖裁剪后的 UI 行或扫描后续计划。
- 经营中订单显示顺序默认是首次出现时间升序；切换为稀客分组时，同组内仍按首次出现时间升序。新订单不应在点单顺序模式下插到已有订单前面；自动化和置顶目标必须使用页面同一排序结果。
- 推荐行需要显示库存数量；料理行需要显示厨具、基础配方和加料，并对这些定位信息做高亮。
