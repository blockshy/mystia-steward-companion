# Repo Memory

## 当前项目定位

仓库项目名统一为 `mystia-steward-companion`，定位为《东方夜雀食堂》BepInEx IL2CPP Mod 与 Tauri 伴随窗口。桌面端是 A 设备本机主入口，Android 端只作为 B 设备通过 LAN 连接的移动伴随窗口。

## 关键目录

- `mods/bepinex/`：插件源码、本地 API、运行时读取、构建脚本和 Mod 文档。
- `apps/companion/src/`：伴随窗口 React 工作台、推荐算法、tag 规则、类型和结构化数据。
- `apps/companion/src-tauri/`：Tauri 伴随窗口壳，桌面能力与 Android 移动端边界在这里隔离。

## 开发事实

- Mod 不编译引用额外的游戏业务 DLL，运行时通过反射读取游戏已加载的 IL2CPP interop 类型。
- 用户可见项目名、安装目录和发布产物使用 `mystia-steward-companion`。`v1.3.0` 已删除 `v1.2.x` 的收藏到自定义料理一次性迁移；`favorites.json` 与 `custom-recipes.json` 现在是无跨存储依赖的独立正式模型。从 `v1.1.x` 或更早版本保留旧手动自定义料理的用户必须先启动一次 `v1.2.0` 完成转换，`v1.3.0` 不支持直接跨版本恢复。自 `v1.2.0` 起不再读取旧 GUID 配置；旧名称只允许出现在上游来源说明中，不保留旧路径、旧类型或旧 API 别名。
- `References/` 只放本机编译 DLL，不提交仓库。
- 根目录 `toolchain.lock.json` 是 Linux、Windows、CI 共用的构建版本基线：Node `24.19.0`、Corepack
  `0.35.0`、pnpm `10.10.0`、.NET SDK `10.0.110`、Rust/Cargo `1.97.1`。标准选择文件和构建入口只投影
  这一份基线；版本不一致直接停止，不回退全局 pnpm、较新 SDK 或 stable channel。Mod 目标仍为
  `net6.0`；三项真实 Harmony/MonoMod smoke 只通过固定 .NET 6 容器运行。
- 当前游戏输入身份由仓库外 `new/analysis-manifest.json` 锁定。源码分析使用 Il2CppDumper metadata C#、
  离线复现的 BepInEx #783 / Il2CppInterop 1.5.3 wrapper、IDA 9/Hex-Rays 和实机日志四层闭环；旧资料在
  `backup/legacy-analysis-20260608/`，不参与业务 fallback。完整流程见 `docs/il2cpp-analysis-workflow.md`。
- Linux Steam 安装仍是 Windows x64 PE 游戏。Linux BepInEx 对它无效；运行时使用 Windows x64 #783 +
  Proton，离线 interop 生成不启动游戏、不写 Steam 目录。Cpp2IL 当前锁定版本的 `dll_il_recovery`
  实际只写 `ldnull; throw`，已从正式分析路径移除。
- IDA 导入只对唯一 Native 地址设置最终名称，全部托管别名保存在 `method_map.csv`；函数体输出以 RVA
  分片，Hex-Rays 失败时保留覆盖全部 chunks 的反汇编。全量导出每 1,000 个函数必须清理反编译缓存，
  避免内存线性增长。
- HUD 目标订单卡片覆盖层所用边框模板，其 BepInEx 783 组件枚举 wrapper 只用于严格计数和唯一 native pointer 集合；`RectTransform`、`CanvasRenderer`、`Image` 必须同时通过 typed native query 与 native class pointer 精确相等复核，源模板和 clone 再与枚举集合闭合。parent `LayoutGroup` 查询有意接受全部派生类型并统一拒绝，禁止以 wrapper `GetType()` 推断原生类别或增加视觉兼容路径。
- 推荐数据来自游戏运行时 `RuntimeDataCatalog`；`build-release.ps1` 和发布包只包含 Mod DLL 与伴随窗口程序。
- 用户安装和测试优先使用已验证的 BepInEx Bleeding Edge #783 Windows x64 IL2CPP 包：`BepInEx-Unity.IL2CPP-win-x64-6.0.0-be.783+c58c42d.zip`。#784 及之后构建当前不建议用于本项目，后续如需支持新版 BepInEx，必须重新实测并检查运行时日志。
- BepInEx 783 / Il2CppInterop 1.5.3 通过 Dobby 1.0.5 detour IL2CPP native method pointer。禁止 Harmony Hook `RunTimeStorage.*Out`、`*OutRange` 或 `ObjectOut`：实机 Windows 事件中的 `0x80000003 / GameAssembly.dll RVA 0x6642b6` 已与 `BeverageOut(0, false)` 的 short-Jcc trampoline 错跳精确闭合。历史 `RuntimeStorageSentinelDiagnostic` 及其 13 个全局出库 Hook 已删除；库存诊断只能放在受控调用方或既有业务日志中，不得恢复同类原生入口观察器。
- 独立伴随窗口默认通过 `127.0.0.1:32145` 读取运行态；该回环 listener 必须始终保留。`LocalApi.AllowLanConnections=true` 只会额外开启 LAN listener，供可信局域网设备连接；LAN 配置和 Token 重置只能由 A 设备本机回环客户端调用。所有正式 Tauri runtime 统一通过 Rust TCP command 访问 API，只有浏览器开发模式直接 fetch；Rust 代理的连接超时最长 5 秒，响应读取超时按前端命令要求最多允许 60 秒。除 `/health` 外，本地 API 使用 `X-Mystia-Steward-Companion-Token` 授权，远程伴随窗口需要手动输入 A 设备 endpoint 和 token，代理只接受 loopback/private/link-local IPv4 endpoint。API 只接受规范路径，不提供 `/` 或 `/api/*` 别名；只读查询使用 `GET`，所有文件、运行时、配置、控制权、诊断和更新副作用使用 `POST`。设备权威端点使用最多 64 KiB 的严格 UTF-8 JSON body，拒绝重复/无效 `Content-Length`、`Transfer-Encoding`、截断、尾随数据和未知字段；其他旧端点不得自行增加 body 兼容协议。`/updates/status` 会归并 updater 结果并可能写入或删除状态文件，因此也使用 `POST`。
- 伴随窗口控制端口固定为 `127.0.0.1:32146`，支持 `show`、`toggle`、`exit` 消息。Tauri 在初始化窗口前原子占有端口并移交预绑定 listener，绑定失败的并发实例只通知端口所有者后退出；Mod 热键先通知已有窗口，控制端口不可达时进入 single-flight launch，所有权保持到端口可连接或明确超时。
- 桌面伴随窗口使用官方 `tauri-plugin-window-state`，在 Tauri app config 目录的 `.window-state.json` 中保存普通窗口位置、大小和最大化状态。插件在最大化或最小化期间保留最近一次普通窗口边界，恢复位置前检查窗口是否仍与可用显示器相交；可见性、最小化、装饰和全屏不进入持久化状态，关闭到托盘或临时最小化不会让下次启动保持隐藏。
- 桌面主窗口在 Tauri 配置中初始隐藏，窗口状态插件先恢复普通边界和最大化状态，Rust setup 再显示并聚焦，避免启动时先显示默认位置再跳到保存位置。桌面最小宽度固定为 640 逻辑像素；核心内容在 640px 及以上保持至少双列。640-719px 使用紧凑窄桌面布局：Header 品牌区可以与连接工具条分行，但连接工具条内部的 endpoint、Token、连接和刷新保持单行；设置专用 SegmentedControl 按内容收缩且标签单行，不得强制全宽等分或任意断词。三项全局状态摘要和经营中六项摘要保持三列；一级导航按实际可见的五或六个顶级页签等分为单行且不保留空轨道，二级及更深层页签同样等分铺满单行。低于 640px 的移动窄屏才允许连接工具条内部换行、纵排状态摘要和各级页签横向滚动。全平台图标以 `apps/companion/src-tauri/icon-source.svg` 为唯一母版；母版根元素通过 `data-icon-background` 声明通用底色、通过 `data-android-background` 声明 Android adaptive 底色，并用 `icon-background` / `icon-foreground` 提供明确分层。`pnpm icons:generate` 从母版重建桌面 PNG、Windows tile、九层 256-first ICO、tray、固定 chunk 顺序的 ICNS、不透明 iOS 图标、Android legacy/adaptive 图标、APK 工程实际资源和 favicon；`pnpm icons:check` 对全部生成物做字节幂等、尺寸、alpha、安全区和容器结构校验。Android legacy 固定为 48/72/96/144/192，规避 Tauri CLI 2.11.2 的 hdpi 49px 生成错误；adaptive foreground 使用缩小后的前景层，除官方安全区外还需通过额外视觉留白校验，`icons/android` 与 `gen/android/app/src/main/res` 的图标必须同步。
- 伴随窗口 `设置` 页分为 `窗口 / 连接 / 推荐 / 实验性功能 / 更新 / 帮助`。`窗口` 负责背景透明度、文字透明度、90% 至 130% 字体大小、焦点切换行为、切换冷却时间、置顶、鼠标穿透锁定、主题、手柄导航和显示调试信息；`连接` 负责本机地址、LAN 状态、按默认网关和接口类型排序的结构化 LAN endpoint、LAN 监听地址、Token、可信局域网访问，以及伴随设备注册表、当前/主设备、在线状态、改名、主设备配置单向同步、显式主设备切换和离线非主设备移除，多地址必须逐项复制，不能静默使用字符串排序首项；`推荐` 负责经营中订单排序、稀客专注模式默认精简、缺失厨具硬过滤、任务料理置顶、收藏料理/收藏酒水置顶、推荐权重、预算处理、带库存显示和名称/库存排序的排除材料/酒水及同基础料理展示数量；其中专注模式默认值是设备本地偏好，其余推荐配置与全部实验性配置进入 schema 1 共享 profile。Mod 将注册表原子保存到 `BepInEx/config/MystiaStewardCompanion/companion-devices.json`，最多 32 台；第一个注册客户端只在空表中成为初始主设备，此后不自动转移。所有客户端展示主设备 active profile，非主设备共享控件只读；同步固定为主设备完整覆盖目标并由目标 ACK，不做合并。`实验性功能` 集中管理自动化总控、稀客/普客自动化和并发/重试参数，以及两类目标各自的游戏列表置顶、加料料理选项、厨具/桌位/订单高亮和高亮色；该分栏顶部使用唯一常驻风险提示条，简要说明自动化和加料料理选项会改变游戏运行时状态并存在风险，游戏界面辅助的十个功能开关名称不重复添加“（实验性）”后缀；`帮助` 渲染统一帮助 JSON 的目录树和详情。加料料理选项、桌位高亮与订单高亮默认关闭。只有当前主设备携带精确 authority revision 时才能取得自动化 lease、调用运行时动作或发布 UI target；主 profile/设备变化会推进 command epoch、撤销 lease 并清空旧 target，非主和迟到请求 fail-closed。设备文件损坏或未来 schema 时保留原文件并禁用 mutation/runtime writer。经营中自动化视图不再写偏好，只保留运行状态、订单步骤、重试、重置和人工确认。设置页的静态功能说明统一放入字段信息图标的只读说明浮层，不再作为常驻段落；鼠标悬停图标、键盘/手柄聚焦原控件或触屏点击图标都能读取，不为手柄增加逐项图标停靠点。连接、更新、运行时和平台限制等当前状态仍常显；浮层使用 Portal、响应式宽度与边缘翻转，不建立内部滚动容器，也不影响设置页布局。字体大小按客户端 localStorage 独立保存，默认 100%，通过单一 CSS 比例同步 Tailwind、Mantine、自定义控件和继承文本，不改变固定间距、图标、窗口几何或响应式断点。背景透明度通过 Tauri transparent window + CSS 背景 alpha 实现，旧 `windowOpacity` 会迁移为背景透明度；文字透明度单独影响普通文字、图标和辅助徽章内容，主操作按钮保持不透明；稀客专注模式的料理/酒水显示数量在专注模式浮层内调整。鼠标穿透通过 Tauri 原生窗口忽略鼠标事件实现，`F10` 切换，`F8`/`RS Click`/托盘显示会自动关闭穿透。
- 伴随窗口顶级导航固定为 `概览 / 推荐料理 / 经营中 / 扩展功能 / 设置`；`日志` 只在 `显示调试信息` 开启后显示。`推荐料理` 使用 `普客 / 稀客 / 自定义推荐料理 / 收藏管理` 二级页签；收藏管理同时显示料理与酒水收藏，默认料理分类，支持搜索、稀客分组、目录缺失标记和逐项精确取消，不承担自定义配方编辑或批量清空。`扩展功能` 使用 `任务列表 / 稀客邀请 / 修改`，`设置` 使用 `窗口 / 连接 / 推荐 / 实验性功能 / 更新 / 帮助`。任务列表与稀客邀请各有独立、按当前客户端 `localStorage` 持久化且严格默认关闭的模块总控；关闭时不读取对应列表、不轮询且不允许发起新邀请，升级时不读取旧键或自动开启。任务列表开关不关闭 Mod 侧共享的任务捕获或任务料理置顶等其他能力。任务列表合并 available 与 active tracked 项，使用 `全部 / 可接取 / 可完成 / 进行中 / 待确认` 受控页签，同一时间只显示一个列表；同 label 重叠时 tracked 优先，`全部` 按状态、中文标题和 label 稳定排序，页签计数保留零值，窄屏页签栏允许横向滚动。帮助内容来自 `apps/companion/src/data/help-content.json`，页面只做搜索、目录树和详情渲染；用户可见功能或排查流程变化时需要同步该 JSON。
- 稀客订单专注页顶部不重复显示模式标题和说明，只保留全宽右对齐的精简模式、料理/酒水数量和退出控制组。稀客页、经营中页和专注模式的生效自定义配方入口统一放在料理推荐标题的 action 区，紧凑可见文案保留完整 `aria-label` 和 tooltip；展开内容仍位于标题后、料理列表前。手柄确认展开时通过声明式确认焦点 key 进入详情滚动区，鼠标点击不抢焦点。
- 伴随窗口 UI 基础组件集中在 `apps/companion/src/components/ui/`，并通过 `apps/companion/src/components/ui-kit/` 对外提供统一导出。当前项目组件层以 Mantine 组件为交互基础，封装了按钮、输入、选择框、多选框、页签、开关、滑杆、树形目录、折叠面板，以及项目展示组件 `ListPanel`、`InfoLine`、`StatusCard`、`Metric`、`EmptyRow`、`EmptyState` 和选项组。视觉形态以企业控制台式扁平分组、直角窄边框、标题条和表格化行项目为准，保留项目既有配色；除开关、滚动条滑块等需要圆形几何的控件外，不再使用圆角。后续不要继续复制外部模板风格组件，也不要在业务页面手写第二套开关/滑杆/卡片样式。
- 伴随窗口根滚动区域固定预留纵向滚动条槽位，避免页面高度变化时滚动条挤占宽度造成内容横向跳动；窗口、下拉和日志滚动条使用主题色并跟随背景透明度。
- 焦点切换支持两种模式：隐藏伴随窗口再聚焦游戏，或保持伴随窗口悬浮并只聚焦游戏。保持悬浮依赖窗口置顶，独占全屏游戏可能覆盖置顶窗口，推荐窗口化或无边框窗口化。
- 伴随窗口退出跟随不只依赖本地 API `/health` 失联，还会监控启动参数中的 `--game-pid`。游戏窗口 X、游戏内退出按钮、或 Unity 退出阶段未及时发送 `exit` 控制消息时，都应由 PID 监控兜底关闭伴随窗口。
- `修改` 页通过 `/inventory/set` 和 `/inventory/bulk-set` 在 Unity 主线程写入当前运行时材料和酒水库存；材料和酒水列表可按名称或库存排序。页面只保留单项 `-10`、`+10`、`99` 和当前存档可编辑材料/酒水批量设为 `99` 快捷按钮，用户仍需在游戏内保存才能持久化。
- 库存写入只走 `RunTimeStorage` 四个 Range 原生入口并在写后精确读取数量；不得在原生异常时直写 `Ingredients` / `Beverages` 私有字典。库存、订单和稀客邀请的主线程命令按类型有界排队且每帧最多执行一个；排队超时会取消未开始命令，已开始命令等待确定结果，控制器销毁会唤醒所有等待者。Local API handler 同样有并发上限，停止服务时先拒绝新连接并关闭在途 socket。
- 伴随窗口 `日志` 页保留总日志 `BepInEx/config/MystiaStewardCompanion/aggregate-mod.log` 开关、总日志目录、文件上限、诊断包导出，以及仅限回环客户端使用的 BepInEx 控制台显示/隐藏按钮。总日志默认关闭，启用后捕获 BepInEx 全局日志源，并接收自动化、经营诊断和运行时固定数据诊断；每条记录标注时间、channel、来源和线程，单个文件 10 MB 后拆分为递增编号分片。默认保留 30 个文件，约 300 MB，超过上限时删除最旧分片；该上限不保护 BepInEx/Unity 共享 output log，后台 worker 不得无限异常重试刷共享日志，Mod 也不接管共享日志文件。订单相关自动化日志使用 `trace=R-0001` / `trace=N-0001` 标识单笔稀客/普客订单，经营中页显示同一“日志”标识；排查长时间或难复现问题时优先让用户开启总日志、复现后提供当前文件和相关分片。
- Mod 不修改全局 `BepInEx.cfg`，也不释放宿主控制台。默认启动自动显示关闭且不覆盖 BepInEx 全局选择；游戏电脑回环客户端可显式显示或隐藏当前进程窗口。隐藏只改变可见性，日志链保持活动；`SetConsoleUtf8` 只调整当前已创建控制台的编码。

- `目标订单高亮` 同时覆盖 HUD 和投掷送达面板。稀客按 exact `R-*` trace、活动 rare capture、desk 和 native pointer 绑定；普客按 exact `N-*` trace、raw order key、活动 normal capture、正 lifecycle、desk 和 native pointer 绑定。Throw 继续要求 exact panel、desk tuple、keyed logical unit、唯一 serialized selection listener 和双背景 XOR；旧 panel close 只有 pointer 与当前登记完全一致时才能清理。
- 所有高亮服务只创建和修改 Mod-owned 对象；Unity 对象的创建、脉冲和正常销毁只在主线程执行。经营 Destroyed、off-main 清理或池化 identity 漂移时只 abandon wrapper，避免触碰已失效或已重绑对象。名称、文本、path、固定 index、原生改色和备用视觉都不是允许的识别或恢复路径。精确 Hook、几何、ownership、禁止项和测试契约见 `mods/bepinex/README.dev.md`，并由 `tests/runtime-seat-highlight`、`tests/runtime-order-highlight` 与 `tests/runtime-throw-delivery-order-highlight` 三个 smoke 锁定。
- 普客与稀客运行时捕获都维护 `ChangeVersion`，但只有 `PushToOrder`、`SetManualControllerOrderInternal`、`RemoveFromOrder`、`EvaluateOrder`、`EvaulateManualOrder`、`CleanOrderInfo`、`RepellInternal` 七个精确生命周期 Hook 全部安装，并且当前经营 generation 从开始时已被完整覆盖，捕获才可用于业务；中途补齐 Hook 的当场继续 fail-closed，下一场才就绪。捕获绑定的 key 只接受非零 IL2CPP 原生对象指针，不得回退到 managed hash。稀客业务集合只使用就绪捕获，已就绪空缓存就是权威空集合，反射/HUD/controller 样本仅作诊断；活动稀客控制器仍可提供显示和预算。普客在捕获就绪后同样以精确捕获作为业务和执行权威，HUD 只补充不可执行可见行，单轮 HUD 空窗或读取错误不得过滤捕获，同 native key 必须去重。UI 控制器在版本变化后延迟 0.2 秒强制刷新经营数据；捕获版本、场景和诊断状态都未变化时复用已有经营上下文，并按较慢节奏重新校验。动作前用 `PeekOrders()` 严格复核同一 controller、native pointer 和请求强身份；一般动作不扫描 manager 回退。幽幽子三阶段和古明地恋 BOSS 仅在各自显式命名且额外门禁成立的专用路径中允许扫描当前 manager controller。Delivery 只接受未满足订单，Completion/NativeEvaluation 允许已送齐但尚未退休的订单。
- 本地 API 快照发布在 Unity 主线程节流到约 0.35 秒一次；快照内容签名是规范内容的固定 64 字符小写 SHA-256，不能把随订单和事件增长的规范原文带入 `knownSignature` 查询串。签名未变化时复用上一份缓存 JSON，不为了 `CapturedAtUtc` 或性能数字重复序列化；完整 `RuntimeDataCatalog` 不再随 `/snapshot` 周期性补发，`/snapshot` 只发布 `snapshotSignature`、`runtimeDataComplete`、`runtimeDataSource`、`runtimeDataStatus` 和 `runtimeDataSignature`，前端只在缓存为空或签名变化时后台读取 `/runtime-data`。`runtimeDataSignature` 对完整发布 JSON 计算 SHA-256，并与同一目录对象代际的一次序列化结果一起缓存，不能用集合数量或首尾条目近似。前端轮询 `/snapshot` 时带 `knownSignature`，后端内容未变化时只返回 `{ unchanged: true, snapshotSignature }`；前端遇到 unchanged 只能更新连接存活状态，不能 `setSnapshot` 或触发推荐/自动化派生，轮询调度也不能依赖 React 重新渲染续约，必须由独立 interval/loop 持续观察后续经营状态变化。前端必须让 `/snapshot` 成功返回后立即更新主快照和签名，不能等待 `/runtime-data` 完成，否则经营中页的特殊经营、普客订单和自动化会被运行时目录请求阻塞；`/runtime-data` 失败只影响推荐目录缓存。前端必须缓存最近一次完整运行时数据，但不要用 `/snapshot` 原始 JSON 文本相等来跳过快照状态更新，以免运行时目录恢复被遗漏；未完整占位只能保留到下一份更精确状态到达，不能锁存首次等待文本。总日志开启时，Local API 会记录 `/snapshot` 请求诊断，包含客户端、known/current 签名短值、full/unchanged、responseBytes、specialActive 和 normalOrders，用于区分前端未请求、连错 API 实例和快照被前端丢弃；聚合 `[snapshot]` 段还必须输出 `runtimeSceneReadiness/runtimeDataComplete/runtimeDataSource/runtimeDataStatus`。`RuntimeReflectionRecommendationStateProvider` 只在核心目录和 base+mapped identity 均完整后构造，并在完整静态目录 ID 闭包内逐项调用 `RunTimeStorage.HaveRecipe`、`GetIngredientCountById` 和 `GetBeverageCountById`；材料和酒水都保留精确 `-1` 为无限，零库存省略，低于 `-1` 令本轮失败，没有已解锁料理时不得发布空的可用料理集合。玩家等级、流行喜好/厌恶 Tag 和明星店开关继续用 `RunTimePlayerData` / `RunTimeDayScene` 轻量 getter 读取。运行时固定目录读取完成后缓存映射和静态目录快照，经营扫描和诊断只复用缓存，不在 `NightBusinessReflectionProvider.LoadContext()` 中重新构造目录。未完成目录由控制器唯一的约 5 秒时钟有界重试，目录对象自身不得再叠加第二套时钟。`performanceMs` 会记录 `refresh.business`、`refresh.runtime`、`snapshot.serialize`、`runtimeData.serialize`、`automation.collect`、`snapshot.publish` 等耗时，概览页和经营中页展示最高几项用于排查掉帧。经营扫描还会记录 `business.rare.*`、`business.normal.*` 和 `runtime.cookerSnapshot` 等子项；普客订单快照有短 TTL 缓存，避免一次快照发布链路内重复枚举 `OrderController`、HUD 和 `GuestsManager`。
- 运行时核心目录 ID 只来自 `DataBaseCore` 的 `IngredientsMapping`、`BeveragesMapping`、`FoodsMapping`、`RecipesMapping` 和 `IzakayasMapping` 五张精确 int/string 字典，完整验证后逐 ID 调对应 `Ref*`。所有条目先严格校验 CLR 键值类型、非空字符串来源、原始 ID 唯一性和容量；材料、酒水、料理、配方显式使用非负内容 ID 域，负数内部键在投影边界排除且不得进入对应 `Ref*`，排除后为空时 fail-closed。`IzakayasMapping` 显式保留完整 signed ID，signed 料理/酒水 Tag 字典也保持独立规则。Izakaya 投影先精确读取 `DaySceneMapLabel`，只跳过空标签占位；非空标签必须严格读取 `DaySceneMapName`，读取失败整轮 fail-closed，合法但不属于支持日间经营地点的条目才记录 skipped。确认支持地点后再读取该条目的严格顾客池，特殊经营或占位条目的合法空池与推荐无关。基础稀客数组只读声明的 raw fields；映射稀客只组合 `GetAllMappedGuests()` 与 `GetAllSpecialGuests()` 的 ID/StringId/source chain，不生成临时对象或调用计算型喜好/厌恶入口。核心目录与基础/映射 identity 使用独立完成状态和重试路径；普通地图/就绪变化复用已完成身份，只解除未完成读取的重试等待；进入非游戏场景清空存档运行态后必须独立重建 identity，不能被仍完整的核心目录短路。
- 本地 API 快照生产必须通过统一脏域发布入口：场景、运行时目录、稀客经营、普客订单、特殊经营和自动化变化只标记对应 dirty domain，由 `StewardOverlayController` 在 `Update()` 末尾统一节流、刷新和发布。不要在新增功能中直接散落调用快照发布；若需要立即反映场景切换或运行时 ready 变化，应使用强制 dirty 标记。`runtimeDataComplete/runtimeDataStatus` 使用 core+identity 组合门禁，即使 core JSON 已序列化，identity 未完成时也不得通知前端消费。总日志开启时可记录 `[snapshot]` 诊断，包含 dirty domain、发布/跳过结果、签名、运行时就绪和目录状态、普客/稀客订单数及特殊经营阶段，用于区分“后端未生产快照”“目录在何处失败”和“前端未消费快照”。
- 前端订单推荐 worker 和页面推荐 worker 会按 `RecommendationDataSet` 语义签名缓存完整运行时目录。签名未变化时，后续请求只传业务 payload 和数据签名，不再重复把完整运行时料理、食材、酒水、客人和规则目录结构化克隆进 worker；签名变化、worker 重建或首次请求才重新发送完整数据集。伴随窗口收到完整 `RuntimeDataCatalog` 后只在连接 hook 的独立缓存中保留一份，并从主 `snapshot` state 剥离完整目录，避免每轮快照和非当前页面 props 链路继续持有大对象。顶层工作台只挂载当前 active tab 的重型页面内容，页面推荐 worker 在 payload 为空时必须 terminate 并清空数据签名。该协议是自动化开启后降低 Mod 窗口内存和 WebView 卡顿的关键路径，新增 worker 推荐入口时要复用同一模式。
- 前端轮询完整快照时，只有在快照已经写入 React state，且所需 `/runtime-data` 已成功缓存或无需刷新时，才能推进 `knownSignature`。运行时目录读取失败不能阻断 `snapshot` 应用，也不能提前把 `snapshotSignature` 记录为已消费；否则后端会持续返回 `unchanged`，经营中页会保持空状态，直到页签切换等偶然重算才恢复。
- 普客订单被动快照缓存约 1 秒。七 Hook 与当前经营 generation 就绪后进入 `normalOrderMode=authoritativeCapture`：`NormalOrderRuntimeCapture` 的精确捕获是业务和执行权威，`OrderController` / HUD 只追加没有捕获绑定的不可执行可见行；同一非零 native `orderKey` 必须去重为捕获订单。单轮 HUD 空窗或读取错误不得过滤、隐藏或退休捕获，桌位、料理、酒水和同桌新订单也不得作为重绑依据。捕获未完整就绪时进入 `normalOrderMode=visibleFailClosed`，仅显示 HUD 行并禁止自动化，不扫描 `GuestsManager`、队列或 `NightSceneDirector.controlledGuest` 建立业务订单。`ChangeVersion` 变化后只刷新 `NormalBusinessContext`，不得重扫完整稀客上下文。只有存在活动 `AutomationCookingJob` 时才在 `Update()` 热路径轮询料理 job；Closing 边界同步发布取消终态并清理。
- 普客订单快照读取门禁是当前处于 `Work` 场景且精确经营生命周期为 Active，而不是 `NightBusinessContext` 已经稳定。怪诞料理等特殊经营中，HUD 普客订单可能早于稀客经营上下文稳定出现；只要 lifecycle Active 且 `OrderController`/HUD 可读，就应允许 `NormalBusinessContext` 读取并进入本地 API 快照。Closing 开始后不得再读取，并同步清空普客快照和捕获缓存。
- 夜间经营生命周期由 `RuntimeNightBusinessLifecycle` 单独拥有。只有 `WorkSceneSustainedPannel.OnPannelPostOpen/0`、`GuestsManager.CloseIzakayaDelayed/2`、`CloseIzakayaAndLeaveChallengeMode/2`、`NightScene.SceneManager.ToResult/0` 和 `OnInstanceDestroyed/0` 五个 Hook 全部成功才允许 Active，任一成员缺失都 fail-closed。`TryCloseIzakaya` 只是倒计时结束后的停止接客/清桌信号；游戏仍允许在座顾客继续点单，Mod 必须保持同一 Active generation 及订单捕获、推荐、自动化、料理 job 和 UI target。最后一桌离席后创建 `CloseIzakayaDelayed`，或特殊经营退出/结果转换时，才进入 Closing 并同步停止运行时访问、失效 target、清理稀客/普客捕获、特殊经营上下文、料理 generation 和自动料理 job；实例销毁进入 Destroyed。Closing 不能重新 Active，下一场只能在 Destroyed 后开启新 generation。场景名只用于辅助读取门禁，不再拥有第二套清理时序。
- 场景切换后 Mod 不做固定秒数等待。`DaySceneSustainedPannel.OnPannelPostOpen` 是独立最终门闩，不是 ready 信号；manager/Action 链可在面板前后捕获。普通读档必须依次匹配同一 manager 的 `OnFirstEnterDaySceneFinish`、`RunTimeScheduler.OnEnterDayScene` 外层 Action、该 Action 的 `DefaultOnFinish`、`m_HasTriggerOnEnterDaySceneEvent=false` 时的 `OnEnterDaySceneMap` 最终 Action及其 `DefaultOnFinish` 返回，且面板已经打开，才能进入 ready。手动经营返回必须在入口前明确读到 `IsManualWorkSceneSession`；每次读取还要验证同一原生 manager、非换图、有效地图，并要求 `RunTimeScheduler.isExecuting`、`SceneDirector.IsInEvent`、manager 的 `isExecutingScheduledActions` 和 `UniversalGameManager.IsSwitchScene` 全部为 false，任一证据缺失都 fail-closed。夜间经营准备仍以 `IzakayaConfigPannel.OnPanelOpen` / `GoToSpecific` 为 ready 信号。IL2CPP 字典为空时前后确认 Count 仍为 0，并在解析具体 Enumerator 前返回；非空字典、列表和数组才按精确泛参及 Enumerator/indexer 形态读取。
- 经营中页使用页内 `推荐` / `自动化` / `诊断` 视图分区；自动化视图集中稀客/普客状态、活动 `AutomationCookingJob` 和订单详情，诊断视图集中原始当前稀客/点单和预计厨具占用。七 Hook 与当前经营 generation 就绪后，普客执行控制器和业务订单来自 `NormalOrderRuntimeCapture` 的精确绑定；`OrderController.GetShowInUIOrders()` 与 HUD 只追加没有捕获绑定的不可执行可见行，单轮读取空窗或错误不能过滤捕获，同一非零 native `orderKey` 必须去重。不得扫描当前控制器补造绑定，也不得按桌号/料理/酒水槽位合并。普客自动化需要总开关和普客子开关同时开启，按首次出现顺序和设置并发数执行，订单变化用短防抖复查。活动 job、送达中或评价中的订单不重复占用开锅名额；job 的 waiting/interrupted/terminal 状态直接来自快照，不再按前端经过时长猜测。每笔普客订单独立记录送酒、开锅、送料理、评价和暂停状态；一般普客料理正常完成后直接送达，酒水在送达提交成功后扣库存，只有 `get_IsFullfilled()` 为真才评价。后续 fresh snapshot 中的 `HasEvaluated` 或订单消失只作为前端观察到的外部收敛信号；Mod 自己发起一次原生评价后，只接受该调用期间同步发布且精确命中同 lifecycle 的 `Evaluated` terminal receipt 证明本次提交成功。显示在普客区域的血池地狱 BOSS 订单仍使用挑战专用目标；Mod 自动推荐、送酒、开锅并复核成品，严格双 Tag 方案优先，仅精确 BOSS `NormalOrder` 可在严格无解且全部硬门禁成立时使用受控推进，再按料理送达与订单完成双开关选择专用无界面结算或人工交接。

- 血池地狱特殊目标 revision 是独立于规范 signature 的动作代际。它必须从同锁运行时快照原样进入前端状态、Worker、回滚目标、本地 API、后端 target 和 cooking job；血池目标只接受正 revision，其他策略使用 `0`。受控推进许可不改变该策略 identity，但必须进入 execution target 和 cooking job identity，严格与受控动作不得复用。`A -> B -> A` 后旧 A 动作不得命中新 A。酒水事务固定为 `BeverageOut -> fresh order -> final setter -> fresh order -> 未 fulfilled 时恢复耐心 -> fresh order -> range 调整 -> fresh order -> consume/status/desk`；每个原生回调后都复核当前 generation/policy/revision 并重新取得同一订单，最后才创建记账上下文。任一不可逆边界后的失败进入安全栅栏，禁止重放。
- 血池地狱专用 lookup 不信任 capture 中旧的 `ManualOrder` 值；每次都从当前 order wrapper 精确读取路由，并在当前为手动控制订单时按同一 order/controller 找回原始回调。酒水初始状态和四次 fresh reacquire 都把 `ServedBeverageInAir` 作为零副作用/不确定边界，最终料理也同时门禁 food/beverage in-air；非手动订单只送达酒水时恢复一次原生耐心并再次重取订单。取消端点要求精确 `target=commands|rare|normal|all`：仅关闭送酒使用 `commands`，推进全局命令 epoch 但保留全部 job 与 automation control lease；关闭稀客/普客处理组、料理直送或完成开关时使用对应 job 目标，只清理该订单组尚未进入不可逆阶段的 job 并保留 automation control lease；总控关闭使用 `all` 清理全部并释放 automation control lease。前端在 ACK 前持久化 endpoint/target，ACK 后记录 Mod session/command epoch 并等待快照 applied epoch，避免锁存旧阶段意图或丢失取消屏障。

- 教学经营不执行自动化。Mod 只在 Unity 主线程精确读取 `NightSceneDirector.Instance.IsInTutorial`；当前 Active generation 一旦确认教学，即锁存至本场结束。状态不可读时 fail-closed，不使用场景、日期、对话、订单或挑战标志兼容猜测。快照的 `nightBusinessAutomationAllowed`、`nightBusinessAutomationBlockReason` 和 `runtimeNightBusinessAutomationStatus` 供前端暂停调度和显示原因；从 true 切换为 false 时必须推进 request epoch 并隔离迟到响应，但不清空用户偏好或订单状态。后端动作入口和 cooking job 仍按同一门禁复核，不信任前端。
- 总日志的活动路径若被外部删除或移走，下一条日志在同一服务锁内释放失路径旧句柄、重建原路径、写入恢复边界并重置当前文件的重复摘要/诊断签名；不启动 watcher 或后台磁盘轮询。
- 成功 `PushToOrder` / `SetManualControllerOrderInternal` 在 exact `HasEvaluated=false + PeekOrders()` 栈顶门禁后，为 generation + concrete kind + order/controller pointer 分配进程单调 `OrderLifecycleSequence`；五个评价/移除/清理/驱逐 Hook 只发布调用前生命周期的 wrapper-free terminal receipt。Clear 清状态但不回退 watermark；同 native tuple 复用、旧 postfix 和延迟旧 HTTP 请求都由 sequence 隔离。普客/稀客快照、runtime event、前端 state key 与三个订单自动化端点都携带正序列，任何游戏副作用前要求 request、fresh capture、active store 完全一致。普客 authoritative capture 按 lifecycle 分组并排除同 raw key 的 unbound HUD 行，避免 pointer 复用时用 `Any` 把旧 served/evaluated 状态合入新订单；任一已绑定 observer 检测到同 lifecycle raw Tag 冲突时则移除 capture 并使该 lifecycle 失效，绝不把漂移值发布成替代身份。
- `AutomationCookingJob` 的 cooker controller lease 与订单评价回执相互独立。只有 `holdsControllerReservation=true` 才算持有 cooker controller lease 并形成 Mod 厨具占用；人工交接、严格 cleanup 完成或 cleanup 明确终止后单调释放，随后 job 即使继续等待精确评价也不再预约旧 controller。料理送达 cleanup 清除 IL2CPP 成品 wrapper，job 通过同 lifecycle terminal receipt 或 fresh exact order 收口评价；自身评价正常返回/异常后都必须读到 `Evaluated` receipt，否则进入 commit-uncertain ACK 且不重放。暂时不可读的 closeout 最多 12 次、至少 5 秒且最多 20 秒有效运行时间，门禁暂停不计时；耗尽转同 lifecycle 栅栏。离开 Active 时按 business generation 清栅栏，调用栈内晚到旧结果降为有界 `business-lifecycle-ended` 事件，不能回填不可 ACK 栅栏。快照中的 `transactionStage`、`holdsControllerReservation` / `controllerLeaseReleaseReason`、`orderRuntimeKind` / `orderPointer` / `orderControllerPointer` / `orderLifecycleSequence` 和 `foodDeliveryEvaluationState` / `foodDeliveryEvaluationAttempts` / `foodDeliveryEvaluationEffectiveSeconds` 是唯一诊断来源；活动 job 或评价中订单本身不等于厨具被占用。


## 推荐排序口径

- 经营中/稀客推荐排序可由伴随窗口 `设置` 页的任务料理、收藏料理、收藏酒水置顶开关、自定义推荐料理单条置顶和推荐权重共同控制。固定顺序是硬过滤、任务料理置顶、自定义推荐料理置顶、收藏料理/酒水置顶，最后进入普通权重排序；默认均衡预设综合稀客偏好、厌恶风险、加料数量、资源压力、成本、利润、酒水库存和当前厨具可做等目标。
- 当前推荐权重项包含料理偏好命中、酒水偏好命中、减少厌恶标签、减少加料数量、少用低库存食材、降低食材成本、提高预计利润、优先酒水库存和当前厨具可做。资源压力优先惩罚低库存材料，并对额外加料加权；不要再使用“总成本越高越靠前”作为收益判断。收藏料理和收藏酒水不是权重项，只能通过对应置顶开关控制。
- 稀客和经营中主推荐使用统一料理/酒水候选池；满足当前点单料理 Tag / 酒水 Tag 的结果优先，不满足点单但命中稀客喜好的结果直接进入同一列表并标注为“偏好备选”。完整候选先构造并排序执行计划，`executionPlans[0]` 是唯一主执行计划，其料理与酒水必须投影为页面首项；经营中页和稀客订单专注模式再按用户设置截取其余展示行，不再维护独立喜好备选数组。料理推荐优先 3 分以上候选，但低于 3 分且满足点单的料理仍要作为兜底显示。
- `blockedDiagnostic` 只在最终 `executionPlans` 为空时生成，并复用正式候选、特殊经营过滤和计划构造入口。它按料理目录/点单 Tag/解锁/基础材料/厨具/特殊规则与厌恶安全、酒水库存/排除/Tag、预算、特殊评价和最终计划记录首个清零阶段，附带缺失材料、所需/已摆厨具、剩余预算与最低组合价。该诊断只解释结果，不参与过滤、排序、业务缓存身份或目标选择；自动化总日志用稳定状态签名在当前会话内维护最多 64 条有界去重集合，稀客和普客分开，切换自动化会话时清空，避免同一状态重复刷日志。
- `排除缺失厨具` 开启且取得完整厨具快照时，统一推荐列表会隐藏当前场景物理未摆放对应厨具的料理。complete 且确认存在事件锁定控制器时，不读取锁定实体的旧能力，而是只保留存活非锁定控制器证明的类型；其他类型作为事件期间硬门禁，不受“排除缺失厨具”开关影响。空位与锁定只闭合 controller 总数，不进入已摆厨具或容量；unavailable 轮次不从安全保留的 locked 计数推断或调度。自动化容量使用更严格的 `automationAvailable + controllerIndex + controllerIdentity + gridPosition`。
- 夜间 live 厨具控制器的唯一来源是 `CookSystemManager.get_AllCookers` 的精确 `Dictionary<Vector3Int,CookController>`；开锅、快照和高亮都通过 `RuntimeConcreteCollectionReader.TryReadDictionary` 共用该来源。完整厨具能力只接受 `AllAvailableCookerType` 的精确泛型 enumerable 读取；Empty-only 只能与精确 `IsEmptyDesk` 状态共同表示空位。已有厨具暂时忙碌、被自动化预约或被挑战机制禁用时属于可重试等待，不等于集合读取为空。
- 运行时稀客目录在前端分为普通地点可选的 `rareCustomers` 与不要求地点的 `rareCustomerProfiles`。后者只提供特殊经营评价需要的 canonical ID 与喜好/厌恶 Tag；映射 ID、名称和静态 Tag 不能作为回退。两份投影都进入推荐数据签名，特殊 NormalOrder 目标缓存也绑定该签名。
- 寻找瑞灵踪迹与月都试炼 1 / 2 / 3 统一由 `mizuchi-challenges` / `MizuchiOrderModule` 主动适配，并共用精确评价 callback/closure 与 order/controller guest 身份链。基础场景使用独立 `mizuchi-story-*` wire role、`targetIngredientId=5002`、基础标志和随机活动 control `0..2`；三场试炼保留 `mizuchi-trial-*` role、`targetIngredientId=5005`、非基础标志和固定活动 control `1/0/2`。两组 role 和目标材料不得互认。角色分为 possessed、ordinary、unverified；附身订单固定优先，在满足原始料理/酒水 Tag 的同时预置本场唯一必需额外材料，普通订单禁止本场目标材料，unverified 无计划。运行时稀客 ID 是非负内容域，莉格露合法 ID 为 `0`；controlled 只接受 `-1` 或非负 ID。实机交付的 `GuestGroupController` 基类 wrapper 必须精确下转型为同 native pointer 的 `SpecialGuestsController`，不得直接读取派生成员或提供转换兜底。
- 四场闭包只接受两种业务状态：精确 `controlled=-1/control=None(3)` 是开场及捕获后的无目标保护期，全部合法活动订单为 ordinary；`controlled>=0` 时，基础场景要求 control 属于 `0..2`，试炼要求等于本场固定值，再按 guest ID 区分 possessed/ordinary。混合组合仍 unverified，不缓存上一目标、不接受任意 `None`。推荐、自动化和 UI 目标共享 `executionPlans[0]`；请求、扣料、`SetCook`、送达和评价边界 fresh 验证 role/lifecycle/closure，并要求实际 `Food.Modifier` 与 extras 全等。只送达酒水时先按 `IsFullfilled=false` 正常等待，fulfilled 后才读取 `ServFood` 并执行 Mizuchi preflight。首次不可逆操作前漂移取消动作；扣料后使用 `cooking-start-unowned`，送达或评价阶段使用 `mizuchi-contract-mismatch` 人工 ACK。旧 passive 基础规则、trial-only 文件/类型和旧安全 code 已删除，不保留兼容路径。
- 月都试炼 1 / 2 / 3 已由用户逐场确认推荐与自动化正常；试炼 1 实机还闭环了基类 wrapper、ID `0`、附身/普通订单、辣椒水 Modifier、捕获推进和 `(-1,None)` 保护期。2026-08-08 的寻找瑞灵踪迹旧构建实机尝试确认 challenge 与订单形态，但被动实现没有加入噗噗呦果，Unity 日志中的果实数持续为 `5`；主动实现现已接入。基础场景仍需验证至少一笔 possessed、一笔 ordinary、一次无目标保护期及捕获推进/最终完成，并回传日志和诊断包。
- 稀客收藏保存在 `BepInEx/config/MystiaStewardCompanion/favorites.json`，按 `customerId + foodTag` 收藏料理方案（含加料 ID），按 `customerId + beverageTag` 收藏酒水；收藏管理页从同一响应派生料理/酒水计数、搜索和稀客分组，写操作按收藏 ID 串行且只移除精确条目。运行时目录缺失不能过滤收藏，必须保留存储名称或显示内容 ID，允许用户清理。自定义推荐料理保存在 `BepInEx/config/MystiaStewardCompanion/custom-recipes.json`，按 `customerId + foodTag/null + foodId + extraIngredientIds` 生效，其中 `foodTag=null` 表示该稀客全部点单料理 Tag；顶层 `enabled` 是整个功能的门禁，关闭不改写单条状态。管理页可按稀客或基础料理派生分组，页面/分组/单条 flags 更新使用同一原子端点，推荐优先级只在同一稀客内移动。`v1.3.0` 中两个存储不互相引用，Local API 启动和 CRUD 不执行跨文件迁移；需要旧手动方案的用户必须先用 `v1.2.0` 完成转换。收藏料理置顶、收藏酒水置顶、自定义推荐置顶和自动化收藏限定都不绕过解锁、库存、预算、排除项和缺失厨具过滤。
- 经营中稀客推荐会根据当前稀客资金构造预算上下文。预算策略支持阻止超预算、仅提示和忽略预算；订单级 `isFreeOrder=true` 时不应用付款预算阻止，非免费订单继续按当前预算策略判断。排除材料会同时过滤基础配方和加料，排除酒水只过滤酒水候选。排除项下拉的库存显示来自 `RuntimeSets`，排序方式只影响设置页选项展示，不进入推荐缓存签名。预算、免费订单状态、排除项、缺失厨具和同基础料理展示数量都必须进入推荐缓存签名，避免设置变化后继续显示旧结果。
- `同基础料理显示` 默认值为 1。同一基础料理存在多个加料变体时，稀客页和经营中页只展示主计划之外当前排序最靠前的指定数量；主计划料理始终保留在首项。收藏匹配仍按基础料理和加料精确匹配；自动化收藏限定只有在总开关、对应阶段和订单自动化权限均开启时参与主计划归一化，并且必须在执行计划上限截断前处理。自动化开始时只锁定主计划，不得依赖裁剪后的 UI 行或扫描后续计划。
- 经营中订单显示顺序默认是首次出现时间升序；切换为稀客分组时，同组内仍按首次出现时间升序。新订单不应在点单顺序模式下插到已有订单前面；自动化和置顶目标必须使用页面同一排序结果。
- 推荐行需要显示库存数量；料理行需要显示厨具、基础配方和加料，并对这些定位信息做高亮。
