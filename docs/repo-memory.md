# Repo Memory

## 当前项目定位

仓库项目名统一为 `mystia-steward-companion`，定位为《东方夜雀食堂》BepInEx IL2CPP Mod 与 Tauri 伴随窗口。桌面端是 A 设备本机主入口，Android 端只作为 B 设备通过 LAN 连接的移动伴随窗口。

## 关键目录

- `mods/bepinex/`：插件源码、本地 API、运行时读取、构建脚本和 Mod 文档。
- `apps/companion/src/`：伴随窗口 React 工作台、推荐算法、tag 规则、类型和结构化数据。
- `apps/companion/src-tauri/`：Tauri 伴随窗口壳，桌面能力与 Android 移动端边界在这里隔离。

## 开发事实

- Mod 不编译引用额外的游戏业务 DLL，运行时通过反射读取游戏已加载的 IL2CPP interop 类型。
- 用户可见项目名、安装目录和发布产物使用 `mystia-steward-companion`。`v1.2.x` 仅暂时保留 Local API 启动阶段执行的 `favorites.source=manual` 转自定义料理一次性数据迁移，计划在 `v1.3.0` 删除。自 `v1.2.0` 起不再读取旧 GUID 配置；除该数据迁移外，旧名称只允许出现在上游来源说明中，不保留旧路径、旧类型或旧 API 别名。
- `References/` 只放本机编译 DLL，不提交仓库。
- 推荐数据来自游戏运行时 `RuntimeDataCatalog`；`build-release.ps1` 和发布包只包含 Mod DLL 与伴随窗口程序。
- 用户安装和测试优先使用已验证的 BepInEx Bleeding Edge #783 Windows x64 IL2CPP 包：`BepInEx-Unity.IL2CPP-win-x64-6.0.0-be.783+c58c42d.zip`。#784 及之后构建当前不建议用于本项目，后续如需支持新版 BepInEx，必须重新实测并检查运行时日志。
- 独立伴随窗口默认通过 `127.0.0.1:32145` 读取运行态；该回环 listener 必须始终保留。`LocalApi.AllowLanConnections=true` 只会额外开启 LAN listener，供可信局域网设备连接；LAN 配置和 Token 重置只能由 A 设备本机回环客户端调用。所有正式 Tauri runtime 统一通过 Rust TCP command 访问 API，只有浏览器开发模式直接 fetch；Rust 代理的连接超时最长 5 秒，响应读取超时按前端命令要求最多允许 60 秒。除 `/health` 外，本地 API 使用 `X-Mystia-Steward-Companion-Token` 授权，远程伴随窗口需要手动输入 A 设备 endpoint 和 token，代理只接受 loopback/private/link-local IPv4 endpoint。API 只接受规范路径，不提供 `/` 或 `/api/*` 别名；只读查询使用 `GET`，所有文件、运行时、配置、控制权、诊断和更新副作用使用 `POST`，现阶段写操作参数仍可使用 query。`/updates/status` 会归并 updater 结果并可能写入或删除状态文件，因此也使用 `POST`。
- 伴随窗口控制端口固定为 `127.0.0.1:32146`，支持 `show`、`toggle`、`exit` 消息。Tauri 在初始化窗口前原子占有端口并移交预绑定 listener，绑定失败的并发实例只通知端口所有者后退出；Mod 热键先通知已有窗口，控制端口不可达时进入 single-flight launch，所有权保持到端口可连接或明确超时。
- 桌面伴随窗口使用官方 `tauri-plugin-window-state`，在 Tauri app config 目录的 `.window-state.json` 中保存普通窗口位置、大小和最大化状态。插件在最大化或最小化期间保留最近一次普通窗口边界，恢复位置前检查窗口是否仍与可用显示器相交；可见性、最小化、装饰和全屏不进入持久化状态，关闭到托盘或临时最小化不会让下次启动保持隐藏。
- 桌面主窗口在 Tauri 配置中初始隐藏，窗口状态插件先恢复普通边界和最大化状态，Rust setup 再显示并聚焦，避免启动时先显示默认位置再跳到保存位置。桌面最小宽度固定为 640 逻辑像素；核心内容在 640px 及以上保持至少双列。640-719px 的窄桌面只让 Header 连接工具条、页面工具条和基础字号进入紧凑形态，三项状态摘要保持三列，一级导航使用五列两行完整显示；低于 640px 的移动窄屏才使用纵排状态摘要和横向滚动一级导航。全平台图标以 `apps/companion/src-tauri/icon-source.svg` 为唯一母版；母版根元素通过 `data-icon-background` 声明通用底色、通过 `data-android-background` 声明 Android adaptive 底色，并用 `icon-background` / `icon-foreground` 提供明确分层。`pnpm icons:generate` 从母版重建桌面 PNG、Windows tile、九层 256-first ICO、tray、固定 chunk 顺序的 ICNS、不透明 iOS 图标、Android legacy/adaptive 图标、APK 工程实际资源和 favicon；`pnpm icons:check` 对全部生成物做字节幂等、尺寸、alpha、安全区和容器结构校验。Android legacy 固定为 48/72/96/144/192，规避 Tauri CLI 2.11.2 的 hdpi 49px 生成错误；adaptive foreground 使用缩小后的前景层，除官方安全区外还需通过额外视觉留白校验，`icons/android` 与 `gen/android/app/src/main/res` 的图标必须同步。
- 伴随窗口 `设置` 页分为 `窗口 / 连接 / 推荐 / 自动化 / 更新`。`窗口` 负责背景透明度、文字透明度、90% 至 130% 字体大小、焦点切换行为、切换冷却时间、置顶、鼠标穿透锁定、主题、手柄导航和显示调试信息；`连接` 负责本机地址、LAN 状态、按默认网关和接口类型排序的结构化 LAN endpoint、LAN 监听地址、Token 和可信局域网访问，多地址必须逐项复制，不能静默使用字符串排序首项；`推荐` 负责经营中订单排序、稀客专注模式默认精简、缺失厨具硬过滤、任务料理/收藏料理/收藏酒水置顶、推荐权重、预算处理、带库存显示和名称/库存排序的排除材料/酒水、同基础料理展示数量、实验性游戏界面置顶和目标厨具高亮；`自动化` 负责实验性自动化总开关和参数。字体大小按客户端 localStorage 独立保存，默认 100%，通过单一 CSS 比例同步 Tailwind、Mantine、自定义控件和继承文本，不改变固定间距、图标、窗口几何或响应式断点。背景透明度通过 Tauri transparent window + CSS 背景 alpha 实现，旧 `windowOpacity` 会迁移为背景透明度；文字透明度单独影响普通文字、图标和辅助徽章内容，主操作按钮保持不透明；稀客专注模式的料理/酒水显示数量在专注模式浮层内调整。鼠标穿透通过 Tauri 原生窗口忽略鼠标事件实现，`F10` 切换，`F8`/`RS Click`/托盘显示会自动关闭穿透。
- 伴随窗口固定包含 `概览`、`普客`、`稀客`、`自定义推荐料理`、`经营中`、`任务`、`修改`、`帮助`、`设置` 页签；`日志` 页签只在 `显示调试信息` 开启后显示。帮助页内容来自 `apps/companion/src/data/help-content.json`，页面只做搜索、目录树和详情渲染；用户可见功能或排查流程变化时需要同步该 JSON。
- 伴随窗口 UI 基础组件集中在 `apps/companion/src/components/ui/`，并通过 `apps/companion/src/components/ui-kit/` 对外提供统一导出。当前项目组件层以 Mantine 组件为交互基础，封装了按钮、输入、选择框、多选框、页签、开关、滑杆、树形目录、折叠面板，以及项目展示组件 `ListPanel`、`InfoLine`、`StatusCard`、`Metric`、`EmptyRow`、`EmptyState` 和选项组。视觉形态以企业控制台式扁平分组、直角窄边框、标题条和表格化行项目为准，保留项目既有配色；除开关、滚动条滑块等需要圆形几何的控件外，不再使用圆角。后续不要继续复制外部模板风格组件，也不要在业务页面手写第二套开关/滑杆/卡片样式。
- 伴随窗口根滚动区域固定预留纵向滚动条槽位，避免页面高度变化时滚动条挤占宽度造成内容横向跳动；窗口、下拉和日志滚动条使用主题色并跟随背景透明度。
- 焦点切换支持两种模式：隐藏伴随窗口再聚焦游戏，或保持伴随窗口悬浮并只聚焦游戏。保持悬浮依赖窗口置顶，独占全屏游戏可能覆盖置顶窗口，推荐窗口化或无边框窗口化。
- 伴随窗口退出跟随不只依赖本地 API `/health` 失联，还会监控启动参数中的 `--game-pid`。游戏窗口 X、游戏内退出按钮、或 Unity 退出阶段未及时发送 `exit` 控制消息时，都应由 PID 监控兜底关闭伴随窗口。
- `修改` 页通过 `/inventory/set` 和 `/inventory/bulk-set` 在 Unity 主线程写入当前运行时材料和酒水库存；材料和酒水列表可按名称或库存排序。页面只保留单项 `-10`、`+10`、`99` 和当前存档可编辑材料/酒水批量设为 `99` 快捷按钮，用户仍需在游戏内保存才能持久化。
- 库存写入只走 `RunTimeStorage` 四个 Range 原生入口并在写后精确读取数量；不得在原生异常时直写 `Ingredients` / `Beverages` 私有字典。库存、订单和稀客邀请的主线程命令按类型有界排队且每帧最多执行一个；排队超时会取消未开始命令，已开始命令等待确定结果，控制器销毁会唤醒所有等待者。Local API handler 同样有并发上限，停止服务时先拒绝新连接并关闭在途 socket。
- 伴随窗口 `日志` 页只保留总日志 `BepInEx/config/MystiaStewardCompanion/aggregate-mod.log` 开关、总日志目录、文件上限和诊断包导出。总日志默认关闭，启用后捕获 BepInEx 全局日志源，并接收自动化、经营诊断和运行时固定数据诊断；每条记录标注时间、channel、来源和线程，单个文件 10 MB 后拆分为递增编号分片。默认保留 30 个文件，约 300 MB，超过上限时删除最旧分片；该上限不保护 BepInEx/Unity 共享 output log，后台 worker 不得无限异常重试刷共享日志，Mod 也不接管共享日志文件。订单相关自动化日志使用 `trace=R-0001` / `trace=N-0001` 标识单笔稀客/普客订单，经营中页显示同一“日志”标识；排查长时间或难复现问题时优先让用户开启总日志、复现后提供当前文件和相关分片。
- Mod 不修改全局 `BepInEx.cfg`，也不主动隐藏宿主控制台；控制台是否启用由 BepInEx/用户配置决定。`SetConsoleUtf8` 只在用户启用时调整当前控制台编码。
- 自动更新检查、下载和安装由单操作门串行；`UpdateService` 在 Local API 生命周期内运行一个可取消调度器，成功按配置间隔续检，失败按 15m/30m/1h/2h/4h/6h 退避。关闭 Local API 会先阻止新操作，再通过统一生命周期令牌取消自动/手动检查和下载，等待 handler、活动操作和调度器退出；取消检查恢复原稳定状态并立即到期，不保留虚假 `checking`。服务启动时把强制退出留下的 `checking/downloading` 恢复为当前元数据对应的稳定状态并立即安排检查，同时只清理下载一级目录内符合 `.<semantic-version>.<guid>.tmp` 的残留目录。状态明确区分最近尝试、最近成功、下次检查和连续失败数，不再使用混合语义的 `checkedAtUtc`。工作台级 `useUpdateManager` 是唯一前端控制器，活动状态 2 秒、稳定状态 60 秒读取主机状态，状态端点连续失败按 2s/5s/15s/60s 退避；状态请求和用户动作分开管理，断连或连接身份变化会清理动作并隔离迟到响应。发现新版后显示非模态提示，可直达更新页或按 endpoint + tag 延后 24 小时。manifest 严格校验 schema 1、版本/tag/channel、包名、SHA256 和长度，包体流式写盘。安装只使用 staged 包内已校验的 updater，且 staged 版本必须高于当前插件版本，旧暂存包只显示为不可安装，不得触发降级。读取更新状态时会归并独立 updater 留下的结果并维护状态文件，因此对应本地 API 不是只读 GET。发布页通过 capability 限定的 Tauri opener 打开；该更新只服务游戏主机 Mod 主包，远程独立 Windows 窗口和 Android APK 不自更新。
- 游戏内 IMGUI 面板已移除；Mod 在游戏侧只保留后台控制器、本地 API、运行时读取、自动化和伴随窗口唤起。
- 仓库不使用 GitHub Actions 自动构建 Release；`.github/workflows/ci.yml` 只保留手动前端检查。版本发布采用 Windows 本机构建后由 GitHub CLI 上传。自动更新发布只支持稳定版 `X.Y.Z` 和预览版 `X.Y.Z-preview.N`；预览版必须是 GitHub Prerelease，用于 `dev` 上测试 `preview.1 -> preview.2 -> stable` 更新链路，稳定版再合并 `main` 发布普通 Release。Release 资产包含 `mystia-steward-companion-bepinex.zip`、`update-manifest.json` 和可直接运行的 `mystia-steward-companion-companion-windows-x64.exe`；如发布机已配置 Android 工具链和签名配置，可通过 `build-release.ps1 -BuildAndroidApk` 或 `publish-release.ps1 -BuildAndroidApk` 额外生成并上传 `mystia-steward-companion-android-arm64-v8a.apk` 和 `mystia-steward-companion-android-armeabi-v7a.apk`。更新清单只指向 Mod 主包，独立 Windows 伴随窗口 EXE 和 Android APK 只给 B 设备跨局域网连接使用。
- 仓库内构建缓存统一通过 `pnpm artifacts:report/prune/clean` 管理。默认 12 GiB 高水位、8 GiB 清理目标、Android 1.5 GiB、.NET 0.5 GiB 和 14 天过期优先级，按文件逻辑大小统计；清理只以完整 Cargo profile/target triple、Gradle build 或 .NET `bin/obj` 为单位，不裁剪 Cargo 单文件，也不得与 Cargo、Gradle、Vite 或 dotnet 构建并发。常用 Tauri/Android package 命令在构建前 prune，直接 Cargo/dotnet 命令需要显式检查。`dist`、References、temp、依赖、Playwright 浏览器和签名材料不自动删除。正常 package/build 使用 staging 完整重建本次 `dist`，不得把旧 APK、manifest、tar、zip 或旧目录带入新发布；`publish-release.ps1 -SkipBuild` 才显式复用现有资产。PowerShell 和 bash package 脚本都只生成 canonical ZIP，缺少 ZIP 工具时必须在触碰旧 `dist` 前失败。
- Android APK 不能从 Windows EXE 直接转换。Android 版按 Tauri mobile 独立目标处理，Android applicationId 固定为 `com.tyukki.mystia.steward.companion`，通过 `apps/companion/src-tauri/tauri.android.conf.json` 覆盖 Android identifier，桌面 Tauri identifier 不变；前端通过 `companion_platform` 识别移动端并隐藏桌面窗口能力；Rust 后端用平台 cfg 隔离托盘、单实例控制、鼠标穿透、窗口状态、全局快捷键和游戏 PID 监控，但本地 API TCP command 与桌面共用。仓库已包含 `apps/companion/src-tauri/gen/android/` 工程和 `src-tauri` library entrypoint；生成的 Gradle Rust 插件使用 Corepack 调用 pnpm，release build 允许连接可信 LAN HTTP endpoint。签名 APK 通过 `pnpm tauri:android:apk:signed` 构建，读取本地被忽略的 `gen/android/keystore.properties`，按 `aarch64` 和 `armv7` 生成拆分 APK，验签后复制到 `mods/bepinex/dist`；release 脚本的 `-BuildAndroidApk` 参数复用该流程。Android Gradle 关闭 Kotlin incremental compilation，避免 Windows 上 Cargo registry 和项目分属不同盘符导致 Kotlin daemon 报 `different roots`。APK 构建需要 Android Studio/SDK/NDK、JDK、Android Rust targets、签名配置和真机 LAN 连接测试；未连接真机时只能验证 APK 构建和包元数据，不能宣称 LAN 已验证。Android 竖屏顶部页签使用横向滚动，焦点或激活页签需要自动滚入可视区域；应用整体需要通过 safe-area inset 避开状态栏和导航栏。
- Android APK 体积优化由签名 APK 脚本注入 `CARGO_PROFILE_RELEASE_STRIP=symbols`、`CARGO_PROFILE_RELEASE_LTO=thin` 和 `CARGO_PROFILE_RELEASE_CODEGEN_UNITS=1`；全局 Cargo release profile 不启用 LTO，避免 Windows-only 发布构建在 Rust 链接优化尾段长时间停顿。
- Tauri mobile 的 Rust lib target 内部名为 `mystia_steward_companion_mobile`，用于避开 Windows MSVC 下桌面 bin `mystia-steward-companion` 规格化后的 PDB 名冲突；桌面产品名、EXE 名、Tauri identifier 和 Android applicationId 不因此改变。
- 默认热键 `F8` 和 `RS Click` 的主语义是游戏与伴随窗口焦点切换；Mod 侧 `RS Click` 只做释放锁存，默认 800ms 可配置冷却由 Tauri 唯一 gate 管理且只在实际 `applied` 后计时。伴随窗口聚焦时由 Tauri 前端处理热键并按设置切回游戏，必须先确认游戏聚焦成功再隐藏窗口。Windows 侧以 `SetForegroundWindow` 非零返回或当前前台窗口属于目标进程确认成功，不把激活转换期的精确 HWND 瞬时不一致误判为失败。
- 伴随窗口手柄实现分为三层：`gamepad-input-engine.ts` 管理 `standard` mapping、活动设备、neutral rearm、按键边沿/重复、摇杆滞回和单方向仲裁；`gamepad-focus-manager.ts` 管理可见焦点、复合控件语义、modal、局部滚动及动态 DOM 回焦；`use-gamepad-navigation.ts` 只负责 React 生命周期和业务动作编排。左摇杆/十字键移动，`A` 确认，`B` 关闭弹层/返回或退出专注模式，`LB/RB` 切页，`LT/RT` 滚动，`Y` 进入专注模式或切换精简模式，`X` 收藏。恢复焦点、可见性、连接、设备或导航状态后必须等待至少 2 帧且连续 50ms 输入中立；动态回焦依赖稳定 key、action epoch 和 DOM 变化，不使用固定延时。
- 经营中稀客订单默认按首次捕获时间稳定排序；也可在设置页切换为稀客分组。稀客分组模式下，同一稀客订单放在一起，稀客组之间按该稀客最早订单出现时间排序，组内仍按点单先后排序。运行时捕获订单保留到明确移除、稀客离场或 6 小时硬上限，避免长时间未上菜时从伴随窗口消失。
- 运行时推荐状态会尝试读取当前夜间经营场景已摆放的全部厨具，优先读取 `CookSystemManager.Instance.AllCookers` 中的控制器和 `Cooker.AllAvailableCookerType`，再兜底读取 `IzakayaConfigure.CookerConfigure` 与 `RunTimeStorage.GetAllCookers()`；读不到快照时不要过滤料理。目标厨具高亮会复用当前推荐目标，并扫描 `AllCookers`、`AllCookerControllers` 和场景中的 `CookController` 兜底寻找可高亮对象；其中 `AllCookers` 是 IL2CPP Dictionary，必须按 1.0.4 的 entries/value 路径读取 values，不能只用通用 enumerable，否则经营中厨具快照可能正常但高亮扫描不到控制器。

- 运行时捕获订单维护 `ChangeVersion`；有捕获订单时，经营扫描优先使用捕获缓存作为稀客订单来源，同时继续读取活动稀客控制器以获取携带资金；捕获缓存为空，或捕获缓存有订单但本轮可接受订单少于缓存数量时，再走完整订单反射扫描补充业务缺失项。诊断开关只控制额外样本和日志，不得改变正式订单来源。UI 控制器在版本变化后延迟 0.2 秒强制刷新经营数据；捕获版本、场景和诊断状态都未变化时复用已有经营上下文，并按较慢节奏重新校验，避免伴随窗口 750ms 轮询带动 Unity 对象重扫。伴随窗口在 `经营中` 和稀客专注模式下以 750ms 轮询快照，其他页面保持 2 秒。经营末尾 manager 集合不可枚举时仍可使用捕获对象，但必须重新确认该对象仍由原 controller 持有且与请求强身份完全一致；Delivery 只接受未满足订单，Completion/NativeEvaluation 允许已送齐但尚未移除的订单。幽幽子三阶段进入 NativeEvaluation 前先从精确 Completion 对象读取 fulfilled，未送齐只等待；评价查找优先严格复核 capture 的强身份、所有权、已送达目标和回调，失败才扫描 manager 并复用同一验证器。剧情版回调只能来自最终匹配的同一原生 order/controller，重修版保留 `_50` / `_70` 检查。所有 `OrderBase` 候选统一 cast 为 `SpecialOrder` 后读取 raw Tag；古明地恋本体的 manager live-controller 专用路径保持不变。
- 本地 API 快照发布在 Unity 主线程节流到约 0.35 秒一次；快照内容签名是规范内容的固定 64 字符小写 SHA-256，不能把随订单和事件增长的规范原文带入 `knownSignature` 查询串。签名未变化时复用上一份缓存 JSON，不为了 `CapturedAtUtc` 或性能数字重复序列化；完整 `RuntimeDataCatalog` 不再随 `/snapshot` 周期性补发，`/snapshot` 只发布 `snapshotSignature`、`runtimeDataComplete`、`runtimeDataSource`、`runtimeDataStatus` 和 `runtimeDataSignature`，前端只在缓存为空或签名变化时后台读取 `/runtime-data`。前端轮询 `/snapshot` 时带 `knownSignature`，后端内容未变化时只返回 `{ unchanged: true, snapshotSignature }`；前端遇到 unchanged 只能更新连接存活状态，不能 `setSnapshot` 或触发推荐/自动化派生，轮询调度也不能依赖 React 重新渲染续约，必须由独立 interval/loop 持续观察后续经营状态变化。前端必须让 `/snapshot` 成功返回后立即更新主快照和签名，不能等待 `/runtime-data` 完成，否则经营中页的特殊经营、普客订单和自动化会被运行时目录请求阻塞；`/runtime-data` 失败只影响推荐目录缓存。前端必须缓存最近一次完整运行时数据，但不要用 `/snapshot` 原始 JSON 文本相等来跳过快照状态更新，以免运行时目录恢复被遗漏。总日志开启时，Local API 会记录 `/snapshot` 请求诊断，包含客户端、known/current 签名短值、full/unchanged、responseBytes、specialActive 和 normalOrders，用于区分前端未请求、连错 API 实例和快照被前端丢弃。`RuntimeReflectionRecommendationStateProvider` 的存储数据只用 `RunTimeStorage.GenerateSaveData()` 生成的一份运行时存储快照，`recipes` 为空时不得发布空的可用料理集合；玩家等级、流行喜好/厌恶 Tag 和明星店开关继续用 `RunTimePlayerData` / `RunTimeDayScene` 轻量 getter 读取。运行时固定目录读取完成后缓存映射和静态目录快照，经营扫描和诊断只复用缓存，不在 `NightBusinessReflectionProvider.LoadContext()` 中重新构造目录。`performanceMs` 会记录 `refresh.business`、`refresh.runtime`、`snapshot.serialize`、`runtimeData.serialize`、`automation.collect`、`snapshot.publish` 等耗时，概览页和经营中页展示最高几项用于排查掉帧。经营扫描还会记录 `business.rare.*`、`business.normal.*`、`runtime.cookerSnapshot`、`mission.serveTargets` 等子项；普客订单快照有短 TTL 缓存，避免一次快照发布链路内重复枚举 `OrderController`、HUD 和 `GuestsManager`。
- 本地 API 快照生产必须通过统一脏域发布入口：场景、运行时目录、稀客经营、普客订单、特殊经营、自动化和任务变化只标记对应 dirty domain，由 `StewardOverlayController` 在 `Update()` 末尾统一节流、刷新和发布。不要在新增功能中直接散落调用快照发布；若需要立即反映场景切换或运行时 ready 变化，应使用强制 dirty 标记。总日志开启时可记录 `[snapshot]` 诊断，包含 dirty domain、发布/跳过结果、签名、普客/稀客订单数和特殊经营阶段，用于区分“后端未生产快照”和“前端未消费快照”。
- 前端订单推荐 worker 和页面推荐 worker 会按 `RecommendationDataSet` 语义签名缓存完整运行时目录。签名未变化时，后续请求只传业务 payload 和数据签名，不再重复把完整运行时料理、食材、酒水、客人和规则目录结构化克隆进 worker；签名变化、worker 重建或首次请求才重新发送完整数据集。伴随窗口收到完整 `RuntimeDataCatalog` 后只在连接 hook 的独立缓存中保留一份，并从主 `snapshot` state 剥离完整目录，避免每轮快照和非当前页面 props 链路继续持有大对象。顶层工作台只挂载当前 active tab 的重型页面内容，页面推荐 worker 在 payload 为空时必须 terminate 并清空数据签名。该协议是自动化开启后降低 Mod 窗口内存和 WebView 卡顿的关键路径，新增 worker 推荐入口时要复用同一模式。
- 前端轮询完整快照时，只有在快照已经写入 React state，且所需 `/runtime-data` 已成功缓存或无需刷新时，才能推进 `knownSignature`。运行时目录读取失败不能阻断 `snapshot` 应用，也不能提前把 `snapshotSignature` 记录为已消费；否则后端会持续返回 `unchanged`，经营中页会保持空状态，直到页签切换等偶然重算才恢复。

- 夜间经营生命周期由 `RuntimeNightBusinessLifecycle` 单独拥有。只有 `WorkSceneSustainedPannel.OnPannelPostOpen/0`、`GuestsManager.CloseIzakayaDelayed/2`、`CloseIzakayaAndLeaveChallengeMode/2`、`NightScene.SceneManager.ToResult/0` 和 `OnInstanceDestroyed/0` 五个 Hook 全部成功才允许 Active，任一成员缺失都 fail-closed。`TryCloseIzakaya` 只是倒计时结束后的停止接客/清桌信号；游戏仍允许在座顾客继续点单，Mod 必须保持同一 Active generation 及订单捕获、推荐、自动化、料理 job 和 UI target。最后一桌离席后创建 `CloseIzakayaDelayed`，或特殊经营退出/结果转换时，才进入 Closing 并同步停止运行时访问、失效 target、清理稀客/普客捕获、特殊经营上下文、料理 generation 和自动料理 job；实例销毁进入 Destroyed。Closing 不能重新 Active，下一场只能在 Destroyed 后开启新 generation。场景名只用于辅助读取门禁，不再拥有第二套清理时序。

- 经营中页使用页内 `推荐` / `自动化` / `诊断` 视图分区；自动化视图集中资源、稀客/普客状态、厨具预约、活动 `AutomationCookingJob` 和订单详情。普客可见性来源是 `OrderController.GetShowInUIOrders()` 与 HUD，执行控制器必须来自 `NormalOrderRuntimeCapture` 或当前控制器扫描；订单按 `orderKey` 优先、桌号/料理/酒水槽位次之合并。普客自动化需要总开关和普客子开关同时开启，按首次出现顺序和设置并发数执行，订单变化用短防抖复查。活动 job、送达中或评价中的订单不重复占用开锅名额；job 的 waiting/interrupted/terminal 状态直接来自快照，不再按前端经过时长猜测。每笔普客订单独立记录送酒、开锅、送料理、评价和暂停状态；料理正常完成后直接送达，酒水在送达提交成功后扣库存，只有 `get_IsFullfilled()` 为真才评价，最终仍以 `HasEvaluated` 或订单消失确认。

- `AutomationCookingJob` 是跨帧料理的唯一权威状态，不再保留旧的前端计时恢复路径。每次精确 `CookController.SetCook(Sellable, Recipe, bool)` 都由 Harmony prefix 在原方法进入前分配新的料理 generation；即使原方法后半段异常，旧 job 也会保守退出。job 绑定 controller 指针和该料理 generation，而不是绑定某个可能被游戏原生完成流程替换的托管 Result wrapper；所有 job 注册、轮询、送达和 cleanup 还必须处于创建时相同的 Active 经营 generation。Mod 不调用 `FinishCooking`；同料理 generation 的原生最终成品可继续送达，料理或经营 generation 改变时旧 job 不得触碰游戏对象。自动送达模式下手动取走发布可恢复中断；仅开始料理模式下所有开锅仍登记 job，但只保留手动交接回执，不送达、不入箱、不复位，防止响应丢失后重复扣料。
- job 的烹饪停滞和出锅送达使用有效运行时间钟，只累计游戏可推进且相邻观测均 eligible 的区间；暂停、断线、非 Active 经营和运行时暂不可读不消耗 90 秒预算。phase/progress 真正前进才重置停滞钟，waiting、轮询成功、等待原生完成和中文状态文本都不能刷新进展。连续 Result 不可读、进度回退或进度停滞会保留旧锅并进入 blocked 人工确认终态；手动交接期间订单字段持续不可读也必须有界转为 blocked，而不是无限 waiting。每个可能重入经营结算的非幂等原生调用返回后都要复核经营 generation；已经 Closing/Destroyed 时立即停止后续对象访问，按已确认副作用返回 cancelled 或 uncertain。`LocalApiSnapshot.automationCookingJobs` 暴露 jobId、trace/order key、controller/result、generation、phase/progress、outcome/reason、交接模式和提交/清理计数，`automationEvents` 用递增 sequence 发布终态；`automationSessionId` 变化时前端清除旧进程状态并重新获取 lease。
- 正常成品直接通过统一送达 helper 提交给目标订单，不经过保温箱。非目标成品、特殊经营目标签名变化、成品 Tag 不符或目标连续不可达时，才进入 `IzakayaConfigure.StoreFood()` 恢复事务并发布对应结构化事件。IDA 已确认 `StoreFood` 与订单 `ServFood/ServBeverage` setter 都先写数据再执行回调；正常返回或异常后读取到同一 Sellable 对象均为 commit-once，不能重复送达、重复入箱或重复扣酒水。提交状态不可读时 blocked 且不清厨具。commit 后只允许有界重试同 generation 厨具 cleanup，并严格确认 `Phase == Idle`、`Result == null`、`ChosenRecipe == null`；耗尽则保留现场和提交/清理诊断。
- 自动化响应 outcome 固定为 `waiting/progressed/completed/interrupted/retryable-failure/blocked/fatal/cancelled`，C# 真实 `beverage/cooking-start/cooking-delivery/order` 阶段优先。失败计数绑定 `retryStage`；真实请求阶段变化或该阶段开关关闭时只清除普通失败计数/退避，不能污染其他阶段或绕过人工确认栅栏。只有 `progressed/completed` 清零当前阶段失败并刷新进展；waiting/interrupted 保留计数，retryable-failure 有界递增。副作用不确定的 blocked/fatal 设置 `manualResolutionRequired` 并保留 `prepared`，普通重试、阶段开关、总开关和无关订单事实都不能清除。Mod 端按目标保留 unresolved barrier，HTTP 入口和未提交 job 都必须在副作用前检查；玩家处理现场后由当前 lease 所有者通过 `/automation/barriers/ack` 精确确认 sequence，后端 ACK 成功后前端才清理状态。`cooking-mismatch-stored` 等事件仍是回退计数的唯一来源。所有自动开锅都登记 generation job；只开启开始料理时 job 仅作为手动交接回执，不送达、不入箱、不复位。
- 关闭自动化通过 `POST /automation/jobs/cancel` 建立 command epoch 原子屏障：服务端在 lease 锁内提升 epoch，epoch fence 等待当前已开始命令完整结束，再取消其余旧命令并清理全部 job，确认后才释放 lease；前端在取消确认前持久保存原 endpoint，lease acquire 单飞且取消先等待在途 acquire，避免旧续约重新占有 lease。临时断线不清理 job，lease TTL 到期后新客户端取得更高 epoch，通过 job 快照和事件 sequence 接管；旧 epoch 请求、排队命令和迟到响应全部失效。
- 稀客自动化开始时只从当前订单的 `executionPlans[0]` 锁定料理、加料、酒水和厨具，不再扫描后续执行计划；该主计划的料理和酒水同时投影为页面首项，并供游戏界面置顶和两类高亮使用。开锅或送酒后，库存变化和推荐重算可以更新页面主计划，但同一自动化任务不能中途切换锁定目标。若目标料理标注为“偏好备选”，状态里也要显示“偏好备选”。特殊经营的动态目标 Tag 是料理锁有效性的一部分：怪诞料理大赛等场景必须用挑战类型、订单角色、阶段和当前目标 Tag 构造签名，签名变化、旧目标不再命中当前 Tag，或旧组合已被实机判定失败时，前端应结束旧锁并从新主计划开始新的执行尝试；怪诞二、三阶段主计划还必须先满足原订单料理/酒水和最高评价估算。料理出锅后 C# 必须按锁定目标直接送达当前订单，不再复用送餐盘堆积料理或可接受成品列表作为兜底。

- 从 `GuestGroupController.AllOrdersData` / `AllOrders` / `PeekOrders()` 读取稀客订单时，运行时对象可能以 `OrderBase` 视角返回；捕获、Provider 和自动化实时扫描都必须先通过共享入口强转到 `GuestsManager+SpecialOrder`，否则 `Type`、`SpecialGuests` 和 raw Tag 字段读取会失败，不能由各路径分别复制 cast 逻辑。
- 稀客订单的原始身份来自 `SpecialOrder.RequestFoodTag` / `RequestBeverageTag`；`0`、`-1` 等数值只要读取成功都必须保留，读取失败用 nullable / `Has*TagId=false` 表示，不能把负数丢弃或当作缺失。`SpecialGuestsController.GetOrderFoodText/GetOrderBevText` 是游戏服务面板和投掷送达面板共同使用的正式展示接口，会应用订单文本 override；捕获层应独立保留该文本，但绝不能把它反向解析成身份或用于订单匹配。没有稀客 controller 上下文时，`SpecialOrder.ToString()` 也只作为展示回退。不要用 `foodRequest` / `beverageRequest` 字段猜测替代原始属性，也不要把订单展示 getter 和静态目录中禁止的未消费语言探针混为一谈。
- 手动事件稀客订单不一定走普通 `PostGenerateOrder` 路径。运行时捕获需要覆盖 `GuestsManager.SetManualControllerOrderInternal`；`EvaulateManualOrder` 可按原生评价清理缓存，`EndDlc4SpecialManualOrder` 只能在当前订单已 `IsFullfilled` 时清理，不能把事件结束回调直接等同于订单完成。项目不再解析 Unity/BepInEx 控制台订单日志，稀客点单必须来自运行时订单对象、控制器、HUD/面板或运行时缓存。
- 总日志开启且经营数据扫描触发时，运行时固定数据会按主题写入总日志 section：`runtime-static-data` 映射稀客与 `aliasSource`、`runtime-tags` 标签和 TagRule、`runtime-database` 核心食材/酒水/料理表对照与读取方式、`runtime-guests` 普客/稀客/事件变体、`runtime-izakayas` 场景和客人池。游戏数据库未初始化时每 5 秒重试，section 中 `Complete: True` 表示读取成功。
- 运行时固定数据不只写总日志，也会构造成 `RuntimeDataCatalog` 并发布到 `/runtime-data`。`/snapshot` 只保留运行时目录元信息和签名，伴随窗口使用按签名缓存的运行时料理、食材、酒水、普客和稀客数据；`runtimeDataComplete=false` 时显示等待运行时数据。排查数据依赖时，先看概览页“推荐数据”是否显示“游戏运行时”，再开启总日志并检查对应 runtime section 的 `Complete: True`；导出的诊断包会同时包含 `snapshot/current-snapshot.json` 和 `snapshot/runtime-data.json`。
- 运行时料理基础食材是数量敏感序列，不是集合。`RuntimeDataCatalog.Recipes[].Ingredients` 和前端 `RecipeCatalogItem.ingredients` 必须保留重复项，例如同一材料需要两份时数组中出现两次；只有 tag、场景和 ID 集合可以去重。推荐加料槽位、基础成本、大份动态 tag 和自动化下单五格保护都依赖这个重复数量语义。
- 经营中页普客订单展示必须区分游戏原订单和推荐执行方案。`NormalBusinessOrder` 只表达游戏快照里的请求料理/酒水、桌位、顾客和状态；配方、厨具、加料、最终标签和特殊经营规则原因由前端 `normal-order-details` 投影层计算。普通经营执行方案等于原订单基础配方；怪诞料理、幽幽子挑战等特殊经营可以通过 `selectSpecialBusinessNormalExecutionTarget()` 生成实际执行方案。该投影属于候选搜索级别工作，只能在 worker 中按需计算，UI 组件只能消费独立详情请求返回的 `normalOrderDetailPlans` 结果；详情请求失败时页面应显示错误状态而不是永久“计算中”。普客详情 worker 输入必须由语义签名稳定，且详情卡片只响应本卡片实际展示的库存数量变化，避免快照轮询和大量普客订单导致 `经营中 -> 推荐 -> 普客` 页面持续重算或重绘。不要把这些执行方案反写成 C# 普客订单原始字段，也不要在 UI 里重复实现特殊经营规则。
- `specialBusiness` 上下文读取 `NightSceneDirector.ChallengeMode`。挑战显示名来自 `NightSceneDirector.ChallengeType` 枚举成员的 `InspectorNameAttribute` 固定中文元数据，不随游戏语言切换；规则注册表不保存名称映射。元数据不可读时保留有效 challenge type、原始 `ChallengeMode` 和明确诊断，不用 `DataBaseLanguage.GetMissionLanguage` 猜测标题，也不使用社区昵称。
- 已确认的 HUD 目标包括妖梦科目一/科目二的目标营业额与符卡计数、血池地狱挑战的双料理 Tag、怪诞料理大赛的单料理 Tag/剩余时间/阶段进度、幽幽子挑战进度，以及青娥/布都/屠自古料理挑战的目标营业额。`RecommendationState` 不写入特殊目标；目标营业额、符卡计数和未确认结算规则只展示。
- 特殊经营规则按模块维护：C# 位于 `mods/bepinex/src/Save/SpecialBusiness/`，前端位于 `apps/companion/src/companion/domain/special-business/` 并通过 registry 接入；规则构造在 `rules/`，普客执行目标在 `normal-targets/`，怪诞料理运行时策略集中在 `WackyCookingCompetitionRuntimePolicy`。
- 怪诞料理大赛的游戏原生规则按阶段不同：第一阶段按喜好 Tag 命中数改判；第二阶段先要求 `ExGood` 再检查当前目标 Tag；第三阶段分身接受 `Normal` 以上并由目标 Tag 再改判。前端对第二阶段和第三阶段分身均保留原订单料理/酒水，并要求预估 `ExGood` 与当前目标 Tag；第三阶段的 `ExGood` 条件是 Mod 的保守策略，不得写成游戏原生最低门槛。
- 怪诞料理大赛分身只在原料理上选择安全加料。`AutomationCookingJob` 保存阶段、目标 Tag 签名、原订单 match 目标和实际 execution 目标；出锅前比较签名，再用 `Sellable.Tags` 校验成品。签名或 Tag 不符时只对本 generation 执行 commit-once `StoreFood`，前后端共同抑制已确认失败的组合。
- 古明地恋本体不能只凭 `guestId=2006` 判断；分身优先读取 `GuestControllerSpawnType=GhostInChallenge`，本体还需结合阶段、订单类型、手动控制器状态和真实 controller。护盾期按揭示 Tag 选择并走通用评价；破防后保留原订单、按剩余目标分/预算/剩余提交次数规划，并通过带 Boss 原生评价回调的 live controller 进入 `EvaluateOrder()` / `OverrideEvaluationCallback`。破防期推荐与自动化共享同一规划入口。
- 幽幽子第二阶段只在稀客标准评价达到 `ExGood` 并触发正面符卡后推进；候选满足当前稀客料理/酒水点单、避开该稀客自身的厌恶，并在排除点单 Tag 后命中至少 `2` 个额外喜好 Tag。该阶段不使用幽幽子的固定厌恶 Tag 或等级合计门槛。第三阶段 `progress` 保留原订单、避开幽幽子的挑战厌恶 Tag，并要求料理与酒水等级合计至少为 `5`；`refresh` 只清理精确原订单且不承诺推进。未 fulfilled 时只等待；已送齐后 capture 优先严格复核、manager scan fallback。剧情版只复用同一原生 order/controller 捕获的 `onEvaluate` 调用 `EvaulateManualOrder`，重修版确认 `_50` / `_70` 进度回调后调用 `EvaluateOrder()`。对应回调、送达目标或阈值不可确认时暂停，普客执行目标、稀客 execution plan、推荐首项和自动化目标共享同一评分入口。
- 挑战/BOSS 订单可能表现为 `OrderBase/Normal` 或 `SpecialOrder`，必须由统一分类器标记归属。live `OrderBase` 客人字段不可读时不能只因 `guestId` 缺失拒绝，但 controller、评价回调、送达目标和原订单不变量仍必须严格确认。血池地狱挑战的 BOSS 订单阻止标准自动化；新增 BOSS 自动化前必须用实机总日志验证移动、送达、评价和结算副作用。
- 自动化步骤和总日志记录 `rule=`、原始/有效挑战类型、match/execution 对照、评价回调证据和阻断原因。任何跨帧任务都保留挑战类型、阶段、订单角色和目标签名，绝不能在空目标 Tag 时回退到当前轮换 Tag。
- 特殊经营激活时，可以在订单层按经营中当前排序跳过没有主执行计划的订单，选择第一笔存在 `executionPlans[0]` 的稀客订单；选中后页面料理/酒水首项、自动化初始锁、游戏界面置顶和目标厨具高亮只能消费同一个主计划。没有主计划时不发布目标，也不得从后续计划另选目标。
- 稀客订单专注模式支持精简模式和料理/酒水显示数量配置；精简模式隐藏推荐料理 Tag 并压缩推荐面板间距，显示数量包含收藏置顶项。默认精简状态在 `设置 -> 推荐` 配置，进入专注模式后仍可临时切换并记忆。
- 实验性自动化由设置页总开关启用，经营中页按稀客订单和普客订单分组配置。稀客使用 `autoPrep*` 阶段配置，普客使用 `autoNormal*` 阶段配置；普客送酒、开始料理、送料理、完成订单和出错暂停互不复用。设置页参数控制稀客/普客并发、最大重试和最大回退，默认值为 `2`、`3`、`3`、`2`；稀客和普客完成订单都按单笔订单 readiness 独立推进，并优先处理已满足料理和酒水的订单，但本地 API 调用仍串行执行。开启自动开始料理后固定尝试完成原生 QTE 奖励结算，不再提供跳过或完成 QTE 的配置开关；该流程不会打开游戏音游面板，失败时只显示诊断并继续料理流程。稀客和普客的酒水、目标料理都通过统一运行时送达 helper 直接送至订单，不再经过送餐盘、保温箱或游戏料理暂存容器作为自动化中转；只有非目标/黑暗料理出锅，或出锅后目标订单/可执行控制器连续不可达时，才作为恢复动作写入游戏保温箱。普客自动化需要开启“启用普客处理”且至少开启一个实际阶段；临时失败应继续等待并重试，非临时失败才按对应订单类型配置暂停。稀客与普客暂停状态不能共用，普客内部也要按订单 key 隔离暂停。

## 推荐排序口径

- 经营中/稀客推荐排序可由伴随窗口 `设置` 页的任务料理、收藏料理、收藏酒水置顶开关、自定义推荐料理单条置顶和推荐权重共同控制。硬过滤后先应用置顶规则，再进入权重排序；默认均衡预设综合稀客偏好、厌恶风险、加料数量、资源压力、成本、利润、酒水库存和当前厨具可做等目标。
- 当前推荐权重项包含料理偏好命中、酒水偏好命中、减少厌恶标签、减少加料数量、少用低库存食材、降低食材成本、提高预计利润、优先酒水库存和当前厨具可做。资源压力优先惩罚低库存材料，并对额外加料加权；不要再使用“总成本越高越靠前”作为收益判断。任务料理、收藏料理和收藏酒水都不是权重项，只能通过对应置顶开关控制。
- 稀客和经营中主推荐使用统一料理/酒水候选池；满足当前点单料理 Tag / 酒水 Tag 的结果优先，不满足点单但命中稀客喜好的结果直接进入同一列表并标注为“偏好备选”。完整候选先构造并排序执行计划，`executionPlans[0]` 是唯一主执行计划，其料理与酒水必须投影为页面首项；经营中页和稀客订单专注模式再按用户设置截取其余展示行，不再维护独立喜好备选数组。料理推荐优先 3 分以上候选，但低于 3 分且满足点单的料理仍要作为兜底显示。
- `排除缺失厨具` 开启且已读取厨具快照时，统一推荐列表会隐藏当前场景未摆放对应厨具的料理；厨具类型 1-5 映射为煮锅、烧烤架、油锅、蒸锅、料理台。
- 稀客收藏保存在 `BepInEx/config/MystiaStewardCompanion/favorites.json`，按 `customerId + foodTag` 收藏料理方案（含加料 ID），按 `customerId + beverageTag` 收藏酒水。自定义推荐料理保存在 `BepInEx/config/MystiaStewardCompanion/custom-recipes.json`，按 `customerId + foodTag/null + foodId + extraIngredientIds` 生效，其中 `foodTag=null` 表示该稀客全部点单料理 Tag；顶层 `enabled` 是整个功能的门禁，关闭不改写单条状态。管理页可按稀客或基础料理派生分组，页面/分组/单条 flags 更新使用同一原子端点，推荐优先级只在同一稀客内移动。旧 `favorites.source=manual` 仅在 `v1.2.x` 作为一次性迁移输入：Local API 启动阶段先原子写入自定义料理，再删除旧收藏条目，使后续读取和 CRUD 端点不承担迁移副作用；该迁移计划在 `v1.3.0` 删除，不是正常推荐路径。收藏料理置顶、收藏酒水置顶、自定义推荐置顶和自动化收藏限定都不绕过解锁、库存、预算、排除项和缺失厨具过滤。
- `任务料理置顶` 使用当前稀客已接取的 `ServeInWork` 投喂任务目标料理。目标料理通过硬过滤后可在经营中推荐中置顶并显示 `任务` 标识；该功能只影响推荐顺序和自动化选择，不自动推进任务状态。
- 经营中稀客推荐会根据当前稀客资金构造预算上下文。预算策略支持阻止超预算、仅提示和忽略预算；订单级 `isFreeOrder=true` 时不应用付款预算阻止，非免费订单继续按当前预算策略判断。排除材料会同时过滤基础配方和加料，排除酒水只过滤酒水候选。排除项下拉的库存显示来自 `RuntimeSets`，排序方式只影响设置页选项展示，不进入推荐缓存签名。预算、免费订单状态、排除项、缺失厨具和同基础料理展示数量都必须进入推荐缓存签名，避免设置变化后继续显示旧结果。
- `同基础料理显示` 默认值为 1。同一基础料理存在多个加料变体时，稀客页和经营中页只展示主计划之外当前排序最靠前的指定数量；主计划料理始终保留在首项。收藏匹配仍按基础料理和加料精确匹配；自动化收藏限定只有在总开关、对应阶段和订单自动化权限均开启时参与主计划归一化，并且必须在执行计划上限截断前处理。自动化开始时只锁定主计划，不得依赖裁剪后的 UI 行或扫描后续计划。
- 经营中订单显示顺序默认是首次出现时间升序；切换为稀客分组时，同组内仍按首次出现时间升序。新订单不应在点单顺序模式下插到已有订单前面；自动化和置顶目标必须使用页面同一排序结果。
- 推荐行需要显示库存数量；料理行需要显示厨具、基础配方和加料，并对这些定位信息做高亮。
