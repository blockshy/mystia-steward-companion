# Repo Memory

## 当前项目定位

仓库项目名统一为 `mystia-steward-companion`，定位为《东方夜雀食堂》BepInEx IL2CPP Mod 与 Tauri 伴随窗口。桌面端是 A 设备本机主入口，Android 端只作为 B 设备通过 LAN 连接的移动伴随窗口。

## 关键目录

- `mods/bepinex/`：插件源码、本地 API、运行时读取、构建脚本和 Mod 文档。
- `apps/companion/src/`：伴随窗口 React 工作台、推荐算法、tag 规则、类型和结构化数据。
- `apps/companion/src-tauri/`：Tauri 伴随窗口壳，桌面能力与 Android 移动端边界在这里隔离。

## 开发事实

- Mod 不编译引用额外的游戏业务 DLL，运行时通过反射读取游戏已加载的 IL2CPP interop 类型。
- 用户可见项目名、安装目录和发布产物使用 `mystia-steward-companion`。`v1.1.x` 只暂时保留旧 GUID 配置复制和 Local API 启动阶段执行的 `favorites.source=manual` 转自定义料理两项一次性迁移，均计划在 `v1.2.0` 删除；除此之外，旧名称只允许出现在上游来源说明中，不保留旧路径、旧类型或旧 API 别名。
- `References/` 只放本机编译 DLL，不提交仓库。
- 推荐数据来自游戏运行时 `RuntimeDataCatalog`；`build-release.ps1` 和发布包只包含 Mod DLL 与伴随窗口程序。
- 用户安装和测试优先使用已验证的 BepInEx Bleeding Edge #783 Windows x64 IL2CPP 包：`BepInEx-Unity.IL2CPP-win-x64-6.0.0-be.783+c58c42d.zip`。#784 及之后构建当前不建议用于本项目，后续如需支持新版 BepInEx，必须重新实测并检查运行时日志。
- 独立伴随窗口默认通过 `127.0.0.1:32145` 读取运行态；该回环 listener 必须始终保留。`LocalApi.AllowLanConnections=true` 只会额外开启 LAN listener，供可信局域网设备连接；LAN 配置和 Token 重置只能由 A 设备本机回环客户端调用。所有正式 Tauri runtime 统一通过 Rust TCP command 访问 API，只有浏览器开发模式直接 fetch；Rust 代理的连接超时最长 5 秒，响应读取超时按前端命令要求最多允许 60 秒。除 `/health` 外，本地 API 使用 `X-Mystia-Steward-Companion-Token` 授权，远程伴随窗口需要手动输入 A 设备 endpoint 和 token，代理只接受 loopback/private/link-local IPv4 endpoint。API 只接受规范路径，不提供 `/` 或 `/api/*` 别名；只读查询使用 `GET`，所有文件、运行时、配置、控制权、诊断和更新副作用使用 `POST`，现阶段写操作参数仍可使用 query。`/updates/status` 会归并 updater 结果并可能写入或删除状态文件，因此也使用 `POST`。
- 伴随窗口控制端口固定为 `127.0.0.1:32146`，支持 `show`、`toggle`、`exit` 消息；Mod 热键应先通知已有窗口，控制端口不可达时才启动新进程。
- 伴随窗口会在 Tauri app data 目录保存 `window-state.txt`，记录外框位置和内框尺寸；启动时恢复大小和仍在显示器范围内的位置，防止换显示器后窗口离屏。
- 桌面主窗口在 Tauri 配置中初始隐藏，Rust setup 恢复 `window-state.txt` 后再显示并聚焦，避免启动时先显示默认位置再跳到保存位置。全平台图标以 `apps/companion/src-tauri/icon-source.svg` 为唯一母版；母版根元素通过 `data-icon-background` 声明通用底色、通过 `data-android-background` 声明 Android adaptive 底色，并用 `icon-background` / `icon-foreground` 提供明确分层。`pnpm icons:generate` 从母版重建桌面 PNG、Windows tile、九层 256-first ICO、tray、固定 chunk 顺序的 ICNS、不透明 iOS 图标、Android legacy/adaptive 图标、APK 工程实际资源和 favicon；`pnpm icons:check` 对全部生成物做字节幂等、尺寸、alpha、安全区和容器结构校验。Android legacy 固定为 48/72/96/144/192，规避 Tauri CLI 2.11.2 的 hdpi 49px 生成错误；adaptive foreground 使用缩小后的前景层，除官方安全区外还需通过额外视觉留白校验，`icons/android` 与 `gen/android/app/src/main/res` 的图标必须同步。
- 伴随窗口 `设置` 页分为 `窗口 / 连接 / 推荐 / 自动化 / 更新`。`窗口` 负责背景透明度、文字透明度、焦点切换行为、切换冷却时间、置顶、鼠标穿透锁定、主题、手柄导航和显示调试信息；`连接` 负责本机地址、LAN 状态、按默认网关和接口类型排序的结构化 LAN endpoint、LAN 监听地址、Token 和可信局域网访问，多地址必须逐项复制，不能静默使用字符串排序首项；`推荐` 负责经营中订单排序、稀客专注模式默认精简、缺失厨具硬过滤、任务料理/收藏料理/收藏酒水置顶、推荐权重、预算处理、带库存显示和名称/库存排序的排除材料/酒水、同基础料理展示数量、实验性游戏界面置顶和目标厨具高亮；`自动化` 负责实验性自动化总开关和参数。背景透明度通过 Tauri transparent window + CSS 背景 alpha 实现，旧 `windowOpacity` 会迁移为背景透明度；文字透明度单独影响普通文字、图标和辅助徽章内容，主操作按钮保持不透明；稀客专注模式的料理/酒水显示数量在专注模式浮层内调整。鼠标穿透通过 Tauri 原生窗口忽略鼠标事件实现，`F10` 切换，`F8`/`RS Click`/托盘显示会自动关闭穿透。
- 伴随窗口固定包含 `概览`、`普客`、`稀客`、`自定义推荐料理`、`经营中`、`任务`、`修改`、`帮助`、`设置` 页签；`日志` 页签只在 `显示调试信息` 开启后显示。帮助页内容来自 `apps/companion/src/data/help-content.json`，页面只做搜索、目录树和详情渲染；用户可见功能或排查流程变化时需要同步该 JSON。
- 伴随窗口 UI 基础组件集中在 `apps/companion/src/components/ui/`，并通过 `apps/companion/src/components/ui-kit/` 对外提供统一导出。当前项目组件层以 Mantine 组件为交互基础，封装了按钮、输入、选择框、多选框、页签、开关、滑杆、树形目录、折叠面板，以及项目展示组件 `ListPanel`、`InfoLine`、`StatusCard`、`Metric`、`EmptyRow`、`EmptyState` 和选项组。视觉形态以企业控制台式扁平分组、直角窄边框、标题条和表格化行项目为准，保留项目既有配色；除开关、滚动条滑块等需要圆形几何的控件外，不再使用圆角。后续不要继续复制外部模板风格组件，也不要在业务页面手写第二套开关/滑杆/卡片样式。
- 伴随窗口根滚动区域固定预留纵向滚动条槽位，避免页面高度变化时滚动条挤占宽度造成内容横向跳动；窗口、下拉和日志滚动条使用主题色并跟随背景透明度。
- 焦点切换支持两种模式：隐藏伴随窗口再聚焦游戏，或保持伴随窗口悬浮并只聚焦游戏。保持悬浮依赖窗口置顶，独占全屏游戏可能覆盖置顶窗口，推荐窗口化或无边框窗口化。
- 伴随窗口退出跟随不只依赖本地 API `/health` 失联，还会监控启动参数中的 `--game-pid`。游戏窗口 X、游戏内退出按钮、或 Unity 退出阶段未及时发送 `exit` 控制消息时，都应由 PID 监控兜底关闭伴随窗口。
- `修改` 页通过 `/inventory/set` 和 `/inventory/bulk-set` 在 Unity 主线程写入当前运行时材料和酒水库存；材料和酒水列表可按名称或库存排序。页面只保留单项 `-10`、`+10`、`99` 和当前存档可编辑材料/酒水批量设为 `99` 快捷按钮，用户仍需在游戏内保存才能持久化。
- 库存写入只走 `RunTimeStorage` 四个 Range 原生入口并在写后精确读取数量；不得在原生异常时直写 `Ingredients` / `Beverages` 私有字典。库存、订单和稀客邀请的主线程命令按类型有界排队且每帧最多执行一个；排队超时会取消未开始命令，已开始命令等待确定结果，控制器销毁会唤醒所有等待者。Local API handler 同样有并发上限，停止服务时先拒绝新连接并关闭在途 socket。
- 伴随窗口 `日志` 页只保留总日志 `BepInEx/config/MystiaStewardCompanion/aggregate-mod.log` 开关、总日志目录、文件上限和诊断包导出。总日志默认关闭，启用后捕获 BepInEx 全局日志源，并接收自动化、经营诊断和运行时固定数据诊断；每条记录标注时间、channel、来源和线程，单个文件 10 MB 后拆分为递增编号分片。默认保留 30 个文件，约 300 MB，超过上限时删除最旧分片；该上限不保护 BepInEx/Unity 共享 output log，后台 worker 不得无限异常重试刷共享日志，Mod 也不接管共享日志文件。订单相关自动化日志使用 `trace=R-0001` / `trace=N-0001` 标识单笔稀客/普客订单，经营中页显示同一“日志”标识；排查长时间或难复现问题时优先让用户开启总日志、复现后提供当前文件和相关分片。
- Mod 不修改全局 `BepInEx.cfg`，也不主动隐藏宿主控制台；控制台是否启用由 BepInEx/用户配置决定。`SetConsoleUtf8` 只在用户启用时调整当前控制台编码。
- 自动更新检查、下载和安装由单操作门串行；manifest 严格校验 schema 1、版本/tag/channel、包名、SHA256 和长度，包体流式写盘。安装只使用 staged 包内已校验的 updater，且 staged 版本必须高于当前插件版本，旧暂存包只显示为不可安装，不得触发降级。读取更新状态时会归并独立 updater 留下的结果并维护状态文件，因此对应本地 API 不是只读 GET。
- 游戏内 IMGUI 面板已移除；Mod 在游戏侧只保留后台控制器、本地 API、运行时读取、自动化和伴随窗口唤起。
- 仓库不使用 GitHub Actions 自动构建 Release；`.github/workflows/ci.yml` 只保留手动前端检查。版本发布采用 Windows 本机构建后由 GitHub CLI 上传。自动更新发布只支持稳定版 `X.Y.Z` 和预览版 `X.Y.Z-preview.N`；预览版必须是 GitHub Prerelease，用于 `dev` 上测试 `preview.1 -> preview.2 -> stable` 更新链路，稳定版再合并 `main` 发布普通 Release。Release 资产包含 `mystia-steward-companion-bepinex.zip`、`update-manifest.json` 和可直接运行的 `mystia-steward-companion-companion-windows-x64.exe`；如发布机已配置 Android 工具链和签名配置，可通过 `build-release.ps1 -BuildAndroidApk` 或 `publish-release.ps1 -BuildAndroidApk` 额外生成并上传 `mystia-steward-companion-android-arm64-v8a.apk` 和 `mystia-steward-companion-android-armeabi-v7a.apk`。更新清单只指向 Mod 主包，独立 Windows 伴随窗口 EXE 和 Android APK 只给 B 设备跨局域网连接使用。
- Android APK 不能从 Windows EXE 直接转换。Android 版按 Tauri mobile 独立目标处理，Android applicationId 固定为 `com.tyukki.mystia.steward.companion`，通过 `apps/companion/src-tauri/tauri.android.conf.json` 覆盖 Android identifier，桌面 Tauri identifier 不变；前端通过 `companion_platform` 识别移动端并隐藏桌面窗口能力；Rust 后端用平台 cfg 隔离托盘、单实例控制、鼠标穿透、窗口状态、全局快捷键和游戏 PID 监控，但本地 API TCP command 与桌面共用。仓库已包含 `apps/companion/src-tauri/gen/android/` 工程和 `src-tauri` library entrypoint；生成的 Gradle Rust 插件使用 Corepack 调用 pnpm，release build 允许连接可信 LAN HTTP endpoint。签名 APK 通过 `pnpm tauri:android:apk:signed` 构建，读取本地被忽略的 `gen/android/keystore.properties`，按 `aarch64` 和 `armv7` 生成拆分 APK，验签后复制到 `mods/bepinex/dist`；release 脚本的 `-BuildAndroidApk` 参数复用该流程。Android Gradle 关闭 Kotlin incremental compilation，避免 Windows 上 Cargo registry 和项目分属不同盘符导致 Kotlin daemon 报 `different roots`。APK 构建需要 Android Studio/SDK/NDK、JDK、Android Rust targets、签名配置和真机 LAN 连接测试；未连接真机时只能验证 APK 构建和包元数据，不能宣称 LAN 已验证。Android 竖屏顶部页签使用横向滚动，焦点或激活页签需要自动滚入可视区域；应用整体需要通过 safe-area inset 避开状态栏和导航栏。
- Android APK 体积优化由签名 APK 脚本注入 `CARGO_PROFILE_RELEASE_STRIP=symbols`、`CARGO_PROFILE_RELEASE_LTO=thin` 和 `CARGO_PROFILE_RELEASE_CODEGEN_UNITS=1`；全局 Cargo release profile 不启用 LTO，避免 Windows-only 发布构建在 Rust 链接优化尾段长时间停顿。
- Tauri mobile 的 Rust lib target 内部名为 `mystia_steward_companion_mobile`，用于避开 Windows MSVC 下桌面 bin `mystia-steward-companion` 规格化后的 PDB 名冲突；桌面产品名、EXE 名、Tauri identifier 和 Android applicationId 不因此改变。
- 默认热键 `F8` 和 `RS Click` 的主语义是游戏与伴随窗口焦点切换；伴随窗口聚焦时由 Tauri 前端处理热键并按设置切回游戏。手柄切换需要释放锁存和可配置后端防抖，防止同一次长按连续 toggle；默认冷却时间为 800ms。
- 伴随窗口内手柄导航由 `apps/companion/src/companion/use-gamepad-navigation.ts` 管理：左摇杆/十字键移动焦点，`A` 确认，`B` 返回或退出专注模式，`LB/RB` 切页，`LT/RT` 滚动，`Y` 进入专注模式或切换精简模式，`X` 收藏当前推荐行。导航采用 `data-gamepad-scope` 分区，顶部页签栏左右键只在页签之间移动，向下进入当前页面内容；内部 `TabsList` 左右键只在当前页签组内移动，下键进入 active panel，panel 顶部上键回到对应 trigger；`SegmentedControl` 以可见 label 作为手柄焦点目标，左右键只在当前选项组内切换；横向按钮组和工具条使用 `data-gamepad-axis="x"` 约束左右移动。通用 content 空间导航按交叉轴对齐优先：左右移动优先垂直对齐候选，上下移动优先水平对齐候选，没有对齐候选时才回退到跨行/跨列候选。行内控件左右移动优先在当前 `data-gamepad-row` 内完成，range 和 Mantine `[role="slider"]` 左右键直接调值，Select/MultiSelect 下拉框必须由确认键展开且展开后方向键才移动选项，推荐行和收藏按钮需要稳定 `data-gamepad-focus-key` 以便状态变化后回焦。Gamepad API 轮询使用集中输入状态机，按键同时读取 `pressed` 与模拟量 `value`，并在 blur、页面隐藏、手柄断开、无手柄或导航关闭时重置 latch；`A` / `X` 在 active element 丢失时会复用上一手柄高亮元素，避免第一次确认被焦点恢复吞掉。
- 经营中稀客订单默认按首次捕获时间稳定排序；也可在设置页切换为稀客分组。稀客分组模式下，同一稀客订单放在一起，稀客组之间按该稀客最早订单出现时间排序，组内仍按点单先后排序。运行时捕获订单保留到明确移除、稀客离场或 6 小时硬上限，避免长时间未上菜时从伴随窗口消失。
- 运行时推荐状态会尝试读取当前夜间经营场景已摆放的全部厨具，优先读取 `CookSystemManager.Instance.AllCookers` 中的控制器和 `Cooker.AllAvailableCookerType`，再兜底读取 `IzakayaConfigure.CookerConfigure` 与 `RunTimeStorage.GetAllCookers()`；读不到快照时不要过滤料理。目标厨具高亮会复用当前推荐目标，并扫描 `AllCookers`、`AllCookerControllers` 和场景中的 `CookController` 兜底寻找可高亮对象；其中 `AllCookers` 是 IL2CPP Dictionary，必须按 1.0.4 的 entries/value 路径读取 values，不能只用通用 enumerable，否则经营中厨具快照可能正常但高亮扫描不到控制器。
- 游戏界面置顶和目标厨具高亮由伴随窗口通过 `POST /ui-pinning/target` 下发；`recipeId` 使用游戏 `Recipe.Id`，不能用成品 `foodID`。发布成功签名按 endpoint、token、连接代际和完整目标去重；业务 `ok:false` 或网络失败持续按上限退避重试，断线或重新应用连接会失效旧成功签名。Worker 输入过期/pending 时保留上一有效目标但不发布旧计算结果，确定 error 时发布空目标并锁存当时的成功 revision，只有新的 current 成功 revision 才恢复目标；任一功能开关变化都必须立即进入发布队列。Tauri 原生请求不可取消，发布器必须单写者串行并只补发最新 desired 状态，不能让旧请求晚到覆盖新目标。Mod 侧场景/运行时临时清理恢复已染色 cooker renderer 和列表 UI Image，但不主动清空当前 target/generation；用户关闭功能或插件销毁时才清空。列表 Image 的实际恢复和着色只能发生在 Unity 主线程。
- 经营中页顶部只保留经营场景、推荐数据、自动化状态、特殊经营摘要、厨具快照和目标厨具等摘要信息；扫描状态、性能耗时和 `RuntimeUiPinningService.Status` 放在调试模式下的 `诊断` 视图。排查“缺失厨具过滤/游戏界面置顶/列表高亮/目标厨具高亮”时，优先让用户开启显示调试信息并提供经营中页 `诊断` 视图中的这些状态；列表高亮重点检查 `listHighlight` 的 `hooks/state/tracked/missingImage/bindingErrors/visualErrors/restoreErrors`。需要日志时开启总日志并导出诊断包。

- 本地 API 快照发布在 Unity 主线程节流到约 0.35 秒一次；快照内容签名未变化时复用上一份缓存 JSON，不为了 `CapturedAtUtc` 或性能数字重复序列化；完整 `RuntimeDataCatalog` 不再随 `/snapshot` 周期性补发，`/snapshot` 只发布 `snapshotSignature`、`runtimeDataComplete`、`runtimeDataSource`、`runtimeDataStatus` 和 `runtimeDataSignature`，前端只在缓存为空或签名变化时后台读取 `/runtime-data`。前端轮询 `/snapshot` 时带 `knownSignature`，后端内容未变化时只返回 `{ unchanged: true, snapshotSignature }`；前端遇到 unchanged 只能更新连接存活状态，不能 `setSnapshot` 或触发推荐/自动化派生，轮询调度也不能依赖 React 重新渲染续约，必须由独立 interval/loop 持续观察后续经营状态变化。前端必须让 `/snapshot` 成功返回后立即更新主快照和签名，不能等待 `/runtime-data` 完成，否则经营中页的特殊经营、普客订单和自动化会被运行时目录请求阻塞；`/runtime-data` 失败只影响推荐目录缓存。前端必须缓存最近一次完整运行时数据，但不要用 `/snapshot` 原始 JSON 文本相等来跳过快照状态更新，以免运行时目录恢复被遗漏。总日志开启时，Local API 会记录 `/snapshot` 请求诊断，包含客户端、known/current 签名短值、full/unchanged、responseBytes、specialActive 和 normalOrders，用于区分前端未请求、连错 API 实例和快照被前端丢弃。`RuntimeReflectionRecommendationStateProvider` 的存储数据只用 `RunTimeStorage.GenerateSaveData()` 生成的一份运行时存储快照，`recipes` 为空时不得发布空的可用料理集合；玩家等级、流行喜好/厌恶 Tag 和明星店开关继续用 `RunTimePlayerData` / `RunTimeDayScene` 轻量 getter 读取。运行时固定目录读取完成后缓存映射和静态目录快照，经营扫描和诊断只复用缓存，不在 `NightBusinessReflectionProvider.LoadContext()` 中重新构造目录。`performanceMs` 会记录 `refresh.business`、`refresh.runtime`、`snapshot.serialize`、`runtimeData.serialize`、`automation.collect`、`snapshot.publish` 等耗时，概览页和经营中页展示最高几项用于排查掉帧。经营扫描还会记录 `business.rare.*`、`business.normal.*`、`runtime.cookerSnapshot`、`mission.serveTargets` 等子项；普客订单快照有短 TTL 缓存，避免一次快照发布链路内重复枚举 `OrderController`、HUD 和 `GuestsManager`。
- 本地 API 快照生产必须通过统一脏域发布入口：场景、运行时目录、稀客经营、普客订单、特殊经营、自动化和任务变化只标记对应 dirty domain，由 `StewardOverlayController` 在 `Update()` 末尾统一节流、刷新和发布。不要在新增功能中直接散落调用快照发布；若需要立即反映场景切换或运行时 ready 变化，应使用强制 dirty 标记。总日志开启时可记录 `[snapshot]` 诊断，包含 dirty domain、发布/跳过结果、签名、普客/稀客订单数和特殊经营阶段，用于区分“后端未生产快照”和“前端未消费快照”。
- 前端订单推荐 worker 和页面推荐 worker 会按 `RecommendationDataSet` 语义签名缓存完整运行时目录。签名未变化时，后续请求只传业务 payload 和数据签名，不再重复把完整运行时料理、食材、酒水、客人和规则目录结构化克隆进 worker；签名变化、worker 重建或首次请求才重新发送完整数据集。伴随窗口收到完整 `RuntimeDataCatalog` 后只在连接 hook 的独立缓存中保留一份，并从主 `snapshot` state 剥离完整目录，避免每轮快照和非当前页面 props 链路继续持有大对象。顶层工作台只挂载当前 active tab 的重型页面内容，页面推荐 worker 在 payload 为空时必须 terminate 并清空数据签名。该协议是自动化开启后降低 Mod 窗口内存和 WebView 卡顿的关键路径，新增 worker 推荐入口时要复用同一模式。
- 前端轮询完整快照时，只有在快照已经写入 React state，且所需 `/runtime-data` 已成功缓存或无需刷新时，才能推进 `knownSignature`。运行时目录读取失败不能阻断 `snapshot` 应用，也不能提前把 `snapshotSignature` 记录为已消费；否则后端会持续返回 `unchanged`，经营中页会保持空状态，直到页签切换等偶然重算才恢复。
- 普客订单被动快照缓存约 1 秒；常规路径先读取 live `OrderController` / HUD 可见订单，再合并仍匹配 live 订单 key 或桌位/料理/酒水槽位的 `NormalOrderRuntimeCapture` 控制器绑定。捕获缓存不再单独证明订单仍存在，已不可见的捕获项必须剔除，避免经营中页残留旧订单；捕获为空且 Hook 已安装、捕获版本未变化时复用上一次空结果，捕获不可用时才进入 `normalOrderMode=reflectionBootstrap` 启动扫描。`NormalOrderRuntimeCapture` 需要同时覆盖 `GuestGroupController.PushToOrder` 和 `GuestsManager.SetManualControllerOrderInternal`；启动扫描和自动化匹配还要枚举 `NightSceneDirector.controlledGuest`，用于怪诞料理三阶段最终 BOSS 这类手动控制普通订单。`NormalOrderRuntimeCapture` 的 `ChangeVersion` 变化后只刷新 `NormalBusinessContext`，不得调用完整 `RefreshBusinessContext(force: true)` 重扫稀客经营上下文。pending 出锅直送只在存在待办时轮询，离开夜间场景时由场景清理或有 pending 的非夜间检查释放。
- 普客订单快照读取门禁是当前处于夜间经营场景，而不是 `NightBusinessContext` 已经稳定。怪诞料理等特殊经营中，HUD 普客订单可能早于稀客经营上下文或经营场景标签稳定出现；只要 `Work` 场景和 `OrderController`/HUD 可读，就应允许 `NormalBusinessContext` 读取并进入本地 API 快照。非夜间场景仍必须清空普客快照和捕获缓存，避免旧订单残留。

- `任务` 页任务状态优先对 `RunTimeScheduler.trackingMissions` 中每条任务调用只读 `RunTimeScheduler.ParseActiveMissionData()`，映射为 `available`、`tracking`、`fulfilled`；读取时还要刷新 `TrackedMissionData.UpdateFinishStates()`，并用 `HasFulfilled/get_HasFulfilled` 与 `conditionFinishStates` 全 true 兜底确认 `fulfilled`，避免可完成任务因 tuple/枚举读取失败继续显示为进行中。已完成任务不再作为筛选分类展示，默认筛选显示可接取和可完成。NPC 交谈任务通过 `RunTimeScheduler.GetAvailableInteractMissionForCharacter()` 读取，但该接口返回“可交互推进”的任务，已存在于 `trackingMissions` 的 label 应归为可完成而不是可接取。真正未接取任务还需要只读扫描 `RunTimeScheduler.scheduledEvents` 当前修正日和 `-1` 桶，使用 `DataBaseScheduler.RefEvent()` 解析 `EventNode.postMissions` / `postMissionsAfterPerformance`；只接受 `OnTalkWithCharacter` 或通过 `CheckCharacterInteractEvent()` 门控的 `KizunaCheckPoint` 事件，且过滤已开始/已完成 label。候选 NPC 来源还需要从 `DataBaseDay` 的 NPC 映射表补齐。场景调查任务通过 `RunTimeDayScene.trackedInteradctables`、`MissionInteractConditionComponent` 与 `trackingMissions` 中的 `InspectInteractable` 条件读取；候选来源会写入分来源诊断。`HaveMissionStarted()` 不能用于过滤已追踪任务页条目，因为它等价于检查任务是否在 `trackingMissions` 中。经营投喂任务读取 `ServeInWork` 条件、mission `reciever` 和 `RunTimeScheduler.ContainsSpecialNPCServeInWorkMission()`，只用于任务页展示和经营中任务料理推荐置顶，不得调用 `TryTriggerServeMission()`。NPC 所在场景优先从 `RunTimeDayScene.trackedNPCs` 的 mapLabel 反查，并通过 `DaySceneLanguage.GetMapLanguageData()` 本地化；tracked 位置缺失时用 `DataBaseDay.RefNPC()` 的 `possibleDestinations` 解析可能场景兜底。NPC 名称优先用 `DaySceneLanguage.RefDaySceneName()`，再回退到 `SchedulerNode.Character.GetLanguageData()`；读取失败不回退静态全任务。
- 经营中页使用页内 `推荐` / `自动化` / `诊断` 视图分区：默认 `推荐` 视图用 `稀客` / `普客` 二级页签承载订单列表和推荐结果；`自动化` 视图集中自动化资源、稀客/普客自动化状态、厨具预约和订单详情；`诊断` 视图仅在显示调试信息时出现，承载特殊经营订单、扫描来源、性能和置顶状态。普客订单常规可见性来源是 `OrderController.GetShowInUIOrders()` 和 HUD `OrderingElement.ActiveOrder`，可执行控制器绑定来源是 `NormalOrderRuntimeCapture` 或启动扫描控制器；live 订单和捕获缓存按 `orderKey` 优先、桌号/料理/酒水槽位次之合并。普客订单读取不能要求 `Place` / `PlaceLabel` 必须存在，游戏在 `Work` 场景且 `GuestsManager` 已初始化时可能已经有订单但经营场景标签仍为空。普客 `NormalOrder` 应优先读取 `foodRequest` / `beverageRequest`，并兜底调用 `get_RequestFood()` / `get_RequestBeverage()` 和 `get_id`；普客 `GuestBase` ID 要按普客表解析，不要在诊断里强行显示稀客映射。读取文本时必须过滤 `GameData.CoreLanguage.LanguageBase` 等运行时类型名，普客订单 key 优先使用运行时订单对象指针 `orderKey`，不要只靠桌号/料理/酒水粗匹配。普客自动化必须依赖 `GuestGroupController.PushToOrder`、`SetManualControllerOrderInternal` 捕获或当前控制器扫描确认的可执行控制器；HUD / `OrderController` 只表示订单可见，不能单独用于送达、恢复耐心或 `EvaluateOrder()`，也不要为了性能删除 `NormalOrderRuntimeCapture` 绑定链路。普客自动化入口需要实验性自动化总开关和普客子开关同时开启；开启后不再保留手动处理按钮，伴随窗口会按首次出现时间稳定排序并发轮询未满足普客订单，并发上限来自设置页参数。普客轮询使用独立快节拍，订单 key、料理、酒水或送达状态变化时短防抖合并触发一次复查。已开始制作、等待 pending 直送或正在送达/评价的订单不得继续占用新的开锅调度名额；长时间未直接送达时必须允许恢复调度。稀客和普客开锅请求会共用伴随窗口本轮厨具预约表，预约容量按当前已摆放厨具快照计算；同类厨具容量不足时优先保留普客待处理订单，稀客料理开锅等待不计作失败。每笔普客订单独立记录送酒、开锅、送料理、完成订单和暂停状态；C# pending 直送优先绑定 `orderKey`，避免同桌同料理或桌位复用时串单；如果游戏重建普客订单对象导致旧 key 失效，只有桌号、料理和酒水仍一致时才允许重匹配当前订单继续直送；非临时错误只暂停对应订单，不影响稀客自动化或其他普客订单。料理完成后必须直接送达目标订单，不再写入 `IzakayaConfigure.StoreFood()`、扫描 `StoredFoods` 或占用送餐盘作为自动化中转；自动送达酒水开启时创建酒水、完成送达提交后再扣库存，自动完成订单开启且 `get_IsFullfilled()` 为真时才调用 `EvaluateOrder()`。`get_IsFullfilled()` 只代表订单已满足并可评价，不代表评价已完成；普客终态应读取 `HasEvaluated` 或等待订单从快照消失。同一订单已有 pending 料理时必须等待，不能重复占用同类厨具制作。
- 自动化部分送达后调用 `GuestGroupController.AddPatient` 恢复顾客耐心前，必须读取 `CurrentPatient` / `MaxPatient` 并裁剪到剩余空间；原生 `AddPatient` 不裁剪上限，超出后会让 `GuestTableDisplayer.UpdatePatient` 用大于 100 的 progress 索引耐心条贴图数组。若检测到当前值已超过上限，只能用 `SetPatient(MaxPatient)` 校正，不得继续追加恢复值。
- 经营中页的动态区域应保持固定入口：推荐、自动化、诊断三类内容不得混回默认视图；对应视图在暂无数据时也显示紧凑空状态，避免稀客入场、点单或自动化诊断刷新时整块内容突然插入导致页面跳动。
- 普客页和稀客页的推荐候选搜索、排序、自定义料理候选合并与展示行派生必须通过页面推荐 Worker 执行；页面组件只维护选择状态、收藏状态和结果渲染。隐藏页不得继续投递页面推荐计算；完整经营中订单推荐 Worker 只允许在经营中页面、稀客专注模式、游戏界面置顶、厨具高亮或稀客自动化实际需要推荐候选时后台运行，不能因自动化总开关或普客自动化单独开启就在所有页面持续计算。非经营中可见页若只是为自动化、置顶或厨具高亮保留推荐结果，必须使用后台轻量用途：限制展示行、限制执行方案和候选缓存容量，并按语义签名去重 worker 回包，避免跨线程反复传递完整推荐结果造成窗口卡顿或内存膨胀。经营中页的普客订单详情投影同样走经营中订单推荐 Worker，并且只在 `经营中 -> 推荐 -> 普客` 可见时通过独立 hook 请求按需计算；自动化和诊断视图不得为了展示详情同步调用 `selectSpecialBusinessNormalExecutionTarget()`，普客详情请求也不得影响稀客订单推荐和自动化使用的 `pending/isCurrent` 门禁。特殊经营普客自动化的执行目标选择也必须由 Worker 预计算，自动化 tick 只能按订单 key 消费结果，不能在主线程逐单同步跑完整目标搜索。主推荐请求、普客详情请求和普客自动化目标请求都必须用语义签名稳定输入，订单推荐 hook 必须保留 active + latest queued 请求模型，快照连续刷新时只排队最新请求，避免 worker 结果被持续判定为过期而让页面长期停留在“计算中”。
- 经营中页的“当前点单推荐”标题右侧承载稀客订单专注模式入口，以及料理/酒水推荐显示数量设置；这两个数量设置与稀客专注模式内部共用同一组 localStorage 配置，不要拆成两套。稀客专注模式默认精简开关放在 `设置 -> 推荐`，不放在窗口分栏。
- `稀客` 页下拉选项不再按当前存档已解锁稀客过滤；只按经营场景、可读中文名称和可用点单 Tag 过滤。后端不再发布 `availableRareCustomerIds`，除非找到游戏内明确稳定的已解锁字段，否则不要恢复该过滤。
- 普客 pending 料理完成后，必须重新定位目标运行时订单并直接执行统一送达提交。不能因为订单对象的 `ServFood` / `ServedFoodInAir` 短暂非空就清理厨具并丢弃成品；若订单或成品对象暂时不可读，应保留 pending 等待下一轮，超过超时后释放 pending 并留下诊断。
- 普客订单显示“已开始制作”后如果长时间没有进入直接送达状态，伴随窗口必须允许该订单重新确认后端 pending 待直送任务；后端仍报告已在制作或等待直送时，前端刷新等待时间并清理旧回退计数，不得直接暂停。C# pending 直送不能因为一次 `Phase=0` 或 IL2CPP 短暂读取异常就立即移除任务。短暂失败应继续重试，超过超时再输出诊断并释放 pending，避免普客/稀客同时自动化抢占厨具后出现永久堆积。
- 自动化状态机只把实际送酒、开锅、单项送达提交和触发评价视为真实进展；“选择订单”“匹配订单”不能刷新进展时间。稀客和普客料理、酒水都允许按阶段分别直接送达，同步顾客桌面显示和订单状态后，订单满足才触发评价。前端用 `hasServedFood/hasServedBeverage` 和后端结构化步骤码校准状态，避免重复送酒或重复开锅。稀客/普客目标料理长时间未直接送达时先重查 pending，pending 仍存在则继续等待，pending 消失才按配置回退或重新进入开锅调度，达到回退上限后才按对应订单类型暂停。若厨具、伙伴或 BUFF 让最终成品变成黑暗料理/非目标料理，C# pending 直送必须通过 `IzakayaConfigure.StoreFood()` 将该成品放入保温箱，并通过 `LocalApiSnapshot.automationEvents` 发布递增序号的 `cooking-mismatch-stored` 运行时事件；前端按事件序号一次性消费，优先用 `traceId` 匹配稀客/普客状态，双方缺失追踪标识时才退回订单 key、桌号、客人和目标料理匹配，清理本地准备/送达/完成态并立即回到确认料理阶段重新调度。不得用反射把错误成品虚空清理，也不得只写普通步骤码或日志让订单永久等待。C# 侧开锅、pending 直送和 pending 移除统一写入总日志的 automation channel，连续相同日志会合并为 `repeat` 摘要。日志页提供一键诊断包导出，zip 包含当前 snapshot 和总日志尾部，便于后续排查。
- 出锅直送 pending 的正常路径仍直接送达目标订单，不经过保温箱中转；当最终成品不匹配，或目标订单/可执行控制器连续不可达并达到自动释放阈值时，C# 会通过 `IzakayaConfigure.StoreFood()` 将成品放入保温箱，发布 `cooking-mismatch-stored` 运行时事件并释放 pending。保温箱写入失败时保留 pending 和厨具成品，避免虚空删除。
- `cooking-mismatch-stored` 运行时事件是 mismatch 回退计数的唯一来源，API 响应只清理准备态，不得把同一次出锅重复计数；目标切换、stale 恢复和 mismatch 计数达到 `autoMaxRollbacks` 时暂停对应订单，配置为 `0` 表示首次回退即暂停。成品 Tag 原始容器存在且每个 Tag 名均可解析时，空集合属于明确不匹配；容器或名称不可读时发布 `cooking-tags-unreadable-stored`，成品入保温箱后立即暂停，不继续消耗材料试错。
- 稀客自动化会在订单状态中锁定料理、加料、酒水和厨具；库存变化或推荐排序变化不会让同一订单中途切换目标。自动化锁定排序后的统一推荐候选，若目标料理标注为“偏好备选”，状态里也要显示“偏好备选”。特殊经营的动态目标 Tag 是料理锁有效性的一部分：怪诞料理大赛等场景必须用挑战类型、订单角色、阶段和当前目标 Tag 构造签名，签名变化、旧目标不再命中当前 Tag，或旧组合已被实机判定失败时，前端应丢弃旧料理锁并切换到当前推荐中命中目标 Tag 的执行候选；怪诞二、三阶段候选还必须先满足原订单料理/酒水和最高评价估算。候选选择函数不得用旧 `state.recipeTarget` 覆盖当前推荐结果。料理出锅后 C# 必须按锁定目标直接送达当前订单，不再复用送餐盘堆积料理或可接受成品列表作为兜底。
- 稀客自动化诊断由前端按订单 key 展示当前候选订单状态，包括步骤、料理/酒水阶段、重试、回退和最近原因。订单级执行步骤保存在对应订单状态中，并在经营中页该订单条目下方的 `自动化详情` 折叠区展示；默认全部折叠，底部全局消息只保留连接、候选跳过、调度等全局状态，不再堆叠单笔订单详情。单笔 `重试` 只解除暂停并保留已完成阶段，单笔 `重置` 删除该订单本地状态并让下一轮重新判断；不得清空其他稀客、普客或全局自动化状态。
- 自动化运行状态属于热路径，不得把每轮 tick 的 busy、message、diagnostic 直接写入 `ModWorkbench` 顶层 React state。前端必须先写入 ref/状态机，只有经营中页面可见时才按语义签名把自动化详情发布给 React；非经营页保持自动化后台执行，但不能因自动化详情刷新导致整个工作台重渲染。普客订单签名变化应短防抖合并后触发复查，自动化动作后的前端快照刷新也应合并调度，避免动作密集时形成 “动作 -> 快照 -> 签名变化 -> 再动作” 的 UI 刷新环。特殊经营普客执行目标选择属于自动化热路径，必须按订单、runtime、特殊经营上下文、偏好和失败组合构造缓存 key，并限制缓存容量；前端自动化调度只能消费 Worker 预计算结果，厨具预约和实际执行应复用同一入口，不能在同一轮为同一订单重复跑完整推荐搜索。
- 稀客自动化完成订单时，C# 必须同时返回缺料理和缺酒水诊断；前端回退料理时要同步失效酒水缓存，下一轮重新校验送酒。稀客料理出锅直送 pending 需要按目标料理 ID 去重，厨具冻结或 Debuff 期间只等待已有 pending，不得重复消耗材料开同一道目标料理。
- 经营中页的自动化资源视图只做可视化：厨具预约来自已摆放厨具容量、真实可进入本轮开锅调度的普客订单和稀客候选订单；特殊经营普客必须复用 Worker 预计算的执行目标结果，预计差评、目标不一致或回调链不完整等 blocked 订单只显示为未占用厨具原因，不计入预约容量。直接送达状态仍以订单 `hasServedFood/hasServedBeverage` 与后端步骤为准。不要让该视图替代真实预约表或后端送达状态。
- 运行时稀客 ID 归一化优先依赖游戏 `DataBaseCharacter.GetAllMappedGuests()` 固定映射和 `GetSpecialGuestsAndMappedGuests()` 完整运行时稀客表；运行时表按游戏语言名称和同族 `StringId` 建立自动别名，例如 `Yuyuko_Free -> Yuyuko`、`DLC4_Remilia -> Remilia`。同一轮游戏内曾成功解析的变体别名会暂存，避免后续短暂读到 `localResolved=0` 时丢失中文名和本地 ID。手工事件变体只作为兜底。本地缺失但运行时具备有效喜好 Tag 的稀客会合成为临时 `RuntimeRareCustomer`，供经营中订单推荐和伴随窗口稀客页使用；剧情 Intro/Parallel/Current、问号占位、隐藏图鉴、NeverCome、无喜好数据的角色不合成。带具体桌号的捕获订单只允许匹配同一桌活跃稀客；手动/事件型 Special 订单允许在 `ManualDesk` 或订单本身已确认 Special 的上下文里用 `GuestBase.Id` 解析稀客身份，并在运行时订单对象仍可引用且包含点单 Tag 时保留捕获订单，避免活跃稀客快照短暂解析失败导致订单一闪而过。
- 任务页提供稀客邀请列表，可在当前场景和全部日间场景之间切换，并支持按名称搜索、单独邀请或邀请全部。实现走游戏日间羁绊邀请链路：`current` 范围优先通过 `DayScene.SceneManager.CurrentActiveMapLabel`、`RunTimeDayScene.GetMapNPCs()`、`DaySceneMap.allCharacters` 和场景 `CharacterConditionComponent` 获取当前场景候选，并用 `DataBaseDay` 目的地兜底，再用 `RunTimeDayScene.RefTrackedNPCAvailability()` 判断当前范围内的运行时可见性；`all` 范围从 `DataBaseDay.GetAllNPCKeys()`、`AllMappedNPCsMapping`、`AllNPCsMapping` 或 `allNPCs` 读取全部日间 NPC 并解析所在地图，同时合并当前场景已读取到的候选。`all` 的全部静态候选不使用当前时间可见性作为硬过滤，因为该运行时入口本质上依赖 `TrackedNPC.ShouldShown(RemainActions)`。候选经 `DataBaseCharacter.RefSGuest()` 映射到 `SpecialGuest`；后端检查 `StatusTracker.HasNPCInvited()`、`RunTimeAlbum.GetOrGenerateSpecialNPCKizunaLevel()` 和当前等级成功邀请对话包。不满足条件的候选也要返回给前端显示原因，只禁用按钮；已邀请候选进入 `ExistingInvited` 并在任务页 `当前已邀请` 区块展示。符合条件后调用 `StatusTracker.RecordInvitedGuest()` 写入今晚邀请名单。列表、单独邀请和全部邀请必须共用同一套扫描和判定逻辑。羁绊等级筛选只限制页面显示和批量邀请执行范围；名称搜索只限制前端展示，不改变后端候选或邀请全部执行范围；列表查询应保留全量候选，避免筛选后丢失其他等级选项。该功能不调用会随机失败并消耗今日尝试次数的 `DaySceneChatSelectionPannel.InviteSpecGuest()`，也不使用 `HasTemptInvited()` 跳过候选，不直接刷客、不推进时间，也不再写 `Story.SpecialGuestControlled`。
- 任务列表、当前日间地图和稀客邀请读取必须使用独立的日间运行态判断：已加载存档、非非游戏页面、非夜间经营、非经营准备场景，并且 `DayScene.SceneManager`、`RunTimeDayScene` 或 `DaySceneMap` 等运行态对象已可用。进入夜间经营准备时，只允许用 `WorkPrepScenePannelRoot` 下活跃的 `IzakayaConfigPannelNew` 和准备面板 ready 信号阻断日间读取；不要用泛化的同名面板或残留对象判断，否则日间场景可能被误挡，导致任务和邀请为空。
- 运行时静态目录加载已经和玩家存档状态读取解耦。DataBase 静态目录完成后，快照 `runtimeLoaded` 即可让任务、邀请、普客和稀客基础数据可用；`recommendationState` 仍由 `RunTimeStorage` / `RunTimePlayerData` 成功读取后生成。经营准备面板触发 `OnPanelOpen` / `GoToSpecific` ready 后可以读取玩家运行态；面板未 ready 或主菜单/读档阶段必须跳过，避免 UI 初始化期间触碰 `GenerateSaveData()` 导致黑屏。
- `Main Scene` / `MainMenuPannel` 是主菜单，不是已加载存档的日间场景。代码必须显式把它识别为非游戏场景；不要依赖默认配置关键词自动生效，避免已有用户配置缺少 `main` 时在主菜单读取 DataBase/Language 静态目录。
- 日间任务和邀请读取不能依赖 `DaySceneSustainedPannel` 面板是否激活；空场景名、主菜单、夜间经营和经营准备仍必须阻断，但正常日间应让具体服务读取运行态并返回分来源诊断。
- 稀客订单捕获缓存只应长期保留仍匹配当前活跃稀客，或仍能从原运行时订单对象和控制器确认未完成的订单；无法确认仍在场的捕获项只给短暂宽限。离开夜间经营场景或清除运行时状态时要清空捕获缓存，避免跨天旧订单复活。若过时订单仍残留，经营中稀客订单行右侧删除按钮会调用 `/orders/rare/dismiss` 清理插件端缓存。
- 稀客自动化匹配运行时捕获订单时要兼容事件变体名称和不完整 Tag。强买强卖等变体可能显示 `Tewi_HardSell`，捕获到的 `foodTag` 可能为空，`beverageTag` 可能是“请给我甘的饮料”这类完整句子；同桌且对象仍有效的捕获订单应优先保留，Tag 匹配允许包含关系，不要只做完全相等。
- 从 `GuestGroupController.AllOrdersData` / `AllOrders` / `PeekOrders()` 读取稀客订单时，运行时对象可能以 `OrderBase` 视角返回；解析前必须先尝试强转到 `GuestsManager+SpecialOrder`，否则 `Type`、`SpecialGuests`、Tag 字段读取会失败，捕获订单会在短暂宽限后消失。
- 手动事件稀客订单不一定走普通 `PostGenerateOrder` 路径。运行时捕获需要覆盖 `GuestsManager.SetManualControllerOrderInternal`；`EvaulateManualOrder` 可按原生评价清理缓存，`EndDlc4SpecialManualOrder` 只能在当前订单已 `IsFullfilled` 时清理，不能把事件结束回调直接等同于订单完成。项目不再解析 Unity/BepInEx 控制台订单日志，稀客点单必须来自运行时订单对象、控制器、HUD/面板或运行时缓存。
- 总日志开启且经营数据扫描触发时，运行时固定数据会按主题写入总日志 section：`runtime-static-data` 映射稀客与 `aliasSource`、`runtime-tags` 标签和 TagRule、`runtime-database` 核心食材/酒水/料理表对照与读取方式、`runtime-guests` 普客/稀客/事件变体、`runtime-izakayas` 场景和客人池。游戏数据库未初始化时每 5 秒重试，section 中 `Complete: True` 表示读取成功。
- 运行时固定数据不只写总日志，也会构造成 `RuntimeDataCatalog` 并发布到 `/runtime-data`。`/snapshot` 只保留运行时目录元信息和签名，伴随窗口使用按签名缓存的运行时料理、食材、酒水、普客和稀客数据；`runtimeDataComplete=false` 时显示等待运行时数据。排查数据依赖时，先看概览页“推荐数据”是否显示“游戏运行时”，再开启总日志并检查对应 runtime section 的 `Complete: True`；导出的诊断包会同时包含 `snapshot/current-snapshot.json` 和 `snapshot/runtime-data.json`。
- 运行时料理基础食材是数量敏感序列，不是集合。`RuntimeDataCatalog.Recipes[].Ingredients` 和前端 `RecipeCatalogItem.ingredients` 必须保留重复项，例如同一材料需要两份时数组中出现两次；只有 tag、场景和 ID 集合可以去重。推荐加料槽位、基础成本、大份动态 tag 和自动化下单五格保护都依赖这个重复数量语义。
- 经营中页普客订单展示必须区分游戏原订单和推荐执行方案。`NormalBusinessOrder` 只表达游戏快照里的请求料理/酒水、桌位、顾客和状态；配方、厨具、加料、最终标签和特殊经营规则原因由前端 `normal-order-details` 投影层计算。普通经营执行方案等于原订单基础配方；怪诞料理、幽幽子挑战等特殊经营可以通过 `selectSpecialBusinessNormalExecutionTarget()` 生成实际执行方案。该投影属于候选搜索级别工作，只能在 worker 中按需计算，UI 组件只能消费独立详情请求返回的 `normalOrderDetailPlans` 结果；详情请求失败时页面应显示错误状态而不是永久“计算中”。普客详情 worker 输入必须由语义签名稳定，且详情卡片只响应本卡片实际展示的库存数量变化，避免快照轮询和大量普客订单导致 `经营中 -> 推荐 -> 普客` 页面持续重算或重绘。不要把这些执行方案反写成 C# 普客订单原始字段，也不要在 UI 里重复实现特殊经营规则。
- 特殊经营场景通过 `specialBusiness` 上下文读取 `NightSceneDirector.ChallengeMode`，并捕获已确认的 HUD 目标和进度：妖梦试炼目标营业额/符卡计数、尤魔双料理 Tag、恋单料理 Tag、恋 Tag 剩余比例与进度、幽幽子进度、DLC3 料理竞赛目标营业额。规则实现已模块化：C# 模块位于 `mods/bepinex/src/Save/SpecialBusiness/`，前端模块位于 `apps/companion/src/companion/domain/special-business/` 并通过 registry 接入推荐和自动化；前端规则构造拆在 `rules/`，普客执行目标按场景拆在 `normal-targets/`，怪诞料理运行时策略集中在 C# `WackyCookingCompetitionRuntimePolicy`。`RecommendationState` 不写入特殊目标；经营中推荐只应用已确认会影响评价的特殊经营规则：怪诞料理大赛第一阶段按高评价或当前目标 Tag 选择执行料理，第二阶段和三阶段分身必须满足原订单料理/酒水、最高评价和当前目标 Tag，小石本体/全力投食订单必须使用场上揭示的正面料理 Tag、厌恶料理 Tag、酒水 Tag，破防期仍先满足原订单料理/酒水，再按剩余目标分和当前预算规划投食总分，避免高分高价组合提前耗尽预算；幽幽子挑战第二阶段必须避开实际厌恶 Tag 并优先选择安全评价组合，第三阶段必须避开实际厌恶 Tag，剧情版和重修版 P3 boss 普客都保持原订单料理/酒水匹配，优先选择按等级合计可触发橙评/粉评的 `progress` 目标；若原订单组合只能达到绿评，则可生成 `refresh` 清理目标，用于调用原生评价清理订单但不承诺推进进度；低于绿评、含厌恶 Tag、目标不一致或回调链不完整时会停止自动送达和评价，喜好命中只作为同评价内排序参考，纯目标营业额/试炼目标金额只展示不改排序。小石破防期自动化目标和经营中推荐首项必须共享同一投食评分与预算规划入口，不能分别维护两套排序；幽幽子三阶段的普客执行目标、稀客 execution plan、推荐首项和自动化目标也必须共享同一幽幽子评分入口。
- 挑战/BOSS 订单可能以 `OrderBase/Normal` 或 `SpecialOrder` 形态出现；C# 侧必须通过统一特殊经营订单分类器标记归属，并按场景决定自动化策略。幽幽子挑战订单需要区分剧情版/重修版，允许通过原生订单对象送达，但三阶段评价前必须重新取得当前 live controller；如果游戏把重修版仍上报为 `Story_Yuyuko`，必须结合只读 `DifficultyMode` 和 `_50` / `_70` 评价回调证据发布有效挑战类型，不得 Harmony patch `DaySceneDirector.StartChallengeSession` / `StartWorkSceneChallengeSession` 这类带 `int?` 参数的 IL2CPP 启动入口。剧情版 `progress` 必须复用 `SetManualControllerOrderInternal` 捕获的 `onEvaluate` 调用 `EvaulateManualOrder`，并确认已送达目标、等级合计和剧情三阶段评分回调；重修版 `progress` 必须确认已送达目标、等级合计和 `_50` / `_70` 原生进度回调后调用游戏 `EvaluateOrder()`，不得走剧情手动评价路径；`refresh` 必须确认已送达成品精确等于请求目标与对应版本评价回调链，但不再因等级合计低于 Good 阻断。live `OrderBase` 读取不到客人字段时不得仅因 `guestId` 不可读拒绝，但 controller、当前版本所需评价 callback、送达目标、普客原订单不变量或清理/推进阈值不满足时必须暂停自动送达或自动评价，并记录请求、运行时匹配、执行模式、送达料理/酒水等级、原始/有效挑战类型、难度、callback 详情和阻断原因。
- 怪诞料理大赛分身允许进入经营自动化，但前端推荐阶段必须保持原订单料理/酒水，只在原料理上选择安全加料，并把当前怪诞目标 Tag 作为 hard condition，开锅前必须确认执行料理预测 Tag 命中当前怪诞 Tag 且 Tag 剩余比例未过低，C# pending 待办必须保存开锅时的怪诞阶段/目标 Tag 签名，出锅直送前先比较签名是否变化，再用成品 `Sellable.Tags` 校验当前 Tag；小石本体/全力投食订单破防前可按揭示规则拆分执行目标，允许使用仍能通过原订单料理/酒水和控制器校验的 `RuntimeCapture:ManualOrderSet`，送齐后调用通用 `EvaluateOrder()` 触发线索阶段评价；破防后必须满足原订单料理/酒水，且自动化匹配只接受带原生 Boss 评价回调的 live controller，订单生成回调只作为诊断信息；前端到本地 API 的请求必须携带 `specialBusinessRole=wacky-koishi-boss`，跨帧 pending 禁止把空目标 Tag 回退成当前怪诞轮换 Tag，破防后的料理和酒水送齐后仍必须通过 live controller 调用游戏原生 `EvaluateOrder()`，由 Boss `OverrideEvaluationCallback` 接管评分和进度更新；签名变化或 Tag 不满足时通过 `IzakayaConfigure.StoreFood()` 放入保温箱并发布带目标 Tag、实际成品 Tag、料理和加料组合的 `cooking-mismatch-stored` 事件，前端据此临时抑制同一失败组合并重新选择其他可执行方案；饕餮尤魔订单仍阻止标准自动化接管。普客特殊经营自动化必须拆分原订单匹配目标和实际执行目标，但怪诞二阶段和三阶段分身实际执行目标不得替换原点单料理/酒水；跨帧 pending 待办必须保存目标信息，不能在出锅时用执行料理反查原订单。自动化步骤和总日志记录 `rule=` 原因以及 match/execution 对照。已分析规则记录在 `docs/special-business-scenes-notes.md`；后续若要自动化其他 BOSS 订单，必须先用实机总日志验证原生移动、送达、评价和挑战结算副作用。
- 怪诞料理大赛第二阶段不是单纯目标 Tag 过滤：反编译确认挑战回调先要求最高评价，再判断成品是否含当前目标 Tag。前端 Phase2/Phase3 必须把原订单料理/酒水满足、最高评价估算和当前目标 Tag 同时作为硬条件；出锅实机判定失败的 `目标 Tag + foodId + recipeId + extraIngredientIds` 组合要被前端即时屏蔽，Mod 侧也保留最近失败缓存，防止同一目标 Tag 下重复开锅。
- 特殊经营激活时，游戏界面置顶和目标厨具高亮不能直接取展示推荐首项；必须按经营中当前排序扫描第一笔带 `executionPlans` 的稀客订单，并使用该执行计划的料理、加料、酒水和厨具目标。没有可执行计划时不发布特殊经营高亮目标，避免页面展示候选与自动化目标分叉。
- 稀客订单专注模式支持精简模式和料理/酒水显示数量配置；精简模式隐藏推荐料理 Tag 并压缩推荐面板间距，显示数量包含收藏置顶项。默认精简状态在 `设置 -> 推荐` 配置，进入专注模式后仍可临时切换并记忆。
- 实验性自动化由设置页总开关启用，经营中页按稀客订单和普客订单分组配置。稀客使用 `autoPrep*` 阶段配置，普客使用 `autoNormal*` 阶段配置；普客送酒、开始料理、送料理、完成订单和出错暂停互不复用。设置页参数控制稀客/普客并发、最大重试和最大回退，默认值为 `2`、`3`、`3`、`2`；稀客和普客完成订单都按单笔订单 readiness 独立推进，并优先处理已满足料理和酒水的订单，但本地 API 调用仍串行执行。开启自动开始料理后固定尝试完成原生 QTE 奖励结算，不再提供跳过或完成 QTE 的配置开关；该流程不会打开游戏音游面板，失败时只显示诊断并继续料理流程。稀客和普客的酒水、目标料理都通过统一运行时送达 helper 直接送至订单，不再经过送餐盘、保温箱或游戏料理暂存容器作为自动化中转；只有非目标/黑暗料理出锅，或出锅后目标订单/可执行控制器连续不可达时，才作为恢复动作写入游戏保温箱。普客自动化需要开启“启用普客处理”且至少开启一个实际阶段；临时失败应继续等待并重试，非临时失败才按对应订单类型配置暂停。稀客与普客暂停状态不能共用，普客内部也要按订单 key 隔离暂停。

## 推荐排序口径

- 经营中/稀客推荐排序可由伴随窗口 `设置` 页的任务料理、收藏料理、收藏酒水置顶开关、自定义推荐料理单条置顶和推荐权重共同控制。硬过滤后先应用置顶规则，再进入权重排序；默认均衡预设综合稀客偏好、厌恶风险、加料数量、资源压力、成本、利润、酒水库存和当前厨具可做等目标。
- 当前推荐权重项包含料理偏好命中、酒水偏好命中、减少厌恶标签、减少加料数量、少用低库存食材、降低食材成本、提高预计利润、优先酒水库存和当前厨具可做。资源压力优先惩罚低库存材料，并对额外加料加权；不要再使用“总成本越高越靠前”作为收益判断。任务料理、收藏料理和收藏酒水都不是权重项，只能通过对应置顶开关控制。
- 稀客和经营中主推荐使用统一料理/酒水列表；满足当前点单料理 Tag / 酒水 Tag 的结果优先，不满足点单但命中稀客喜好的结果直接进入同一列表并标注为“偏好备选”。经营中页和稀客订单专注模式按用户设置的显示数量截取统一列表，不再维护独立喜好备选数组。展示行必须从完整排序候选池派生，不能受自动化执行候选上限裁剪影响。料理推荐优先 3 分以上候选，但低于 3 分且满足点单的料理仍要作为兜底显示。
- `排除缺失厨具` 开启且已读取厨具快照时，统一推荐列表会隐藏当前场景未摆放对应厨具的料理；厨具类型 1-5 映射为煮锅、烧烤架、油锅、蒸锅、料理台。
- 稀客收藏保存在 `BepInEx/config/MystiaStewardCompanion/favorites.json`，按 `customerId + foodTag` 收藏料理方案（含加料 ID），按 `customerId + beverageTag` 收藏酒水。自定义推荐料理保存在 `BepInEx/config/MystiaStewardCompanion/custom-recipes.json`，按 `customerId + foodTag/null + foodId + extraIngredientIds` 生效，其中 `foodTag=null` 表示该稀客全部点单料理 Tag；顶层 `enabled` 是整个功能的门禁，关闭不改写单条状态。管理页可按稀客或基础料理派生分组，页面/分组/单条 flags 更新使用同一原子端点，推荐优先级只在同一稀客内移动。旧 `favorites.source=manual` 仅在 `v1.1.x` 作为一次性迁移输入：Local API 启动阶段先原子写入自定义料理，再删除旧收藏条目，使后续读取端点保持只读；该迁移计划在 `v1.2.0` 删除，不再作为推荐路径。收藏料理置顶、收藏酒水置顶、自定义推荐置顶和自动化收藏限定都不绕过解锁、库存、预算、排除项和缺失厨具过滤。
- `任务料理置顶` 使用当前稀客已接取的 `ServeInWork` 投喂任务目标料理。目标料理通过硬过滤后可在经营中推荐中置顶并显示 `任务` 标识；该功能只影响推荐顺序和自动化选择，不自动推进任务状态。
- 经营中稀客推荐会根据当前稀客资金构造预算上下文。预算策略支持阻止超预算、仅提示和忽略预算；订单级 `isFreeOrder=true` 时不应用付款预算阻止，非免费订单继续按当前预算策略判断。排除材料会同时过滤基础配方和加料，排除酒水只过滤酒水候选。排除项下拉的库存显示来自 `RuntimeSets`，排序方式只影响设置页选项展示，不进入推荐缓存签名。预算、免费订单状态、排除项、缺失厨具和同基础料理展示数量都必须进入推荐缓存签名，避免设置变化后继续显示旧结果。
- `同基础料理显示` 默认值为 1。同一基础料理存在多个加料变体时，稀客页和经营中页只展示当前排序最靠前的指定数量；收藏匹配仍按基础料理和加料精确匹配，自动化从独立执行候选构造目标，不能只依赖裁剪后的 UI 行。候选构建器应返回完整排序候选，执行候选上限只在自动化/plan 构造阶段应用。
- 经营中订单显示顺序默认是首次出现时间升序；切换为稀客分组时，同组内仍按首次出现时间升序。新订单不应在点单顺序模式下插到已有订单前面；自动化和置顶目标必须使用页面同一排序结果。
- 推荐行需要显示库存数量；料理行需要显示厨具、基础配方和加料，并对这些定位信息做高亮。
