# 运行时游戏图像资源

更新日期：2026-10-23

## 生命周期

客户端资源声明和发布包不包含提取的游戏 PNG。首次没有有效缓存时，Controller 等待完整运行时目录，从已加载的精确游戏目录提取；每帧最多一个实体，完成后停止提取，不依赖客户端连接或自动刷新开关。原生目录尚未就绪时每五秒重试；若仅等待纯托管后台指纹任务，完成后的下一次主线程 Tick 即继续，不额外等待五秒。未承诺固定初始化时长；单项提取持续未就绪超过三十秒则失败。

后续启动可在主菜单复用缓存：`RuntimeGameMediaStartupProbe` 只读取游戏已完成依赖加载、Steam 已初始化、DLC 缓存集合已确认（含 CORE）的状态，不主动调用会懒初始化的 DLC getter；后台结合游戏/Unity/算法版本、资源索引 SHA256、DLC 集合及精确 bundle 文件名/长度/修改时间校验私有 `startup.json` 凭据、原清单和全部 PNG。大体积 bundle 元数据不是内容哈希，不每次全读数 GB；正常更新由资源索引摘要识别，手动改包可显式重读。证据未知时低频只读等待，超时退回原目录流程；整代磁盘校验每次启动最多一次，不在未读档期间循环校验。

旧缓存无启动凭据时需进入存档完成一次完整核验：真实目录、计划与现有图片均通过后，在原代补建凭据，不重新提取 PNG。以后游戏版本、DLC 与资源身份未变化且缓存完整时，无需先读档即可在主菜单校验复用；每次启动仍检查资源身份、缓存清单及全部图片文件。实际目录到来后再次精确比较完整计划（含配方食材顺序及重复项），相同保持 ready，不重新插入门禁；变化立即撤销旧代。提前就绪只恢复图片服务，不能替代业务目录、场景、快照或执行许可。

源指纹由 `StreamingAssets/aa/catalog.bundle` 的 SHA256、Unity 版本、游戏应用版本及提取算法版本组成，不递归计算全部资源 bundle 的摘要。主线程只取得路径和版本字符串，文件摘要、缓存校验及提交在后台执行。Unity Sprite、纹理与 IL2CPP wrapper 仅在主线程的一次调用内使用，不跨帧或线程保存；跨帧只保留托管目录、精确 ID、状态和已编码字节。

`waiting` 表示首次、启动证据不足或人工重读等待目录，`verifying` 表示正在核验缓存候选，`extracting` 才表示实际提取或保存新代，`ready` 表示完整代次已经就绪。缓存候选仅查询固定 `current.json` 存在性，不授予可读或执行权限。合法缺图记录在 `missing` 中并采用通用图标，不用其他实体图片替代。缓存位于插件的 `user-data/game-media`：启动时完整核验源指纹、目录身份、配方映射及全部 PNG；有效缓存从 `verifying` 直接进入 `ready`，代次和 PNG 不变。缓存缺失、损坏或来源/计划已变化时，等待真实目录就绪后重新提取；仅缺少启动凭据不等于 PNG 损坏。如果已经就绪后读取图片才发现缓存损坏，服务进入 `failed` 并要求重新读取，不会静默继续使用旧图。

人工重新读取限主设备，等待、核验或提取中的重复请求复用当前作业。重读会重新计算源指纹，并强制从当前已加载资源生成整代图片；即使指纹未变化也不会直接复用旧缓存。新代完整写入后原子发布，失败保留旧磁盘缓存，但不将失败作业显示为 `ready`。游戏更新后应先重启游戏，使新资源实际加载，再核验或重读；此功能不在运行中的游戏里热加载更新后的 bundle。

聚合日志的 `MSC-GAME-MEDIA v1` 只在作业转换时记录 `cache-check`、`cache-hit`、`cache-miss`、`forced-extract`、`complete` 或 `failed`，包含阶段、数量及安全代次，不记录路径或凭据。启动缓存未命中附固定原因码，区分缺少凭据、身份变化和内容校验失败。缓存命中不写 PNG 或清单；一次任务只产生有限条事件，诊断接收器失败不会改变资源状态。

## 身份与图像来源

- 六个独立命名空间：food、beverage、ingredient、cooker、rare-guest、normal-group；整数 ID 不按显示名称联结。
- 料理 ID 与配方 ID 为独立双键；配方食材按真实数组保留顺序和重复，标准厨具按枚举 ID。
- 物品读取当前语言目录的 Visual Sprite，使用精确顶点/三角形/UV，支持紧密及旋转图集。
- 图鉴头像依当前游戏 Native 与 `NoteBook_MainPannel` prefab 的像素头像组合：使用95×126矩形显示范围和 `OffsetRect(-1,+1)`，按 `TrimBack → MainSprite[1] → EyeSprite[1] → TrimFront` 合成；主体与眼睛使用 `SpriteOffsetInNoteBook`，饰品取明确索引0。稀客使用精确 ID 对应的默认像素皮肤，不再把全身立绘的 `faceInNoteBook` 字段当作头像。提取结果不包含图鉴背景，也未复刻遮罩图片本身的轮廓。
- 普客选择对应客群声明顺序的首个皮肤作为固定代表，不调用会消耗游戏 RNG 的随机形象方法，也不将其声称为现场某位客人的随机皮肤。
- 订单所在业务通道不决定头像种类。普通订单的 `guestImageKind` / `guestImageId` 来自主线程对订单客人及控制器客人的精确派生类型、唯一目录 ID 核验；复制稀客使用 `rare-guest`，确定普客使用 `normal-group`，冲突或未知不赋图。禁止按中文名、数字范围或运行时对象 ID 猜图，且不改变订单的执行身份。
- 输出为最长边不超过128的透明 PNG，小图不放大；离屏资源独占并在 `finally` 释放，恢复原渲染目标、矩阵和 sRGB 写入状态，不修改游戏原纹理。缺少精确图片引用时使用通用图标，身份冲突、几何异常或编码错误使整项作业失败。

## 认证协议与限制

| 路由 | 行为 |
| --- | --- |
| GET /game-media/status | phase、generation、completed、total、message、error |
| GET /game-media/manifest | ready 时提供 version:1、generation、sourceFingerprint、items、recipes、missing |
| GET /game-media/image?generation=…&key=food:1 | 精确当前代次的 image/png；失效代次拒绝 |
| POST /game-media/reload | 主设备及 authorityRevision 检查后登记重读；不在 HTTP 线程访问 Unity |

读取沿用 API 的 Token 鉴权；客户端同时发送已有 Client-ID 请求头。重读还要求已注册的当前主设备和精确 `authorityRevision`，Token 不进入 URL。单图256KiB、最多2048项、整代32MiB；路径仅从严格种类与整数 ID 推导，拒绝重解析路径与越界。PNG 长度、签名、尺寸及摘要在缓存和客户端读取时核验，宿主缓存还校验 PNG 分块 CRC。

初始化/核验/重读期间业务与人工游戏写入拒绝执行，旧队列同时绑定图片代次；实际自动化步骤也检查资源就绪并撤销租约。设备注册、连接修复、日志、更新和释放租约保持可用。客户端替换 Navigator 内容，先撤回图片与租约，再发一次重读请求；模糊写入结果只用 GET 确认，不能自动重复 POST。缓存核验、客户端清单同步、等待目录、实际提取及失败统一显示独立初始化界面，以对应状态说明当前工作；核验不冒充提取进度，也不先显示工作台页头再切换界面。完成前不挂载业务表单，完成后自动进入工作台；需要一次完整确认时明确提示进入存档。门禁解除不重放期间收到的手柄输入。

## 客户端显示与验证边界

`GameMediaController` 管理代次和下载，`GameMediaScope` 向 `EntityImage` 提供同步 Provider；最多四个真实在途请求。PNG 只缓存在客户端内存中，不写入 Windows 或 Android 的图片磁盘缓存。切换连接、资源代次或失败会撤回旧图及配方索引。100% 字号下标签20px、名称28px，图片随 TextScaler 同步放大；原订单、客群详情和菜单共用组件。

自定义配方编辑的候选、已选食材、基础材料与厨具，以及排除资源的候选与已选标签均使用相同精确 ID 入口。基础材料/厨具须通过 `foodId:recipeId` 当前依赖联结，保留重复材料；缺失依赖和历史未知 ID 显示通用图标，不按名称补图，也不隐藏原有移除操作。自动化详情只显示宿主确认的处理目标图片及来源，不以最新推荐替换已锁定目标。

数据“资源管理”默认显示全部分类，支持六类筛选与名称/编号搜索。搜索只匹配当前已验证的清单，切分类或资源刷新保留输入草稿，预览图片继续按可见项延迟加载；主设备可重读，手机和查看设备同步宿主进度。发布前需使用干净构建并检查 Windows ZIP 和 Android APK 不包含旧 `assets/game-media` 目录；仅删除源码和资产声明不能证明旧构建目录没有残留。运行时缓存属于 `user-data`，不应作为安装包载荷收集。

离线测试使用合成 PNG，预览显示明确合成标识。纯托管缓存/API、Dart 状态机、Flutter 组件和原生合成预览可覆盖协议与布局，但不能证明真实 Unity 的 Shader 可用性、UV 方向、透明边缘、图鉴裁剪效果或 `ReadPixels` 单帧耗时；这些结论须绑定具体游戏版本与实机证据，不能从构建或文档整理推定。每帧只处理一项不等于已经证明不会卡顿。游戏更新若改变精确类型、像素帧或图鉴布局，需要重新核对提取约定，不能由 ID 匹配成功推断画面仍然正确。
