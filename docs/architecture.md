# 项目架构

更新日期：2026-09-02

本文只描述长期稳定的组件边界和数据流。构建命令见[本地开发与构建](local-development.md)，具体运行时约束见对应专题文档。

## 组件

| 组件 | 目录 | 职责 |
| --- | --- | --- |
| BepInEx IL2CPP Mod | `mods/bepinex/` | 在 Unity 主线程边界读取游戏状态、维护运行时缓存、执行经过检查的游戏动作并提供本地 API |
| 伴随窗口前端 | `apps/companion/src/` | 展示运行态、运行推荐 Worker、管理设置与设备连接，不直接访问游戏对象 |
| Tauri 桌面/移动壳 | `apps/companion/src-tauri/` | 窗口与单实例控制、本地 TCP 代理、独立更新程序，以及 Windows/Android 平台接入 |
| 测试与审计 | `tests/`、`scripts/` | 固定协议、运行时订单标识、发布策略和 UI 行为，防止文档与实现边界不一致 |

## 主要数据流

```text
Unity / IL2CPP 运行环境
        │  Unity 主线程读取与经过检查的命令
        ▼
BepInEx 数据提供器与服务
        │  不可变托管快照
        ▼
回环/局域网本地 API ── Tauri TCP 代理 ── React 伴随窗口
        ▲                                         │
        └──── 经过鉴权的命令 / 控制权 ─────────────┘
```

- 游戏当前状态和所有游戏写操作只由 Mod 管理。前端不得通过静态表、UI 文本或计时器猜测游戏状态。
- 网络线程只读取托管快照或把命令排入 Unity 主线程；不得直接持有或修改 IL2CPP wrapper。
- `/snapshot` 发布频繁变化的轻量状态；完整游戏数据目录由 `/runtime-data` 按内容签名缓存。详见[游戏数据提供器](runtime-provider.md)。
- 订单捕获、自动化控制和游戏 UI 目标各有独立的轮次、修订号和控制权，不能用一个布尔状态代替。详见[订单捕获与生命周期](runtime-order-lifecycle.md)、[自动化运行时](automation-runtime.md)和[游戏 UI 集成](game-ui-integration.md)。

## 平台边界

- 游戏电脑必须运行 BepInEx Mod；伴随窗口可在同一台 Windows 电脑或局域网内另一台 Windows/Android 设备运行。
- 回环监听器始终存在，局域网监听器是额外能力。远端设备不能调用只允许游戏电脑执行的本机管理操作。
- 桌面专属能力包括托盘、窗口聚焦、鼠标穿透、单实例和游戏退出联动；Android 只承担 LAN 伴随客户端，不实现这些桌面行为。
- 独立更新程序只面向 Windows 10 1703 及以上；Android APK 和独立 Windows EXE 不参与 Mod ZIP 自动安装。

## 线程与状态所有权

- Unity 对象只能在已确认的主线程边界读取、修改、恢复或销毁。
- 跨线程只传递不可变的托管 DTO、签名、轮次、修订号、原生对象标识值或命令结果；不跨帧缓存仍与游戏对象绑定的 IL2CPP wrapper。
- 读不到状态、订单标识不唯一、集合结构发生变化或游戏调用结果不确定时一律拒绝继续。恢复必须来自下一次可信读取，不增加旧来源或猜测路径。
- React 页面只渲染领域层和 Worker 的结构化结果；热路径状态先进入专用 store/ref，再按语义签名发布，避免把每次轮询都提升到顶层组件。

## 判断依据

| 问题 | 判断依据 |
| --- | --- |
| 游戏类型、字段与方法语义 | 锁定的 metadata C#、BepInEx #783 interop、IDA/Hex-Rays 与实机日志交叉验证 |
| 当前料理、库存、角色、场景和标签 | 游戏数据目录与状态提供器 |
| 推荐候选与排序 | 前端推荐引擎及 Worker |
| 游戏动作是否允许 | Mod 内当前经营轮次、精确订单标识、生效配置版本和自动化控制权 |
| 发布版本与资产 | `main` 上的版本字段、正式工作流、清单/目录和不可变 GitHub Release |
| 逐条回归断言 | `tests/` 与 `scripts/` 中的 smoke/audit |
