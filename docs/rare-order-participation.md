# 稀客调度与订单参与

更新：2026-11-06。本文描述当前 C# 业务模块与 Flutter 客户端的实现；原始订单身份仍由[订单生命周期](runtime-order-lifecycle.md)维护，游戏效果由[游戏 UI 集成](game-ui-integration.md)维护。

## 用户操作与默认行为

经营页的“稀客调度”页签始终可见。内部使用公共 `ModuleSwitchRow` 保存共享开关；模块默认关闭，关闭时保留名单并卸载队列及名单编辑内容。开启后顶部固定放置默认收起的“调度设置”，将名单与等待条自动启用规则合并为一个折叠区。名单支持搜索添加、动态标签移除，并提供当前场景已确认到场稀客的快捷添加标签。现场客人按精确 `guestId` 去重，包含尚未点单者；读取不完整时空集不代表无人。

下方仅显示名单内稀客，默认展开首位，同时最多展开一位；轮询及订单增减保留当前展开项。每位稀客的“全部优先、全部排尾、全部暂停”位于名称右侧，窄屏/大字号使用有完整提示的同语义图标按钮。展开后按订单列表显示身份、需求与队列位置，单笔操作位于右侧。未到场或暂无订单的名单成员保留入口，操作禁用；折叠及页面筛选不改变整组 CAS 所需的全部当前订单。

- `rareGuestParticipationModuleEnabled` 为严格布尔值；`managedRareGuestIds` 是规范、升序、去重、非负且最多 512 项的客人 ID 集合。名单不是推荐白名单。
- 名单内每一笔新订单默认暂停；启用某位稀客的当前订单不会自动启用其下一笔订单。名单外订单自动参与。
- “排到队尾”将尚未启用的目标按首次观测次序追加。“优先启用”排到正在处理的工作之后，不中断现有工作；重复启用已经参与的订单不会重新排序。
- 稀客级按钮使用该客人完整的当前订单集合，单订单按钮只操作一笔精确身份。集合改变时整个请求冲突，不部分应用，也不自动重发。
- “暂停”只停止自动化与游戏辅助参与，不删除采集、推荐或订单显示。暂停订单仍在经营稀客页、外部专注与游戏内专注中显示，标题标注“调度暂停”；在调度页明确启用后才恢复参与。移出名单或关闭模块时，受名单管理的订单恢复自动参与并排到队尾。
- 主设备切换后，名单内当前订单全部恢复默认暂停。普通名单变更只影响生效名单差异。模块关闭或有效名单为空时，所有功能完整沿用普通时间顺序与原执行行为。

“等待条自动启用”位于“调度设置”内部，与名单通过分隔线区分，不再单独折叠。该共享规则默认关闭；开启后可选择1–100%的阈值（默认30%）及队首/队尾（默认队尾）。名单内暂停订单的实际剩余等待条**低于**阈值时启用；恰好等于阈值不触发。队首仍排在已开工料理之后，不打断制作；同批符合条件的订单按点单先后排列。每个订单生命周期只自动启用一次，之后手动再暂停就保持暂停；新一笔订单有独立机会。规则不要求开启自动做菜，手动制作也能使用恢复后的游戏辅助。

调度详情显示每单“等待 N%”。普客、稀客订单统一提供`patienceRemainingRatio`：0–1的剩余耐心比例，未知为null，不猜剩余秒数。该值对应游戏原生`CurrentPatient / MaxPatient`等待条，仅在精确订单生命周期、原生等待回调有效且订单未送齐时读取。离店、待评价、异常值或读取失败不沿用旧低值，也不触发自动启用。

暂停订单统一排在所有非暂停订单之后，包括普客；暂停组内保留点单先后。两个专注窗口采用相同规则，且暂停尾排优先于“稀客优先”。经营页签顺序为稀客、普客、专注、稀客调度、统计信息。

## 状态和安全边界

`RuntimeRareGuestParticipationState` 是唯一运行时队列。公开身份为经营轮次、`R-*` 追踪编号、订单生命周期序号和规范客人 ID。桌号、名称、现场角色 ID、列表下标均不作匹配条件。精确原生订单解析后，只能向同一公开身份单向补充 `RuntimeOrderBindingToken`，不能替换或跨轮次复用。

一次完整采集最多接受 512 笔当前订单，每场经营最多保留 4096 个已见身份用于防止 ABA 重用。只有明确标记 `OrdersReadComplete=true` 且无错误的完整 `NightBusinessContext` 才能结束消失订单；字段缺失、逐项解析跳过或未知采集状态都不视为完整；不完整采集保留上一份已确认状态。后台线程与跨帧状态只持有标量，不保存关联游戏对象的 IL2CPP wrapper。

夜间订单读取成功后立即对齐参与队列，快照发布时再幂等复核。不能只在节流后的HTTP快照发布时更新队列，否则完成上一单后，下一帧可能比较新的订单集合与旧参与集合而误拒绝。对齐复用刚读取的托管数据，不额外扫描游戏；严格身份、代次、完整性、CAS与人工参与状态仍受保护。

优先启用只保护已绑定的活动料理任务。游戏辅助的多订单高亮是被动展示，不代表对应订单都已开工，也不占用自动化并发或厨具；不能把全部高亮订单当作队列锚点。活动任务复制在料理锁内完成，释放后再按同一调度快照分类，避免反向锁序；旧缓存中已暂停的任务不充当锚点。未知、重复或跨轮次绑定拒绝整个优先操作。

特殊经营中已有的安全优先级仍先于调度队列。队首暂时缺料或缺厨具时，计划器继续考察后续可执行订单，不为等待订单凭空保留资源。

## API 与投影

人工队列写入口为 `POST /orders/rare/participation`。请求必须来自当前主设备，携带与请求头一致的 `expectedAuthorityRevision`，以及正数 `expectedBusinessGeneration`、`expectedParticipationRevision`。

自动启用策略与名单共用profile schema10：`rareGuestParticipationAutoResumeEnabled`、`rareGuestParticipationAutoResumeThresholdPercent`、`rareGuestParticipationAutoResumePosition`。v1–v9严格验证原字段和哈希后补false/30/tail；保留已有设置并要求新的持久化确认，不兼容旧客户端在线写入。自动判定只在游戏主线程本次等待条采样、完整订单对账后进行：检查有效已确认主配置、主设备在线、经营及资源就绪、精确完整身份与已开工保护锚点。配置切换锁忙碌时跳过本次，不阻塞游戏，也不消费一次机会。客户端只编辑规则，不执行阈值算法。

`action` 为 `pause`、`enable-tail` 或 `enable-front`。`target` 严格使用以下二选一字段：

- 单笔：`type: order`、`order`（完整公开身份）。
- 整组：`type: guest`、`guestId`、`expectedCurrentOrders`（该客人完整身份集合）。

服务端先推进自动化命令轮次，撤销尚未开始的旧排队命令，再执行队列 CAS。请求失败不允许旧命令重新获得许可。暂停成功后立即精确移除对应稀客游戏目标，普客与其他稀客目标保留。`/orders/rare/dismiss` 不属于调度契约。

`snapshot.rareGuestParticipation` 发布 `active`、`ready`、`businessGeneration`、`participationRevision`、`managedGuestIds`、`entries` 和 `displayOrderKeys`。`entries` 包括参与与暂停订单，参与位置为连续正整数，暂停位置为 `null`。`displayOrderKeys` 是全部当前稀客的只读显示顺序，参与单按队列位置在前，暂停单按首次观测顺序在后：

- `null`：未启用调度排序，客户端沿用原现场集合与时间顺序。
- 空数组：没有可提供的显示排序；不能据此隐藏当前完整现场集合，也不授予执行许可。
- 精确身份数组：只有同代、完整且唯一覆盖当前稀客集合才用于排序；缺项、多余旧项或重复时沿用当前现场的原时间顺序，不实现另一套人工队列规则。

`RareOrderParticipationProjection` 在 C# 自动化及目标发布前核对生效名单、经营轮次、全部当前订单身份、无重复和连续队列位置；任一不完整使整份执行参与投影不可用。原推荐计算仍包含全部订单。Flutter服务/专注与游戏内专注只用显示键排序，不把暂停当作订单消失；专注先复用原跨普稀显示槽位，再将已确认暂停的订单统一排在所有非暂停订单之后；不改变原快照。暂停标签仅由同代、就绪且完整身份唯一匹配的managed/participating事实产生，不能根据姓名或单独guestId猜测。

## 暂停、恢复与终态

主线程准备/完成动作在当前精确订单许可内执行，并在同一许可锁内复核当前完整采集集合；保留旧队列不授予部分采集时的执行资格。已经取得许可的同步动作完整结束后，暂停才能提交；未开始的动作由命令轮次和许可共同拒绝。已经开锅的任务不退款、不清锅、不重复开锅；暂停期间不自动收取、送达或评价，有效超时钟暂停，恢复后从未提交的下一阶段继续。

前置准入发现读取暂不完整（`participation-source-incomplete`）、名单未同步（`participation-profile-not-aligned`）或完整订单集合尚未对齐（`participation-orders-not-aligned`）时，尚未进入Prepare/Complete，返回`waiting/participation`，至少等待500ms后由当前完整投影重新计划。它不消耗失败或回退次数、不清除已开锅任务和送达事实，也不显示要求手动重试的永久暂停。编排器仅接受上述精确等待契约且无副作用或人工屏障证据的响应，释放此次未执行请求的计划预约，不立即续接旧命令。手动暂停、错误身份、未知提交和人工确认保持原有阻断规则。

终态回执先于调度与控制权检查：未由 Mod 提交送达的订单若已经有同经营轮次、原生订单/控制器和生命周期的 `Evaluated` 或 `Removed` 记录，立即退休旧料理任务并释放逻辑厨具预约。保留锅内料理与厨具现场，不送达、不评价、不入箱、不复位。已提交送达的事务仍完成其独立清理；评价阶段先处理已确认终态，仅仍需原生动作时申请当前许可。旧生命周期的终态不得结束新订单。

## 验证入口

- `tests/runtime-rare-guest-participation`：完整集合、默认暂停、整组/单笔 CAS、非抢占优先、权限串行、主设备重置、ABA、不可变与上限、未送达终态、逻辑预约释放及长时间暂停后的有效计时恢复。
- `tests/csharp-automation`：生产编排器的暂停过滤、恢复、损坏/缺失快照拒绝、关闭模块及空名单回归。
- `tests/night-business-lifecycle`：经营结束与清理边界。
- `tests/flutter-contracts/bin/verify.dart --unit-only`：服务端顺序、专注槽位、不变输入与坏身份拒绝。
- `apps/companion-flutter/test/rare_guest_scheduling_test.dart`：390/544 宽、100%/150% 字号、整组和单笔请求、查看设备禁写、关闭模块保留名单。
- `tests/flutter-contracts/host` 的 `--snapshot-signature` / `--participation-admission`：调用生产快照签名及主线程准入，验证完整性单独变化可发布、部分集合拒绝与许可释放、模块关闭不改变原行为。
- 同一宿主的 `--order-patience` / `--rare-patience-auto-resume`：验证实际等待条读取契约、未知值与生命周期隔离、严格低于阈值、同一生命周期一次自动启用、已开工保护以及主设备/配置切换边界。
- 同一宿主的 `--rare-order-display`：验证暂停订单仍完整显示、统一尾排和坏显示键降级，不把展示队列当执行许可。
- `tests/automation-cooking-job`：终态优先与料理事务边界；完整 Harmony 探针使用[验证指南](validation-guide.md)中的锁定 Docker 入口。普通 Windows 执行缺少其指定 RuntimeDetour 时不能计作完整通过。

以上是隔离测试，不替代真实经营场景验证。真实游戏复核应覆盖开锅前后暂停、玩家自行完成订单、同客人多订单、主设备切换、8笔现场订单中最多6笔辅助目标与优先启用并存，以及缺料队首不阻塞后续订单。等待条规则另检查阈值相等时不触发、低于时启用、已自动启用后手动再暂停不重复恢复。
