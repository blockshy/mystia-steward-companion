# mystia-steward-companion

**mystia-steward-companion** 是面向《东方夜雀食堂》的 BepInEx IL2CPP Mod。它读取游戏当前运行时数据，并通过 Windows 或 Android 伴随窗口提供普客、稀客和夜间经营推荐。

项目由游戏内 Mod 读取运行时数据，并通过本地 API 提供给伴随窗口展示和操作。同机 Windows 客户端使用回环地址，其他 Windows 或 Android 设备可在可信局域网内连接。

## 功能概览

### 实时数据与推荐

- 实时读取已解锁料理、酒水、食材、库存、流行标签、明星店状态和当前经营场景。
- 普客页按当前地区推荐料理与酒水。
- 稀客页按候选稀客和点单 tag 推荐料理、加料与酒水，可在设置页调整推荐排序规则和同基础料理展示数量。
- 经营中页自动检测当前稀客和普客订单，并用 `推荐` / `自动化` / `诊断` 视图分开展示订单推荐、自动化状态和排查信息；普客订单会显示原订单、实际料理/酒水方案、厨具、配方、加料和标签。
- 经营中订单可按点单顺序或稀客分组排列；偏好命中但不满足点单的候选会直接进入同一推荐列表，并以喜好备选标识区分。
- 支持收藏稀客常用料理方案和酒水；也可在 `自定义推荐料理` 页为指定稀客配置固定料理、加料、全部点单或指定点单 tag，并通过功能总开关、稀客/基础料理分组和页面级/分组级批量命令统一管理启用与推荐置顶状态。

### 任务与稀客邀请

- `任务` 一级页包含 `任务列表` 和 `稀客邀请` 两个分栏。任务列表合并显示当前可接取任务与已接取且仍活动的任务，并使用 `全部`、`可接取`、`可完成`、`进行中`、`待确认` 页签切换分类和显示数量。每项任务还会显示任务定义关联的角色和该角色静态配置的相关场景；相关场景表示可能出现地点，不表示角色此刻实时所在位置。读档任务会在任务系统初始化完成后确认一次游戏原生条件状态；新接取任务会在创建完成后确认初始状态，之后只跟随游戏自身的任务刷新。读取链不完整时会显示明确状态，技术原因写入日志和诊断包，不会把不确定状态伪装成空列表或已完成。
- 首版可接取列表只发布已经过接取前后实机闭环验证的羁绊检查点任务：游戏日间运行态稳定时，Mod 在每次列表请求中通过 Unity 主线程重新读取当前日和永久调度事件，并严格校验任务前置节点、活动状态、循环属性、完成历史及任务/日间/稀客映射代际。Mod 不会为了显示列表而触发事件、接取或完成任务、领取奖励，普通角色对话触发的其他可接任务暂不进入列表。
- 可接取列表仅用于任务页展示，不参与任务料理置顶、自动化、游戏界面置顶、列表高亮或厨具高亮；任务实际接取后，既有的活动任务与任务料理链才按各自严格条件生效。
- 稀客邀请分栏在日间运行态就绪后自动读取当前场景或全部场景候选；首次进入、切换范围、换图、日间场景重新初始化或重连时会重新读取，也可手动强制刷新。游戏暂时无法提供日间运行态时，页面会按 0.5、1、2、4 秒有限重试，之后显示具体原因并等待手动刷新或场景状态变化，不会把读取失败显示成空列表。候选列表读取不会刷新 NPC 或生成羁绊状态。
- 可邀请项支持单独邀请或一次邀请全部，不满足羁绊或已邀请的项会显示原因并禁用按钮；当前已邀请稀客会单独汇总显示。点击邀请时会同时校验候选所属的日间场景代际和地图，若场景已变化则拒绝旧请求并提示刷新，不会把旧候选写入新场景。

### 经营辅助与自动化

- 支持稀客订单专注模式，可调节料理/酒水显示数量并切换精简模式，减少滚动切换。
- 每笔稀客订单会先确定一组主执行方案。`任务料理置顶` 默认开启；普通经营中，游戏被动确认某笔唯一活动订单需要提交指定任务料理时，对应 `foodId + recipeId` 可以跳过普通的料理点单 Tag 和料理厌恶判断，但仍须满足料理解锁与库存、材料、厨具、预算、排除项、自动化收藏限定等硬门禁，配对酒水也必须满足当前点单。合法任务方案会排在自定义置顶、收藏料理/酒水和普通权重之前，并显示 `任务目标`。关闭该设置会恢复普通推荐顺序，但不关闭安全的任务状态捕获；未接取任务、特殊经营、订单身份不唯一或证据不完整时不启用任务置顶。页面料理与酒水首项、自动化、游戏界面置顶、列表高亮和目标厨具高亮都跟随同一主方案；多笔订单并存时，游戏内全局置顶与高亮目标优先选择主方案为任务方案的订单。真正写入游戏列表仍由 `游戏界面置顶推荐` 独立控制；目标变化时，Mod 只会在 Unity 主线程对已经打开的对应列表执行一次安全刷新。
- 设置页提供实验性自动化总开关和自动化参数；开启后可在经营中页的 `自动化` 视图分别配置稀客订单和普客订单的处理阶段。
- `自动化` 视图会显示真实参与本轮调度的厨具预约和订单日志标识；特殊经营中因规则拦截的普客会单独显示为未占用厨具，不计入预约容量。每笔订单的执行步骤默认折叠在对应条目的自动化详情中。稀客自动化开始时会从当时的主执行方案锁定料理、加料和酒水；开锅或送酒后，即使库存变化让页面重新计算出新的首项，已开始的任务也不会中途换菜。
- 多个 Windows 或 Android 伴随窗口可以同时查看数据，但同一时间只有一个窗口能取得自动化控制权并执行自动化动作。
- 稀客和普客的酒水、出锅料理都会直接提交到目标顾客桌面；订单满足后才触发评价。
- 每次自动开锅都会绑定精确厨具锅次。玩家先手动取走料理、立即复用同一厨具时，旧任务会退出且不会读取、存储或清理玩家的新料理；订单仍缺料理时再按最大回退次数重新调度。
- 阶段等待、真实失败和外部中断使用结构化状态分别处理；临时断线保留活动任务，重连后从 Mod 快照接管。关闭总开关会先作废排队命令并释放 Mod 所有权，不会清空厨具或回滚材料。
- 经营进入结算后，Mod 会停止本轮新的自动化和界面辅助操作，撤销本轮目标并清理未完成任务；旧目标不会带到下一次经营。
- 开锅、送达、入箱、订单评价或厨具复位的副作用无法确认时，Mod 会登记人工确认栅栏并在执行前阻止同一订单再次动作；普通重试、阶段开关、总开关、断线和控制权转移都不会绕过。处理游戏现场后，在订单卡片或独立的“待人工确认”列表点击“确认已处理”，只有 Mod 返回 ACK 后才会恢复该订单。
- 只开启“自动开始料理”而关闭“出锅后送达/自动送达料理”时，Mod 只登记防重复开锅的手动交接回执，不会送达、入箱或复位厨具；成品留给玩家处理。
- 若厨具或伙伴效果让出锅结果变成非目标料理，或目标订单连续不可达，自动化会将该成品放入保温箱，并在下一轮重新尝试目标料理。订单送达和保温箱写入都只允许提交一次，提交后只在原锅次内有界确认厨具复位。
- 自动开始料理时会固定尝试完成原生 QTE 奖励结算。

### 运行时修改

- 修改页可按名称或库存排序材料和酒水，并用快捷按钮调整当前运行时库存数量。
- 支持把当前存档可编辑材料或酒水批量设为 99。

### 伴随窗口体验

- 独立伴随窗口可移动、缩放、置顶，并会记住上次的普通窗口位置、大小和最大化状态；最小化或隐藏到托盘不会影响下次启动时的正常显示。
- `F8` / `RS Click` 可在游戏和伴随窗口之间切换；同一次手柄长按只触发一次，窗口隐藏时会重新显示。`F10` 可开启或关闭鼠标穿透锁定，游戏关闭后窗口会自动退出。
- 独立伴随窗口支持标准映射手柄导航：左摇杆/十字键移动，A 确认，B 返回，LB/RB 切页，LT/RT 滚动，X 收藏，Y 进入专注模式或切换精简模式；原有按键不变。连接、重连或窗口重新获得焦点后会先等待摇杆和按键回到中立位置，避免残留输入误触。
- 可在可信局域网内让另一台 Windows 或 Android 设备运行伴随窗口，连接运行游戏和 Mod 的主设备；正式 Tauri 客户端统一通过原生 TCP 代理访问受 Token 保护的私网 IPv4，Release 会提供可直接运行的独立 Windows x64 伴随窗口 EXE，并可附带按 ABI 拆分的 Android APK。
- 本地 API 断开时窗口会保留最近一次只读数据用于查看，重连期间停止派发新的自动化与置顶写入；Mod 已登记的自动料理锅次保留，重连后按服务端锅次状态继续接管。
- 设置页可分别调整背景透明度、文字透明度和界面字体大小，并可配置置顶状态、主题、焦点切换行为、连接与 LAN 访问、推荐权重、预算处理、缺失厨具过滤、任务料理置顶、收藏料理/收藏酒水置顶、带库存显示与排序的排除材料/酒水、同基础料理展示数量、稀客专注模式默认精简、实验性游戏界面置顶及列表目标高亮、目标厨具高亮。字体大小默认保持当前的 `100%`，可在 `90%` 至 `130%` 间调整并按设备独立保存。
- Mod 会按配置周期自动检查正式版更新；发现新版本后，工作台显示非模态提示并可直接进入更新分栏。网络失败会按阶段退避重试，下载和安装仍由用户手动确认。

### 日志、帮助与排查

- 概览页和经营中页 `诊断` 视图会显示关键快照耗时，用于排查运行时读取或自动化导致的卡顿。
- 日志页提供总日志开关、总日志目录、一键诊断包导出，以及仅限游戏电脑本机使用的 BepInEx 控制台显示/隐藏按钮；总日志统一记录 BepInEx/Unity 事件、自动化、前端候选跳过原因、经营诊断和运行时数据诊断。
- 经营中页的订单和自动化状态会显示 `日志 R-0001` / `日志 N-0001` 这类标识，可在总日志中按 `trace=R-0001` 或 `trace=N-0001` 查找同一笔订单的自动化记录。
- 最终没有可执行推荐方案时，订单提示和总日志会记录首个候选清零阶段、阶段计数、缺失材料/厨具与预算证据；这些诊断只解释现状，不会放宽 Tag、资源、预算或特殊经营评价门槛。
- 帮助页使用目录树展示功能用法、常见问题、卡顿排查和诊断信息收集步骤。
- Mod 不改写全局 `BepInEx.cfg`，也不释放 BepInEx 共享控制台。日志页按钮只管理当前游戏进程的控制台窗口，每次显隐成功后会立即保存为 Mod 下次启动的自动显示偏好；启动自动显示默认关闭，用户在全局 BepInEx 配置中显式开启的控制台不会被 Mod 启动流程覆盖。排查运行期问题时优先使用日志页的总日志和诊断包。

### 特殊经营支持

- 经营中页会显示游戏 `ChallengeType` 枚举中的固定中文 `InspectorName`。Mod 不维护挑战名称映射，也不使用社区昵称；元数据不可读时只显示原始挑战标识并记录诊断。
- 怪诞料理大赛的原生规则按阶段不同：第一阶段按喜好 Tag 命中数评价；第二阶段只在原生最高评价后再检查当前目标 Tag；第三阶段分身另有改判规则，古明地恋本体则使用揭示 Tag、护盾和投食进度机制。Mod 对第二阶段和第三阶段分身采用更严格的保守策略：保留原订单料理/酒水，并同时要求预估最高评价和当前目标 Tag。
- 幽幽子挑战和重修的第二阶段通过稀客触发正面符卡推进；只有稀客原生评价达到完美（ExGood）才会计数。Mod 会满足当前稀客的料理/酒水点单、避开该稀客自身的厌恶，并在排除点单 Tag 后命中至少 `2` 个额外喜好 Tag，以预估完美评价；当前资源无法构造该组合时保持无推荐并给出阻塞诊断，不以较低评价方案兜底。
- 幽幽子挑战剧情版第三阶段的主幽幽子按已送达料理与酒水的等级合计评价：等级合计至少为 `2` 时为普通（Normal），至少为 `5` 时为满意（Good），至少为 `8` 时为完美（ExGood）。
- 幽幽子重修第三阶段不使用上述等级合计规则，并且存在两种订单形态。稀客 `SpecialOrder` 按最终料理与酒水的完整 Tag 走标准点单评价：满足料理和酒水点单后形成基础 `2`，点单外命中的当前稀客喜好或厌恶继续影响结果，达到满意（Good）或完美（ExGood）时推进。精确料理/酒水的 `NormalOrder` 才使用 modifier-only 评价：精确匹配先得到普通（Normal，值为 `2`），之后只计算实际生效的动态料理 Tag 和额外材料新增 Tag；Mod 会严格核对加料和预期 modifier Tag，普通评价只能清理订单，不承诺推进。
- 目标营业额和符卡计数等展示值本身不改变推荐排序。结算副作用尚未确认的 BOSS 订单会暂停或阻止标准自动化，不猜测处理。开锅后若怪诞料理大赛的阶段或目标 Tag 已变化，Mod 会将不符合当前目标的成品放入保温箱，再按最新状态重新选择方案。
