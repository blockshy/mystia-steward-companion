# mystia-steward-companion

**mystia-steward-companion** 是面向《东方夜雀食堂》的 BepInEx IL2CPP Mod。它读取游戏当前运行时数据，并通过 Windows 或 Android 伴随窗口提供普客、稀客和夜间经营推荐。

项目由游戏内 Mod 读取运行时数据，并通过本地 API 提供给伴随窗口展示和操作。同机 Windows 客户端使用回环地址，其他 Windows 或 Android 设备可在可信局域网内连接。

## 功能概览

### 实时数据与推荐

- 实时读取已解锁料理、酒水、食材、库存、流行标签、明星店状态和当前经营场景。
- 普客页按当前地区推荐料理与酒水。
- 稀客页按候选稀客和点单 tag 推荐料理、加料与酒水，可在设置页调整推荐排序规则和同基础料理展示数量。
- 经营中页自动检测当前稀客和普客订单，并用 `推荐` / `自动化` / `诊断` 视图分开展示订单方案、自动化状态和排查信息。`推荐` 视图的稀客与普客页签统一使用 `当前订单方案` 展示框架：稀客显示点单主方案和候选料理、酒水，普客显示游戏原订单与当前执行方案。原始当前稀客、稀客点单和预计厨具占用集中在诊断视图。
- 经营中订单可按点单顺序或稀客分组排列；偏好命中但不满足点单的候选会直接进入同一推荐列表，并以喜好备选标识区分。
- 支持收藏稀客常用料理方案和酒水；也可在 `自定义推荐料理` 页为指定稀客配置固定料理、加料、全部点单或指定点单 tag，并通过功能总开关、稀客/基础料理分组和页面级/分组级批量命令统一管理启用与推荐置顶状态。

### 任务与稀客邀请

- `任务` 一级页包含 `任务列表` 和 `稀客邀请` 两个分栏。任务列表合并显示当前可接取任务与已接取且仍活动的任务，并使用 `全部`、`可接取`、`可完成`、`进行中`、`待确认` 页签切换分类和显示数量。每项任务还会显示任务定义关联的角色和该角色静态配置的相关场景；相关场景表示可能出现地点，不表示角色此刻实时所在位置。读档任务会在任务系统初始化完成后确认一次游戏原生条件状态；新接取任务会在创建完成后确认初始状态，之后只跟随游戏自身的任务刷新。读取链不完整时会显示明确状态，技术原因写入日志和诊断包，不会把不确定状态伪装成空列表或已完成。
- 首版可接取列表只发布已经过接取前后实机闭环验证的羁绊检查点任务：游戏日间运行态稳定时，Mod 在每次列表请求中通过 Unity 主线程重新读取当前日和永久调度事件，并严格校验任务前置节点、活动状态、循环属性、完成历史及任务/日间/稀客映射代际。Mod 不会为了显示列表而触发事件、接取或完成任务、领取奖励，普通角色对话触发的其他可接任务暂不进入列表。
- 可接取列表仅用于任务页展示，不参与任务料理置顶、自动化、游戏界面置顶、料理/材料/酒水列表项高亮、目标厨具高亮、目标桌位高亮或目标订单高亮；任务实际接取后，既有的活动任务与任务料理链才按各自严格条件生效。
- 稀客邀请分栏在日间运行态就绪后自动读取当前场景或全部场景候选；首次进入、切换范围、换图、日间场景重新初始化或重连时会重新读取，也可手动强制刷新。游戏暂时无法提供日间运行态时，页面会按 0.5、1、2、4 秒有限重试，之后显示具体原因并等待手动刷新或场景状态变化，不会把读取失败显示成空列表。候选列表读取不会刷新 NPC 或生成羁绊状态。
- 可邀请项支持单独邀请或一次邀请全部，不满足羁绊或已邀请的项会显示原因并禁用按钮；当前已邀请稀客会单独汇总显示。点击邀请时会同时校验候选所属的日间场景代际和地图，若场景已变化则拒绝旧请求并提示刷新，不会把旧候选写入新场景。

### 经营辅助与自动化

- 支持稀客订单专注模式，可调节料理/酒水显示数量并切换精简模式，减少滚动切换。
- 每笔订单先确定唯一主执行方案。`任务料理置顶` 默认开启；普通经营中，游戏被动确认某笔唯一活动稀客订单需要指定任务料理时，对应 `foodId + recipeId` 可以跳过普通料理点单 Tag 和料理厌恶判断，但仍须通过解锁、库存、材料、厨具、预算、排除项、自动化收藏限定等硬门禁，配对酒水也必须满足点单。合法任务方案排在自定义置顶、收藏料理/酒水和普通权重之前，并显示 `任务目标`；未接取任务、特殊经营、订单身份不唯一或证据不完整时不启用。
- 页面首项、自动化和游戏界面辅助都消费所属订单的同一主方案。游戏内同时保留至多一笔稀客目标和一笔普客目标，两类可并存；稀客槽内仍优先未送达的任务方案。每个目标只保留尚未送达的组件，订单送达、结束或身份失效后只清除对应槽，不影响另一类目标。列表、厨具或桌位同时属于两类目标时由一个 Mod 高亮对象在两种颜色间往返，不叠加两层；左下 HUD 卡片和投掷送达面板按所属订单颜色显示。稀客默认色为 `#FFDB2E`，普客默认色为 `#5FACD3`，可在实验性功能中分别自定义，并统一应用到料理/材料/酒水列表、加料料理选项、厨具、桌位和两处订单高亮。稀客与普客各自配置游戏列表置顶、加料料理选项、厨具、桌位和订单高亮；关闭一类不会影响另一类。
- 稀客和普客可分别开启加料料理选项。目标方案含加料时，制作页会在原基础料理后显示独立选项；相同基础料理和相同有序加料合并为一项，不同加料分别显示。基础料理保持原配方；加料项按所属目标色高亮，只加入自己的加料并按游戏规则扣除材料。选中后仍可切换到基础料理、其他料理或另一加料项；只有游戏在同一次提交中确认退回旧材料、装入新配方且正常返回，Mod 才结束旧事务。目标变化触发的料理列表刷新只重建料理行；只要权威配方、已选材料和现有出锅回调仍能精确复核，已经稳定应用的加料事务会保留原始身份，即使目标暂时为空也能继续出锅或正常关闭。完整视觉刷新会重建出锅区，因此已就绪的出锅回调会退回等待重新绑定。当前厨具没有目标配方时直接跳过；出现重复权威配方、收据漂移、事务处于副作用中间态，或目标变化落在活动换菜回调内时，才停止本场加料操作。料理行刷新失败不会冒充库存不确定，无法确认的 Insert 也不会重放。Mod 不清游戏原生料理回调、不禁用料理按钮，也不猜测退款或重放材料操作。
- 设置页的 `实验性功能` 分栏集中提供自动化总控、稀客自动化设置和普客自动化设置；经营中页的 `自动化` 视图只展示当前执行状态、订单级重试/重置和待人工确认事项。稀客与普客均可独立暂停调度，并按相同顺序配置送酒、开锅、送料理、完成订单和出错暂停；稀客收藏限定仍放在稀客自动化设置分区。
- 教学经营中会保留用户已开启的自动化设置，但暂停所有自动化动作，避免 Mod 跳过游戏要求玩家手动完成的教程步骤；离开教学经营后按原设置恢复。
- `诊断` 视图会显示按当前完整快照推导的预计厨具占用和订单日志标识；特殊经营中因规则拦截的普客会单独显示为未占用厨具，不计入预计容量。每笔订单的执行步骤仍默认折叠在 `自动化` 视图对应条目的详情中。稀客自动化开始时会从当时的主执行方案锁定料理、加料和酒水；开锅或送酒后，即使库存变化让页面重新计算出新的首项，已开始的任务也不会中途换菜。
- 物理厨具快照只分为完整和不可用。完整快照会先读取特殊事件锁定位置；锁定条目只保留字典位置和运行时实体身份并计数，不读取可能已被游戏销毁的状态或类型。其余控制器仍严格核对字典位置、控制器位置、空位/已摆放状态和可开状态；未摆放空位与锁定条目都不计入推荐或自动化容量。任一来源或未锁条目不完整时，本轮整体不可用，不用部分数据继续运行。存在锁定条目时，只有仍开放的控制器能够证明其可用类型，缺少开放证据的类型会暂时退出推荐，恢复后自动重新参与计算。
- 多个 Windows 或 Android 伴随窗口可以同时查看数据，但同一时间只有一个窗口能取得自动化控制权并执行自动化动作。
- 一般稀客和普客的酒水、出锅料理会直接提交到目标顾客桌面；任何直接送达都必须同时启用“自动完成订单”，确保 Mod 成为最后送达者时在同一次后端调用或料理任务事务中继续通过订单对应的精确原生评价入口完成结算。开启任一直送项会同步开启完成阶段，关闭完成阶段会同步关闭本组送酒和送料理；只开启自动开始料理时，成品仍留给玩家。后端也会在库存、厨具或订单副作用前拒绝不满足该约束的请求。血池地狱 BOSS 使用更严格的专用结算边界：只有自动送达料理和自动完成订单同时开启时，Mod 才会在复核原订单、当前双 Tag 策略、锅次和实际成品后完成料理送达，并按当前订单的原生类型完成评价与状态通知。显示在普客区域的 BOSS 指定料理订单会优先选择同时满足双 Tag 的严格方案；严格方案无解、但原料理和原酒水仍通过全部硬门禁时，才使用明确标记的受控推进方案。该方案仍由游戏正常结算，但伤害可能较低并增加狂暴。任一最终阶段关闭时仍保留成品并交给玩家。游戏可能在一段时间内开启玩家投掷送餐模式，该模式只决定玩家的送餐交互，不会阻断 Mod 的无界面结算；只有订单存在原生飞行中料理或酒水时才会无副作用等待。Mod 不会打开送餐界面，也不会生成或模拟投掷协程；订单、厨具、成品、动态目标、评价回调或经营会话无法精确复核时保持暂停。受控推进不会绕过这些门禁，也不会切换到其他结算路径。
- 每次自动开锅都会绑定精确厨具预约、原生身份、锅次和厨具内容代际，但不会跨帧保留游戏厨具对象。Mod 只被动观察游戏原生的开锅、取出、厨具内容换入，以及血池地狱的锁锅/可用性更新；每次读取成品、送达、复位或出锅前都会从当前物理目录重新确认同一厨具。挑战事件锁定、移除或替换厨具后，旧任务不会再访问原对象；订单仍缺料理时会基于新的完整厨具快照重新规划，未受影响的开放厨具可以继续工作。料理送达后的厨具清理或人工交接一旦严格结束，Mod 会立即释放该物理厨具；即使对应订单仍在等待精确评价回执，其他订单也能复用它，且旧回执按订单生命周期隔离，不会串到复用后的新订单。Mod 不读取或跟踪玩家托盘；玩家正常取出成品后，只要厨具已空闲且取出过程完整结束，自动化也能重新使用该厨具。原成品若仍由游戏保留，重新准备可能再次消耗材料，Mod 不会读取、移动或删除该成品。
- 自动化共用 Mod 对厨具完整状态的判定，不会只看游戏的“可开锅”标志。预约同时绑定本轮索引、原生实体身份和物理坐标，真正开锅前再次读取特殊事件锁定状态并复核三者；任何漂移只等待新快照，不在后端静默改选厨具。多类型厨具在同一轮只占用一次；排序靠前的订单等待某类厨具时，不会阻塞后续能使用其他厨具的订单。厨具只是被预约、占用或暂时锁定时仍只局部等待，不消耗阶段重试次数。
- 阶段等待、真实失败和外部中断使用结构化状态分别处理；临时断线保留活动任务，重连后从 Mod 快照接管。关闭单组送酒只作废排队和迟到命令，不影响已经登记的料理任务；关闭 `启用稀客处理` 或 `启用普客处理`、关闭该组送料理或完成阶段，才会只取消该组尚未进入不可逆步骤的 Mod 料理任务。关闭自动化总开关会取消全部可取消任务并释放控制权。任何取消都不会清空厨具、回滚材料或撤销已经开始的原生副作用。
- 经营进入结算后，Mod 会停止本轮新的自动化和界面辅助操作，撤销本轮目标并清理未完成任务；旧目标不会带到下一次经营。
- 开锅、送达、入箱、订单评价或厨具复位的副作用无法确认时，Mod 会登记人工确认栅栏并在执行前阻止同一订单再次动作；普通重试、阶段开关、总开关、断线和控制权转移都不会绕过。处理游戏现场后，在订单卡片或独立的“待人工确认”列表点击“确认已处理”，只有 Mod 返回 ACK 后才会按对应栅栏规则继续。
- 只开启“自动开始料理”而关闭“自动送达料理”时，Mod 只登记同一订单的防重复开锅回执，不会送达、入箱或复位厨具；玩家取出成品后，该回执不会继续占用已经空闲的厨具。
- 若厨具或伙伴效果让出锅结果变成非目标料理，或目标订单连续不可达，自动化会将该成品放入保温箱，并在下一轮重新尝试目标料理。订单送达和保温箱写入都只允许提交一次，提交后只在原锅次内有界确认厨具复位。
- 自动开始料理时会固定尝试完成原生 QTE 奖励结算。

### 运行时修改

- 修改页可按名称或库存排序材料和酒水，并用快捷按钮调整当前运行时库存数量。
- 支持把当前存档可编辑材料或酒水批量设为 99。

### 伴随窗口体验

- 独立伴随窗口可移动、缩放、置顶，并会记住上次的普通窗口位置、大小和最大化状态；最小化或隐藏到托盘不会影响下次启动时的正常显示。
- `F8` / `RS Click` 可在游戏和伴随窗口之间切换；同一次手柄长按只触发一次，窗口隐藏时会重新显示。`F10` 可开启或关闭鼠标穿透锁定，游戏关闭后窗口会自动退出。
- 独立伴随窗口支持标准映射手柄导航：左摇杆/十字键移动，A 确认，B 返回，LB/RB 切页，LT/RT 滚动，X 收藏，Y 进入专注模式或切换精简模式；原有按键不变。连接、重连或窗口重新获得焦点后会先等待摇杆和按键回到中立位置，避免残留输入误触。
- 可在可信局域网内让另一台 Windows 或 Android 设备运行伴随窗口，连接运行游戏和 Mod 的主设备；正式 Tauri 客户端统一通过原生 TCP 代理访问受 Token 保护的私网 IPv4，Release 会提供可直接运行的独立 Windows x64 伴随窗口 EXE，并可附带按 ABI 拆分的 Android APK。
- 本地 API 断开时窗口会保留最近一次只读数据用于查看，重连期间停止派发新的自动化与置顶写入；Mod 已登记的自动料理锅次保留，重连后按服务端锅次状态继续接管。
- 设置页可分别调整背景透明度、文字透明度和界面字体大小，并可配置置顶状态、主题、焦点切换行为、连接与 LAN 访问。`推荐` 分栏集中管理推荐权重、预算处理、缺失厨具过滤、任务料理置顶、收藏料理/收藏酒水置顶、带库存显示与排序的排除材料/酒水、同基础料理展示数量和稀客专注模式默认精简；`实验性功能` 分栏集中管理自动化总控、稀客/普客自动化，以及两类目标各自的游戏界面置顶、加料料理选项、厨具/桌位/订单高亮和高亮色。稀客默认 `#FFDB2E`，普客默认 `#5FACD3`；目标订单高亮同时覆盖左下 HUD 卡片和投掷送达面板，原生焦点轮廓保持不变。加料料理选项、目标桌位高亮和目标订单高亮默认关闭。字体大小默认 `100%`，可在 `90%` 至 `130%` 间调整并按设备独立保存。
- Mod 会按配置周期自动检查正式版更新；发现新版本后，工作台显示非模态提示并可直接进入更新分栏。网络失败会按阶段退避重试，下载和安装仍由用户手动确认。

### 日志、帮助与排查

- 概览页和经营中页 `诊断` 视图会显示关键快照耗时；经营诊断还集中显示原始当前稀客、当前稀客点单和预计厨具占用，用于排查运行时读取、目标选择或自动化导致的问题。
- 日志页提供总日志开关、总日志目录、一键诊断包导出，以及仅限游戏电脑本机使用的 BepInEx 控制台显示/隐藏按钮；总日志统一记录 BepInEx/Unity 事件、自动化、前端候选跳过原因、经营诊断和运行时数据诊断。
- 总日志开启期间若活动的 `aggregate-mod.log` 被外部删除或移走，Mod 会在下一条日志到达时重建原路径并继续记录。
- 经营中页的订单和自动化状态会显示 `日志 R-0001` / `日志 N-0001` 这类标识，可在总日志中按 `trace=R-0001` 或 `trace=N-0001` 查找同一笔订单的自动化记录。
- 最终没有可执行推荐方案时，订单提示和总日志会记录首个候选清零阶段、阶段计数、缺失材料/厨具与预算证据；这些诊断只解释现状，不会放宽 Tag、资源、预算或特殊经营评价门槛。
- 高亮失效时，请开启 `显示调试信息`，提供完整 `aggregate-mod.log`、经营中页诊断信息和对应截图或短视频。桌位高亮日志应保留 `Runtime seat highlight fill bound` 或 `Runtime seat highlight fill failed`；投掷送达面板日志应保留 `Runtime throw-delivery order highlight patched` 以及相关的 `fill bound`、`fill failed` 或 `fill retired`，并注明桌号、顾客、订单类型和操作顺序。
- 帮助页使用目录树展示功能用法、常见问题、卡顿排查和诊断信息收集步骤。
- Mod 不改写全局 `BepInEx.cfg`，也不释放 BepInEx 共享控制台。日志页按钮只管理当前游戏进程的控制台窗口，每次显隐成功后会立即保存为 Mod 下次启动的自动显示偏好；启动自动显示默认关闭，用户在全局 BepInEx 配置中显式开启的控制台不会被 Mod 启动流程覆盖。排查运行期问题时优先使用日志页的总日志和诊断包。

### 特殊经营支持

- 经营中页会显示游戏 `ChallengeType` 枚举中的固定中文 `InspectorName`。Mod 不维护挑战名称映射，也不使用社区昵称；元数据不可读时只显示原始挑战标识并记录诊断。
- 怪诞料理大赛的原生规则按阶段不同：第一阶段按喜好 Tag 命中数评价；第二阶段只在原生最高评价后再检查当前目标 Tag；第三阶段分身另有改判规则，古明地恋本体则使用揭示 Tag、护盾和投食进度机制。Mod 对第二阶段和第三阶段分身采用更严格的保守策略：保留原订单料理/酒水，并同时要求预估最高评价和当前目标 Tag。
- 幽幽子挑战和重修的第二阶段通过稀客触发正面符卡推进；只有稀客原生评价达到完美（ExGood）才会计数。Mod 会满足当前稀客的料理/酒水点单、避开该稀客自身的厌恶，并在排除点单 Tag 后命中至少 `2` 个额外喜好 Tag，以预估完美评价；当前资源无法构造该组合时保持无推荐并给出阻塞诊断，不以较低评价方案兜底。
- 幽幽子挑战剧情版第三阶段的主幽幽子按已送达料理与酒水的等级合计评价：等级合计至少为 `2` 时为普通（Normal），至少为 `5` 时为满意（Good），至少为 `8` 时为完美（ExGood）。
- 幽幽子重修第三阶段不使用上述等级合计规则，并且存在两种订单形态。稀客 `SpecialOrder` 按最终料理与酒水的完整 Tag 走标准点单评价：满足料理和酒水点单后形成基础 `2`，点单外命中的当前稀客喜好或厌恶继续影响结果，达到满意（Good）或完美（ExGood）时推进。精确料理/酒水的 `NormalOrder` 才使用 modifier-only 评价：精确匹配先得到普通（Normal，值为 `2`），之后只计算实际生效的动态料理 Tag 和额外材料新增 Tag；Mod 会严格核对加料和预期 modifier Tag，普通评价只能清理订单，不承诺推进。
- 血池地狱会动态指定两个料理 Tag。第二阶段混合生成 `NormalOrder` 与 `SpecialOrder`，第三阶段生成 `NormalOrder`；游戏回调可能只以声明的 `OrderBase` 视角暴露具体订单。Mod 仅在精确转换唯一成功，且订单及其顾客控制器均属于 canonical BOSS `1003` 时接管。`SpecialOrder` 继续要求原点单和双 Tag 全部成立；显示在普客区域的 BOSS `NormalOrder` 先搜索保留原料理、原酒水并同时满足双 Tag 的严格方案，只有严格方案无解且原订单仍可安全执行时才选择受控推进。页面推荐首项、自动化、游戏界面置顶以及料理/材料/酒水列表项、目标厨具、目标桌位和目标订单高亮共用最终选定的同一方案。Mod 可以自动送酒和开锅；匹配成品出锅后，只有料理送达和订单完成两个阶段都已开启，才会执行专用的无界面送达、评价与状态通知，否则进入人工交接。
- 目标营业额、符卡计数和其他尚未确认结算规则的展示值本身不改变推荐排序。身份、动态目标或评价链无法精确确认的特殊订单会暂停，不猜测处理。血池地狱最终送达前发现目标轮换时，旧成品走既有保温箱恢复链并按新目标重新规划；每个非空目标签名拥有独立回退预算。特殊事件锁定或摧毁厨具后，锁定实体会同时退出推荐、预约和高亮，尚未开锅的订单等待新快照并重新规划。专用结算会严格区分游戏的手动控制订单与标准订单；缺少对应原生回调或入口时不会跨类型兜底。Mod 不会模拟送餐界面、主动重启阶段、生成订单或恢复协程。
